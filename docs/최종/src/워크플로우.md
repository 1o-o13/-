# 3. ① 지원 · 1차 서류
**목적:** 지원서를 받고, AI가 요건별 근거를 찾아 주면 담당자가 2차에 올릴 사람을 정합니다. 1차에는 **점수가 없고 자동 탈락도 없습니다** (11/12 하드 필터 제거).

![안쪽 흐름 ① 1차 서류](fig:wf_doc.png)

---

**시작 조건:** 공고가 게시되어 접수 기간 안이고, 지원자가 로그인했으며 다른 공고에 진행 중인 지원이 없습니다.

**순서**
1. **지원자 — 지원서 작성:** 팀 4쪽 양식 순서로 인적사항·학력·경력·프로젝트·자기소개서를 쓰고 증명사진을 올립니다. AI 처리(국외 전송) 동의는 필수입니다. 쓰는 중에는 임시 저장됩니다.
2. **지원자 — 제출:** 제출하면 그 시점의 이력서가 지원 건에 **스냅숏**(JSON)으로 저장되고 단계가 '서류 접수'가 됩니다. 접수 마감 전·서류 심사 중이면 고칠 수 있고, 마지막 저장본이 제출본입니다.
3. **담당자 — 평가 기준 확인:** 공고 설명에서 필수·우대 요건을 뽑아 둔 기준을 보고 고칠 수 있습니다.
4. **시스템 — AI 1차 검토 (`AI 1차 검토 실행` 버튼):** 지원자마다 요건별로 이력서에서 근거 문장을 찾고(검색), LLM이 요건마다 '충족·근거 없음' 라벨과 원문 인용, 의견을 씁니다.
5. **시스템 — 코드 검증:** 인용이 이력서 원문에 정말 있는지, 결론 규칙(추천 근거는 '충족' 요건에서만)을 지켰는지 코드가 봅니다. 틀리면 그 결론은 비워 담당자가 판단하게 합니다.
6. **시스템 — 추천 정하기:** 공고 지원자의 30%까지만 '추천'을 붙이고 나머지는 '비추천' 또는 빈칸입니다.
7. **담당자 — 검토와 체크:** 지원자마다 근거·의견을 보고 합격할 사람을 체크합니다. AI가 '비추천'한 사람은 체크할 수 없습니다(빈칸은 가능).
8. **담당자 — '결정 확인 (합격 n · 불합격 m)' 한 번:** 체크한 사람은 1차 합격, 나머지는 불합격으로 한 번에 확정되고 발표됩니다.
9. **시스템 — 발표 · 알림:** 메일·문자(가짜 발송 기록)와 홈페이지 알림이 가고, 단계가 바뀌며(1차 합격 → 합격 후 단계 끝 → 응시 안내 발송), 합격자에게는 면접 인계 데이터(이력서 확인 포인트·결핍 가치)가 만들어집니다.

| 항목 | 내용 |
|---|---|
| 화면 | 채용 홈 CAN-001 · 지원서 CAN-005 · 지원 현황 CAN-007 · 1차 서류 결정 ADM-040 |
| API | `POST /api/site/postings/{pid}/apply` · `GET·PUT .../draft` · `POST /api/admin/postings/{pid}/document/screen` · `POST /api/admin/applications/{id}/document` · `POST /api/admin/postings/{pid}/document/announce` |
| 저장 | application(이력서 스냅숏) · document_criteria · document_evaluation(AI 근거·인계 데이터) · stage_result · application_stage · announcement · notification |
| 규칙·예외 | 한 번에 한 공고만 진행. 발표 뒤 합격 취소는 부정행위일 때만, 사유 필수. AI 근거는 지원자에게 공개하지 않음 (최종 결정을 사람이 하므로 설명 의무 대상 아님) |
| 다음 | 1차 합격자는 ② 단계로, 불합격자는 지원 현황에서 감사 인사와 함께 결과 안내 |

# 4. ② 1차 발표 · 2차 안내
**목적:** 합격자가 2차(코딩 + AI 면접)를 준비하게 하고, 면접 중 대기 시간을 줄이려고 질문을 미리 만들어 둡니다.

![안쪽 흐름 ② 질문 만들기](fig:wf_qgen.png)

---

**시작 조건:** 1차 결과가 발표되어 지원 건이 '응시 안내 발송' 단계입니다.

**순서**
1. **시스템 — 질문 미리 만들기 (1차 합격 즉시):** 직무별 질문 은행에서 이력서 경험과 겹치는 주제를 골라 1·2번(비기술)과 기술 본 질문 후보를 만듭니다. 근거는 회사 문서의 tier 3 공개 청크입니다.
2. **시스템 — 검증 7가지:** 길이, 지시문 베끼기, 근거 금지어, 개인정보, 문서 번호 노출, 근거 청크(tier 3·internal 아님), 다른 질문과 중복. 떨어지면 1번 다시 만들고, 또 떨어지면 은행의 기본 질문(이미 검증됨)을 씁니다. 통과한 질문만 '준비됨'으로 저장합니다.
3. **지원자 — 결과 확인:** 알림을 눌러 1차 결과를 봅니다. 합격이면 2차 응시 기간과 준비물이 나옵니다.
4. **지원자 — 2차 응시 안내 읽기:** 진행 순서, 면접 규칙(10문항·생각 시간·답변 3분), **AI 활용 고지**(AI가 하는 일, 합격 결정은 담당자, 개인정보 가림, 기록 180일 뒤 파기)를 읽습니다.
5. **지원자 — 연습 면접 (선택):** 질문 2개를 실제와 같은 흐름(음성 → 생각 10초 → 녹음 40초 → 인식 글)으로 해 봅니다. 평가·저장하지 않습니다.
6. **지원자 — 글로 답하기 신청 (선택):** 말하기가 어려우면 사유를 적어 신청합니다.
7. **담당자 — 글로 답하기 승인·거절:** AI 면접 결과 화면 위쪽 목록에서 사유를 보고 정합니다. 거절 사유는 지원자에게 보입니다.

| 항목 | 내용 |
|---|---|
| 화면 | 1차 결과 CAN-006 · 2차 응시 안내 CAN-008 · AI 면접 결과(신청 목록) ADM-033 |
| API | `GET /api/interview/applications/{id}/guide` · `GET .../practice` · `POST .../practice/stt` · `GET·POST .../accommodation` · `POST /api/admin/accommodations/{id}/decision` |
| 저장 | question_bank(읽기) · prepared_question · llm_call · answer_accommodation |
| 규칙·예외 | 면접을 시작한 뒤에는 글로 답하기 신청 불가. 미리 만든 질문이 없으면 면접 때 새로 만듦(느려질 뿐 막히지 않음) |
| 다음 | 응시 기간이 되면 '응시 시작'이 열림 → ③ |

# 5. ③ 사전 점검 · 본인 확인 · 코딩 테스트
**목적:** 응시 환경과 본인 여부를 확인하고, 개발 직군은 코딩 테스트를 봐서 면접 3번 질문의 재료(약점)와 난이도를 정합니다.

**시작 조건:** 응시 기간 안이고 2차 대상입니다.

**순서**
1. **지원자 — 장치 점검:** Chrome, 카메라, 마이크(소리 막대), 얼굴 1명, 업로드 속도를 확인합니다.
2. **지원자 — 동의:** 필수 3개(음성 녹음·AI 평가 활용·국외 전송)와 선택 1개(얼굴 대조). 필수 동의가 없으면 시작할 수 없습니다. 이때 응시 1회(interview_session)가 만들어집니다.
3. **지원자 → 시스템 — 본인 확인:** 웹캠 프레임 1장을 보내면 face 컨테이너(InsightFace)가 지원서 증명사진과 거리를 잽니다. 0.55 이하 일치, 0.75 이하 애매(재촬영), 그 위 불일치. **사진은 저장하지 않고 거리만** 남깁니다. 결과는 바로 화면에 보입니다.
4. **재촬영:** 애매·불일치면 3번까지 다시 찍습니다. 얼굴을 못 찾은 촬영은 횟수에 넣지 않습니다. 그래도 불일치면 응시는 막고 의심 건으로 담당자에게 넘깁니다. 얼굴 대조를 거부했으면 담당자가 직접 확인합니다.
5. **지원자 — 움직임 확인(라이브니스):** 고개 돌리기 → 정면 → 눈 깜빡이기. 사진·영상으로 대신 보는 것을 막는 단계이고, 실패해도 막지 않고 의심 건으로 남깁니다.
6. **지원자 — 코딩 테스트 (개발 직군):** 1·2번(기본 등급)을 풀면 결과로 등급을 정해 3번을 새로 출제합니다. 예제 실행과 제출이 되고, 채점은 judge 컨테이너가 하며 지원자에게는 통과 수만 보입니다.
7. **시스템 — 코딩이 끝나면:** 등급(예: 골드3)과 약점 요약(알고리즘·실패 그룹·약점 태그)을 저장하고, 약점으로 면접 3번 질문을 만들어 검증합니다. 등급으로 난이도 대역(상·중·하)이 정해집니다.

| 항목 | 내용 |
|---|---|
| 화면 | 사전 점검·동의·본인 확인 CAN-009 · 코딩 테스트 CAN-010 |
| API | `POST /api/interview/applications/{id}/precheck` · `.../identity` · `.../liveness` · `POST /api/coding/applications/{id}/start` · `POST /api/coding/sessions/{id}/run` · `.../submit` · `.../finish` |
| 저장 | interview_session(점검·동의) · identity_check · suspicion_case · coding_session · coding_attempt · coding_submission · coding_result · prepared_question(3번) |
| 규칙·예외 | 영상은 브라우저 밖으로 나가지 않음(본인 확인 프레임 1장만). 비개발 직군은 코딩 없이 바로 ④ |
| 다음 | 코딩이 끝나야 면접 안내(CAN-011)가 열림 → ④ |

# 6. ④ AI 화상면접
**목적:** 10문항을 물어 답변을 받고, 답변마다 점수를 매겨 다음에 무엇을 물을지 정합니다.

**시작 조건:** 점검·본인 확인을 마쳤고, (개발 직군은) 코딩이 끝났습니다.

**시작할 때**
1. **지원자 — 면접 안내(CAN-011) 열기:** 이때 서버가 1~3번 질문을 준비(미리 만든 것 꺼내기)하고, 준비되면 'AI 화상면접 시작'이 켜집니다.
2. **지원자 — 시작:** 공고의 면접 설정이 **잠기고**(이후 수정 불가), 인계 데이터·코딩 약점·난이도 대역·모델을 응시에 복사해 면접 도중 바뀌지 않게 고정합니다. 면접 그래프(thread)가 시작됩니다.

**한 문항마다**
1. **질문 제시:** 미리 만든 Supertonic 음성을 재생하고 같은 글을 띄웁니다. 번호·질문 종류·남은 시간이 보이고, 생각 시간에는 다시 듣기와 글자 크기 조절이 됩니다.
2. **생각 시간:** 비기술 10초, 기술 20초. 질문 음성이 끝난 뒤부터 셉니다. 녹음하지 않습니다.
3. **답변 녹음:** 음성만 녹음합니다. '답변 끝'을 누르거나 3분이 지나면 끝납니다. 재녹음은 없습니다. 침묵 비율은 재기만 하고(비언어 점수용) 자동 제출하지 않습니다.
4. **업로드 → STT:** 음성을 올리면(실패 시 3번까지 다시) worker가 STT를 맡기고, 인식이 끝나면 **음성을 바로 지웁니다**. 질문의 핵심어를 STT에 힌트로 줍니다.
5. **인식 글 확인:** 인식된 글이 화면에 뜨면 지원자가 틀린 곳만 고치고(글자 30%까지) '완료'를 누릅니다. 60초가 지나면 원본 그대로 진행합니다. 원본·수정본·수정 비율을 모두 남깁니다.
6. **판정:** 개인정보를 가린 글로 LLM이 판정합니다(아래 안쪽 흐름 ③). 기술은 0~100점·루브릭·인용, 비기술은 의견만.
7. **다음 결정 (`next_action`):** 70점 이상·깊이 2 미만이면 꼬리질문(면접 전체에서 2개 주제까지), 본 질문 40점 미만이면 재질문(주제당 1번), 그 밖은 다음 주제, 10번째면 종료. 높은 점수라도 질문과 관련 없는 답(관련성 0.4 미만)이면 범위를 좁혀 다시 묻습니다.
8. **다음 질문:** 꼬리·재질문은 그 자리에서 만들고 검사한 뒤(안쪽 흐름 ②의 아래 줄), 본 질문은 미리 만든 것을 꺼냅니다. SSE로 화면에 알립니다.

# 7. ⑤ 평가 · 확정
**목적:** 응시 한 번을 하나의 점수로 정리하고, 그 점수가 근거와 맞는지 자동으로 검사한 뒤 담당자가 확정합니다.

![안쪽 흐름 ④ 최종 평가 → 확정 → 2차 종합 → 최종 결정](fig:wf_final.png)

---

**순서**
1. **시스템 — 주제 점수:** 본 질문과 그 꼬리·재질문을 한 주제로 묶어 `깊이 점수(0·30·60) + 40 × 평균 점수 / 100`. 깊이 답할수록 높습니다.
2. **시스템 — 최종 평가 v1:** 내용 60(주제 점수 평균 × 0.6) · 언어 30(답변별 구조·용어·의도) · 비언어 10(시간 안에 마침·침묵 비율). 의견으로 프로젝트 적합성·확장성을 씁니다(점수 아님).
3. **시스템 — 5검사:** ① 형식·범위 ② 인용이 답변 안에 있나 ③ 기술 답변 점수 누락 ④ 금지 요소 ⑤ 근거–점수 정합(평가 모델과 다른 사내 모델). 하나라도 실패하면 재평가 v2, 또 실패하면 담당자 알림이 생기고 확정할 수 없습니다.
4. **지원자 — 응시 완료 안내:** "면접이 종료되었습니다"와 최종 발표일만 보입니다.
5. **담당자 — 리포트 검토:** 물어본 순서대로 질문·근거 문서·답변(인식 원본·수정 비율)·점수·루브릭·판정 근거, 주제 점수(프로젝트 이름·막대), 코딩 약점, 본인 확인·감독 기록, 표정·목소리 구간을 봅니다.
6. **담당자 — 의심 건 처리 · 메모:** 의심 건마다 결정과 사유를 남깁니다. AI 점수는 고칠 수 없고 메모만 남길 수 있습니다.
7. **담당자 — '평가 확정':** 검증을 통과한 버전만 확정됩니다. 확정하면 2차 종합 점수가 만들어지고 공고 전체 순위가 다시 매겨집니다.
8. **필요하면 — 재응시 부여:** 끝났거나 장애로 멈춘 응시에 최대 3차까지 새 질문으로 다시 보게 할 수 있습니다.

| 항목 | 내용 |
|---|---|
| 화면 | 응시 완료 CAN-013 · AI 면접 결과 목록·리포트 ADM-033 |
| API | `GET /api/admin/interviews` · `GET .../interviews/{sid}` · `POST .../interviews/{sid}/confirm` · `POST .../reattempt` · `POST .../notes` · `POST /api/admin/suspicions/{id}/decision` |
| 저장 | interview_evaluation · evaluation_check · ai_error_alert · suspicion_case · interview_note · stage2_score |
| 다음 | 공고의 2차 대상자 점수가 모이면 → ⑥ |

# 8. ⑥ 최종 결정 · 발표
**목적:** 2차 종합 점수와 AI 추천을 참고해 담당자가 합격자를 정하고 한 번에 알립니다.

**순서**
1. **시스템 — 2차 종합:** 면접 60% + 코딩 40%. 면접 50점 미만이나 코딩 40점 미만은 **과락**으로 추천하지 않습니다.
2. **시스템 — AI 순위·추천:** 총점 순으로 순위를 매기고, 과락이 아닌 사람 중 위에서 **모집 인원 × 2**까지 '합격 추천'을 붙입니다(예비 합격 없음, 임시 규칙).
3. **담당자 — 합격 체크:** 순위·면접·코딩·종합·AI 추천을 보고 합격할 사람을 체크합니다. 과락이거나 처리하지 않은 의심 건이 있으면 체크할 수 없습니다. 아직 2차 진행 중인 사람은 아래에 따로 보이고 이번 확정에서 빠집니다.
4. **담당자 — '결과 확정' 한 번:** 체크한 사람은 최종 합격, 나머지는 불합격으로 확정되고 메일·문자·홈페이지 알림이 갑니다. 확정 뒤에는 바꿀 수 없습니다.
5. **지원자 — 최종 결과 확인:** 합격자는 축하 인사와 입사 안내 예정, 불합격자는 감사 인사와 격려 문구를 봅니다. 확정 전에는 지원자에게 아무것도 보이지 않습니다.
6. **시스템 — 기록 파기:** 최종 발표 후 180일이 지나면 매일 03:00 작업이 면접 기록을 지웁니다.

| 항목 | 내용 |
|---|---|
| 화면 | 최종 합격 결정 ADM-042 · 지원 현황 CAN-007 |
| API | `GET /api/admin/postings/{pid}/final` · `POST /api/admin/postings/{pid}/final/announce` |
| 저장 | stage2_score(순위·추천) · stage_result(final) · application_stage(final_pass·final_fail) · announcement · notification |

허용된 이동 25개는 `stage_transition` 표에 있고, 단계를 바꿀 때마다 DB 트리거가 확인해 그 밖의 이동은 거부합니다. 이동할 때마다 `application_stage_log`에 누가·왜 바꿨는지 남깁니다.

## 메인 그래프 (지원 건 1개 = thread 1개)
지원 건의 큰 흐름도 LangGraph로 돌립니다. 사람의 판단이나 바깥 사건을 기다려야 하는 곳에서 멈추고(interrupt), 그 일이 생기면 같은 thread로 이어 갑니다. 진행 상태는 PostgreSQL에 저장해 서버가 다시 켜져도 이어집니다.

| 순서 | 노드 | 하는 일 | 기다리는 것 |
|---|---|---|---|
| 1 | retrieve → score → verify | 1차 서류: 비교 문서 검색 → AI 의견 → 코드 검증 | — |
| 2 | hr_screen | 담당자 1차 판단 | **사람 판단 1** |
| 3 | save_decision → handoff | 결정 저장, 합격이면 면접 인계 데이터 만들기 | — |
| 4 | wait_invite · wait_access | 응시 안내 발송 · 지원자 접속 | 바깥 사건 1·2 |
| 5 | wait_ct2 → s1 → wait_ct_end | 코딩 1·2번 종료 → 3번 문제 준비 → 3번 종료 (코딩 없는 직군은 건너뜀) | 바깥 사건 3·4 |
| 6 | device_check → interview | 점검·본인 확인 → 면접 그래프가 끝나기를 기다림 | 바깥 사건 5 |
| 7 | final | 담당자의 최종 선발 | **사람 판단 2** |

늦게 온 사건이 엉뚱한 단계를 깨우지 않도록, 다시 시작할 때 넘기는 값에 지금 단계(phase)를 넣어 확인합니다.

# 12. 예외 상황 처리

| 침묵 답변 | STT 없이 무응답(silent) 0점 → 다음 주제 | interview_answer |
| 판정 30초 초과 | 대체 모델(Haiku 5.5 · qwen3:1.7b)로 다시 | llm_call |
| 판정 60초 초과·형식 오류 | 점수 보류(parse_error) → 다음 주제, 면접 계속 | answer_judgement |
| 질문 생성 실패 | 은행의 기본 질문 또는 고정 기본 질문 | prepared_question, interview_question |
| 탭·창 이탈 | 1번째 경고, 2번째이거나 한 번에 10초 이상이면 응시 포기 | proctor_event |

| 본인 확인 불일치 | 재촬영 3번까지, 그 뒤 불일치면 응시를 막고 의심 건 | identity_check, suspicion_case |
| 연결 끊김·새로고침 | 같은 문항부터 이어서 (이미 낸 답변은 바뀌지 않음) | interview_session |
