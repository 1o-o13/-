# 와치타워 — 3급 프로젝트 문서
<!--meta: doc=PRJ-OBS-3; doc_type=project; tier=3; topic=OBS; disclosure=public; status=done; stages=1차|2차-->

## 와치타워 1. 두 서버 로그 합치기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-OBS-01-->
서버 두 대의 로그를 시간순으로 합쳐 봐야 할 때가 많습니다. 각 로그는 이미 시간순이므로 투 포인터를 앞에서부터 움직이며 더 이른 줄을 먼저 내보내면 한 번에 합칠 수 있습니다. 서버 시계가 조금씩 달라 순서가 미세하게 어긋날 수 있다는 점은 화면에 함께 표시합니다.

## 와치타워 2. 오류율 알림 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-OBS-2-->
서비스 오류율 알림은 최근 5분 동안 요청 대비 오류 비율을 슬라이딩 윈도우로 계산해, 2%를 넘는 상태가 3분 이상 이어질 때 울립니다. 순간적인 튐에 알림이 울리지 않도록 '이어진 시간' 조건을 함께 둡니다.

## 와치타워 3. 분산 트레이스 조립 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-OBS-01-->
한 요청이 여러 서비스를 거친 흐름은 OpenTelemetry 트레이스로 남습니다. 서비스마다 따로 수집된 스팬 목록을 시작 시각 순으로 정렬한 뒤 투 포인터 방식으로 병합하고, 부모-자식 관계로 트리를 만들어 어느 구간이 느린지 보여 줍니다. 모든 요청을 저장하면 비용이 커서 느리거나 실패한 요청은 모두, 나머지는 1%만 남기는 꼬리 샘플링을 씁니다.

## 와치타워 4. 운영 대시보드 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-OBS-2-->
운영 대시보드는 서비스마다 같은 네 지표(요청 수, 오류율, 지연, 포화도)를 같은 배치로 보여 줘서, 처음 보는 서비스도 바로 읽을 수 있게 했습니다.

# 쉽잇 — 3급 프로젝트 문서
<!--meta: doc=PRJ-CID-3; doc_type=project; tier=3; topic=CID; disclosure=public; status=done; stages=1차|2차-->

## 쉽잇 1. 바뀐 모듈만 빌드 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-CID-01-->
여러 모듈이 서로 의존하는 저장소에서 한 모듈이 바뀌면 그 모듈에 의존하는 모듈도 다시 빌드해야 합니다. 의존 관계를 그래프로 두고 바뀐 모듈에서 BFS로 따라가며 영향받는 모듈을 모두 찾아 그것만 빌드합니다. 바뀌지 않은 모듈은 캐시된 결과를 씁니다.

## 쉽잇 2. 서비스 배포 순서 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CID-2-->
배포 순서도 의존 그래프로 정합니다. 다른 서비스에 의존하지 않는 서비스부터 배포하도록 진입 차수가 0인 것부터 큐에 넣는 위상 정렬(BFS 방식)을 쓰고, 같은 단계에 있는 서비스는 동시에 배포합니다. 그래프에 순환이 있으면 배포를 멈추고 알립니다.

## 쉽잇 3. 대규모 병렬 빌드 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-CID-01-->
빌드 작업이 수백 개로 늘자 BFS 위상 정렬로 단계를 나누고 단계 안의 작업을 빌드 서버 여러 대에 나눠 돌립니다. 가장 오래 걸리는 경로(임계 경로)에 있는 작업을 먼저 배정해 전체 시간을 줄였고, 빌드 결과 캐시는 입력 파일 해시로 찾아 다른 브랜치에서도 다시 씁니다.

## 쉽잇 4. 배포 화면 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-CID-2-->
배포 화면은 서비스별 현재 버전과 배포 중인 버전, 카나리 비율을 한눈에 보여 주고, 문제가 있으면 버튼 하나로 이전 버전으로 되돌리게 합니다.

# 플레이온 — 3급 프로젝트 문서
<!--meta: doc=PRJ-VOD-3; doc_type=project; tier=3; topic=VOD; disclosure=public; status=done; stages=1차|2차-->

## 플레이온 1. 화질 자동 선택 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-VOD-01-->
시청자의 네트워크 속도에 따라 화질을 고르는 적응형 재생에서, 가장 단순한 방법은 최근 측정한 다운로드 속도보다 낮은 비트레이트 중 가장 높은 것을 고르는 그리디 방식입니다. 속도가 흔들릴 때 화질이 자주 바뀌지 않도록 한 단계 올릴 때는 여유를 더 둡니다.

## 플레이온 2. 구간별 화질 배분 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-VOD-2-->
업로드된 영상은 360p부터 1080p까지 여러 화질로 변환(트랜스코딩)합니다. 장면마다 필요한 비트레이트가 달라, 구간별로 화질-용량 표를 만든 뒤 전체 용량 한도 안에서 화질 합이 가장 높아지는 조합을 DP로 고릅니다.

## 플레이온 3. 라이브 변환 서버 배분 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-VOD-01-->
라이브 방송에서는 변환 서버 수가 정해져 있어, 동시 방송이 몰리면 어떤 방송에 어떤 화질 세트를 줄지 정해야 합니다. 시청자 수와 화질별 비용을 놓고 DP로 배분을 계산하되, 계산이 1초를 넘지 않게 화질 세트를 몇 가지로 묶어 상태 수를 줄였습니다.

## 플레이온 4. 재생기 끊김 진단 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-VOD-2-->
재생기는 HLS 영상을 작은 조각으로 받아 재생합니다. 다음 조각을 미리 받아 두는 버퍼 길이를 보여 주는 진단 모드를 두어, 끊김 신고가 오면 원인이 네트워크인지 변환인지 바로 구분합니다.

# 팩토리아이 — 3급 프로젝트 문서
<!--meta: doc=PRJ-IOT-3; doc_type=project; tier=3; topic=IOT; disclosure=public; status=done; stages=1차|2차-->

## 팩토리아이 1. 센서 값 이동 평균 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-IOT-01-->
공장 설비 센서는 1초마다 온도와 진동 값을 보냅니다. 값이 순간적으로 튀는 잡음을 줄이기 위해 최근 30초 값의 이동 평균을 슬라이딩 윈도우로 계산하고, 평균이 기준을 넘을 때만 경고를 띄웁니다. 새 값이 들어오면 가장 오래된 값을 빼는 방식이라 매번 다시 더하지 않습니다.

## 팩토리아이 2. 주기가 다른 센서 맞추기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-IOT-2-->
온도 센서와 진동 센서는 보내는 주기가 달라 시각이 정확히 맞지 않습니다. 두 센서 기록을 시간순으로 두고 투 포인터로 훑으며, 각 진동 값에 가장 가까운 시각의 온도 값을 짝지어 하나의 표로 만듭니다. 차이가 2초를 넘으면 짝을 짓지 않습니다.

## 팩토리아이 3. 엣지에서 진동 분석 (상)
<!--meta: sec=s3; dept=BE|EMB; level=신입|주니어|시니어; ct_band=상; related=ISS-IOT-01-->
설비 고장 전에는 진동의 특정 주파수가 서서히 커집니다. 엣지 장비에서 10초 단위 슬라이딩 윈도우로 주파수 분석을 하고 결과 요약만 서버로 보내 통신량을 줄였습니다. 윈도우를 겹쳐 움직이면 정확도가 오르지만 엣지 장비의 계산이 늘어 겹침 비율을 50%로 정했습니다.

## 팩토리아이 4. 센서 게이트웨이 (중)
<!--meta: sec=s4; dept=EMB; level=신입|주니어; ct_band=중; related=PRJ-IOT-2-->
센서 게이트웨이는 C++로 만든 엣지 프로그램이 MQTT로 서버에 값을 보냅니다. 공장 네트워크가 끊기면 최대 24시간치를 장비 안에 쌓아 두었다가 다시 연결되면 순서대로 보냅니다.

# 헬프데스크 — 3급 프로젝트 문서
<!--meta: doc=PRJ-HLP-3; doc_type=project; tier=3; topic=HLP; disclosure=public; status=done; stages=1차|2차-->

## 헬프데스크 1. 문의 처리 순서 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-HLP-01-->
고객 문의는 티켓으로 쌓이고 상담원이 하나씩 처리합니다. 결제 오류처럼 급한 문의와 오래 기다린 문의가 먼저 처리되도록, 긴급도와 대기 시간을 합친 점수로 우선순위 큐를 만듭니다. 오래 기다릴수록 점수가 올라 계속 밀리는 문의가 없게 합니다.

## 헬프데스크 2. 상담원 배정 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-HLP-2-->
들어온 티켓을 상담원에게 배정할 때, 그 분야를 다룰 수 있는 상담원 중 지금 맡은 티켓이 가장 적은 사람에게 주는 그리디 방식을 씁니다. 상담원마다 동시에 맡을 수 있는 최대 수를 두고, 모두 찼으면 대기열에 남깁니다.

## 헬프데스크 3. 묶음 재배정 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-HLP-01-->
상담원의 숙련도, 언어, 현재 부담을 모두 보면 그리디 배정은 전체 대기 시간을 최소로 만들지 못합니다. 1분마다 쌓인 티켓을 모아 최소 비용 매칭으로 풀어 보았지만 계산 시간이 길어, 지금은 그리디 배정을 기본으로 하고 대기가 길어질 때만 묶음 재배정을 합니다.

## 헬프데스크 4. 문의 요약 (중)
<!--meta: sec=s4; dept=AI; level=신입|주니어; ct_band=중; related=PRJ-HLP-2-->
긴 문의 내용은 LLM으로 세 줄 요약을 만들어 상담원 화면에 먼저 보여 줍니다. 요약에 고객 이름·연락처가 들어가지 않도록 요약 전에 개인정보를 가리고, 요약이 원문에 없는 내용을 만들지 않았는지 원문 문장과 대조합니다.

# 비드엔진 — 3급 프로젝트 문서
<!--meta: doc=PRJ-ADS-3; doc_type=project; tier=3; topic=ADS; disclosure=public; status=done; stages=1차|2차-->

## 비드엔진 1. 예산 안에서 광고 고르기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-ADS-01-->
광고주는 하루 예산을 정해 두고, 입찰 서버는 광고 요청이 올 때마다 낼 광고를 고릅니다. 남은 예산이 있는 광고 중 예상 수익(입찰가 × 예상 클릭률)이 가장 큰 것을 고르는 그리디 방식이 기본이며, 예산이 오전에 다 써지지 않게 시간대별로 나눠 씁니다.

## 비드엔진 2. 노출 횟수 제한 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-ADS-2-->
같은 사용자에게 같은 광고를 하루 3번 넘게 보여 주지 않도록 노출 횟수를 셉니다. 사용자 수가 많아 정확히 세면 메모리가 커서, 이미 본 사용자인지는 블룸 필터(여러 해시 함수를 쓰는 비트 배열)로 먼저 거르고 횟수는 근사 카운터로 셉니다. 블룸 필터는 '봤다'고 잘못 답할 수는 있어도 '안 봤다'고 잘못 답하지는 않습니다.

## 비드엔진 3. 100ms 안에 후보 좁히기 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-ADS-01-->
실시간 입찰은 100ms 안에 답해야 합니다. 광고 후보를 타깃 조건별로 미리 정렬된 목록(역색인)으로 두고, 요청의 조건 목록들을 투 포인터로 교집합해 후보를 빠르게 좁힙니다. 점수 계산은 좁힌 후보 상위 수백 개에만 합니다.

## 비드엔진 4. 노출·클릭 집계 (중)
<!--meta: sec=s4; dept=DATA; level=신입|주니어; ct_band=중; related=PRJ-ADS-2-->
광고 노출·클릭 로그는 하루 20억 건으로, 실시간 집계는 스트림으로, 정산용 집계는 다음 날 배치로 한 번 더 계산해 두 결과를 비교합니다.

# 레이크하우스 — 3급 프로젝트 문서
<!--meta: doc=PRJ-DWH-3; doc_type=project; tier=3; topic=DWH; disclosure=public; status=done; stages=1차|2차-->

## 레이크하우스 1. 날짜별 파티션 저장 (하)
<!--meta: sec=s1; dept=BE|DATA; level=신입|주니어; ct_band=하; related=INC-DWH-01-->
매일 밤 각 서비스의 DB를 데이터 레이크로 복사한 뒤 날짜와 서비스 기준으로 정렬해 파티션별 파일로 저장합니다. 정렬해 두면 '어제 주문만' 같은 조회가 필요한 파일만 읽어 빠릅니다. 작업 순서는 Airflow가 관리합니다.

## 레이크하우스 2. 데이터 계보 영향 분석 (중)
<!--meta: sec=s2; dept=BE|DATA; level=신입|주니어|시니어; ct_band=중; related=PRJ-DWH-2-->
테이블끼리 어떤 테이블에서 만들어졌는지(데이터 계보)를 그래프로 기록합니다. 원본 테이블에 문제가 생기면 그 테이블에서 BFS로 따라 내려가 영향받는 하위 테이블과 대시보드를 모두 찾아 담당자에게 알립니다.

## 레이크하우스 3. 쏠린 키 조인 (상)
<!--meta: sec=s3; dept=BE|DATA; level=신입|주니어|시니어; ct_band=상; related=ISS-DWH-01-->

# 가디언 — 3급 프로젝트 문서
<!--meta: doc=PRJ-FDS-3; doc_type=project; tier=3; topic=FDS; disclosure=public; status=done; stages=1차|2차-->

## 가디언 1. 같은 사람의 여러 계정 묶기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-FDS-01-->
같은 기기나 같은 계좌를 쓰는 계정은 같은 사람일 가능성이 높습니다. 계정 쌍이 기기나 계좌를 공유할 때마다 Union-Find로 두 계정을 한 묶음으로 합치면, 한 사람이 여러 계정을 만들어 혜택을 반복해 받는 경우를 찾을 수 있습니다. 경로 압축으로 찾기를 빠르게 합니다.

## 가디언 2. 실시간 묶음 갱신 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-FDS-2-->
가입 이벤트가 실시간으로 들어올 때마다 Union-Find 묶음을 갱신하고, 한 묶음의 계정 수가 10개를 넘으면 검토 대상으로 올립니다. 묶음 크기는 합칠 때 함께 갱신해 매번 세지 않습니다. 공용 와이파이처럼 많은 사람이 함께 쓰는 값은 합치는 기준에서 뺍니다.

## 가디언 3. 묶음 다시 만들기 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-FDS-01-->
Union-Find 묶음은 합치기는 쉽지만 나누기는 어렵습니다. 공유 기준이 잘못이었다고 밝혀지면 묶음을 다시 계산해야 하는데, 전체를 매번 새로 만들면 몇 시간이 걸립니다. 그래서 최근 30일 관계만으로 매일 새 묶음을 만들고, 실시간으로는 그 위에 합치기만 하는 방식으로 나눴습니다.

## 가디언 4. 이상 거래 점수 모델 (중)
<!--meta: sec=s4; dept=AI; level=신입|주니어; ct_band=중; related=PRJ-FDS-2-->
규칙으로 잡기 어려운 이상 거래는 거래 금액, 시각, 기기 변화 같은 특징으로 학습한 모델이 점수를 매깁니다. 사기 사례가 전체의 0.1%라 정확도 대신 재현율과 정밀도로 평가합니다.

# 부킹온 — 3급 프로젝트 문서

## 부킹온 1. 겹치는 예약 찾기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-BKG-01-->
병원·미용실 예약에서 새 예약이 기존 예약과 겹치는지 확인해야 합니다. 그날 예약을 시작 시각 순으로 정렬해 두고 새 예약 구간과 비교하며 앞에서부터 훑으면 겹침을 찾을 수 있습니다. 두 사람의 빈 시간 목록을 투 포인터로 훑어 공통 빈 시간을 찾는 기능도 같은 방식입니다.

## 부킹온 2. 회의실 몰아 배정 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-BKG-2-->
회의실 예약 요청이 한꺼번에 들어오면 끝나는 시각이 빠른 요청부터 배정하는 그리디 방식으로 가능한 많은 요청을 받아 줍니다. 회의실이 여러 개면 시작 시각 순으로 보며 가장 먼저 비는 회의실에 넣습니다.

## 부킹온 3. 동시 예약 충돌 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-BKG-01-->
같은 시간대를 두 사람이 동시에 예약하면 둘 다 성공하는 문제가 있었습니다. 예약 행에 버전 번호를 두는 낙관적 락으로 늦게 쓴 쪽을 실패시키고, 충돌이 잦은 인기 시간대는 시간 슬롯을 미리 행으로 만들어 두고 비관적 락을 쓰는 방식과 비교했습니다. 반복 예약은 구간을 정렬한 뒤 투 포인터로 병합해 겹침 검사를 한 번에 합니다.

## 부킹온 4. 예약 화면 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-BKG-2-->
예약 화면은 사용자가 시간을 고르는 사이 다른 사람이 가져간 시간을 5초마다 확인해 회색으로 바꿉니다. 결제 단계로 넘어가면 10분 동안 그 시간을 임시로 잡아 둡니다.

# 노트허브 — 3급 프로젝트 문서
<!--meta: doc=PRJ-WIK-3; doc_type=project; tier=3; topic=WIK; disclosure=public; status=done; stages=1차|2차-->

## 노트허브 1. 두 버전 비교 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-WIK-01-->
문서의 두 버전 사이에 무엇이 바뀌었는지 보여 줄 때, 두 버전의 줄 목록에서 가장 긴 공통 부분(LCS)을 DP로 구하고 나머지를 추가·삭제로 표시합니다. 줄 수가 많으면 표 전체를 만들지 않고 바뀐 부분 근처만 계산합니다.

## 노트허브 2. 버전 기록 저장 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WIK-2-->
버전 기록이 쌓이면 저장 공간이 커져, 모든 버전을 통째로 저장하지 않고 이전 버전과의 차이만 저장합니다. 차이는 DP 기반 비교로 만들고, 50번째마다 전체본을 저장해 오래된 버전을 열 때 차이를 너무 많이 적용하지 않게 합니다.

## 노트허브 3. 동시 편집 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-WIK-01-->
여러 사람이 동시에 같은 문서를 고치면 충돌이 생깁니다. 노트허브는 항상 같은 결과로 합쳐지는 CRDT(Yjs)를 쓰고, 사람이 보는 비교 화면에서는 DP 기반 차이 계산으로 누가 무엇을 바꿨는지 보여 줍니다. CRDT는 지운 글자도 표시로 남겨 문서가 커지는데, 오래된 표시를 정리하는 시점을 정하는 것이 어렵습니다.

## 노트허브 4. 편집기 화면 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-WIK-2-->
편집기는 다른 사람의 커서 위치를 색깔로 보여 주고, 접속이 끊긴 동안 쓴 내용은 브라우저에 저장했다가 다시 연결되면 합칩니다.
