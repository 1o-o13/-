# 페이브릿지 — 3급 프로젝트 문서
<!--meta: doc=PRJ-PAY-3; doc_type=project; tier=3; topic=PAY; disclosure=public; status=done; stages=1차|2차-->

## 페이브릿지 1. 결제 요청 중복 막기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-PAY-01-->
결제 승인 요청은 네트워크 재시도 때문에 같은 요청이 두 번 들어올 수 있습니다. 페이브릿지는 쇼핑몰이 보내는 멱등 키(Idempotency-Key)를 해시 맵처럼 Redis에 저장해, 같은 키가 다시 오면 카드사로 보내지 않고 처음 결과를 그대로 돌려줍니다. 키는 24시간 뒤 만료되며, 아직 처리 중인 키로 같은 요청이 오면 409를 돌려줍니다.

## 페이브릿지 2. 카드사 응답 지연 감시 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
카드사별 응답 지연을 감시하기 위해 최근 5분 동안의 응답 시간을 슬라이딩 윈도우로 모아 p95를 계산합니다. p95가 기준을 넘는 카드사는 상태 화면에 '지연'으로 표시하고 승인 요청의 타임아웃을 3초에서 5초로 늘립니다. 윈도우는 1초 단위 버킷 300개로 나눠 오래된 버킷을 버리는 방식이라 요청마다 전체를 다시 계산하지 않습니다.

## 페이브릿지 3. 결제 원장 샤딩 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-01-->
결제 원장 테이블이 커지면서 가맹점 ID의 해시값으로 원장을 16개 샤드에 나눴습니다. 같은 가맹점의 거래는 한 샤드에 모이므로 가맹점 단위 조회는 빠르지만, 여러 가맹점을 묶는 조회는 모든 샤드를 읽어야 합니다. 샤드를 늘릴 때 옮겨야 하는 데이터를 줄이기 위해 일관된 해싱을 검토했고, 거래 ID에 샤드 번호를 넣어 어느 샤드에 있는지 바로 알 수 있게 했습니다.

## 페이브릿지 4. 결제창 화면 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-PAY-2-->
React와 TypeScript로 만든 결제창은 카드사 인증 화면을 새 창이 아니라 iframe으로 띄워 모바일에서 창 전환을 없앴습니다. 결제 버튼은 첫 클릭 뒤 바로 비활성화해 중복 제출을 막고, 결과 페이지는 서버가 확정한 상태만 보여 줍니다.

# 정산온 — 3급 프로젝트 문서
<!--meta: doc=PRJ-SET-3; doc_type=project; tier=3; topic=SET; disclosure=public; status=done; stages=1차|2차-->

## 정산온 1. 가맹점별 정산 집계 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-SET-01-->
하루치 거래 내역을 가맹점별로 묶어 정산 금액을 계산합니다. 거래를 가맹점 ID와 거래 시각 순으로 정렬한 뒤 앞에서부터 읽으며 가맹점이 바뀔 때마다 합계를 끊어 기록하므로, 전체를 메모리에 올리지 않고도 집계할 수 있습니다. 수수료는 원 단위 미만을 버리는 규칙을 씁니다.

## 정산온 2. 카드사 매입 파일 대사 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-SET-2-->
정산 결과와 카드사가 보내온 매입 파일을 맞춰 보는 대사 작업이 있습니다. 두 목록을 거래 번호 순으로 정렬해 두고 투 포인터로 함께 움직이며 비교하면, 한쪽에만 있는 거래와 금액이 다른 거래를 한 번 훑어서 찾을 수 있습니다. 차이가 난 거래는 담당자 검토 목록으로 보냅니다.

## 정산온 3. 거래 폭증일의 외부 정렬 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-SET-01-->
연말처럼 거래가 평소의 열 배로 늘면 하루치 거래가 메모리에 들어가지 않습니다. 이때는 거래를 나눠 정렬한 조각 파일을 S3에 쓰고, 조각들을 다시 합치는 외부 정렬로 처리합니다. Spring Batch의 파티셔닝으로 가맹점 구간마다 작업을 나눠 병렬로 돌리되, 같은 가맹점이 두 파티션에 걸치지 않게 경계를 잡습니다.

## 정산온 4. 정산 결과 적재 (중)
<!--meta: sec=s4; dept=DATA; level=신입|주니어; ct_band=중; related=PRJ-SET-2-->
정산 결과는 매일 아침 데이터 웨어하우스로 복사되어 재무팀 대시보드에 쓰입니다. Airflow 작업이 정산 완료 신호를 기다렸다가 적재하며, 전날과 비교해 가맹점 수나 총액이 30% 넘게 변하면 적재를 멈추고 알림을 보냅니다.

# 톡허브 — 3급 프로젝트 문서
<!--meta: doc=PRJ-CHT-3; doc_type=project; tier=3; topic=CHT; disclosure=public; status=done; stages=1차|2차-->

## 톡허브 1. 방별 연결 관리 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-CHT-01-->
채팅 서버는 사용자가 접속하면 WebSocket 연결을 열어 둡니다. 서버마다 방 ID를 키로, 그 방에 접속한 연결 목록을 값으로 하는 해시 맵을 두고, 메시지가 오면 해당 방의 연결에만 보냅니다. 연결이 끊기면 맵에서 지우고, 30초 안에 다시 붙으면 놓친 메시지를 이어서 받습니다.

## 톡허브 2. 메시지 순서 맞추기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-2-->
서버가 여러 대라 같은 방 메시지가 서로 다른 서버를 거쳐 늦게 도착할 수 있습니다. 메시지마다 방 단위로 증가하는 순번을 붙이고, 클라이언트는 순번으로 정렬해 표시하며 빠진 순번이 있으면 서버에 다시 요청합니다. 기기 시각은 기기마다 달라 순서 기준으로 쓰지 않습니다.

## 톡허브 3. 방을 서버에 나누기 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-01-->
동시 접속이 50만을 넘자 방을 서버에 고르게 나눌 방법이 필요해졌습니다. 방 ID를 일관된 해싱으로 서버에 배정하면 서버를 한 대 늘려도 일부 방만 옮겨 가므로 재접속 폭주를 줄일 수 있습니다. 인기 방이 한 서버에 몰리는 쏠림은 가상 노드 수를 늘리고, 아주 큰 방은 여러 서버가 나눠 맡도록 따로 처리합니다.

## 톡허브 4. 채팅 화면 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-CHT-2-->
웹과 앱 화면은 새 메시지가 오면 목록 끝으로 자동 스크롤하되, 사용자가 위로 올려 과거 메시지를 보는 중이면 '새 메시지' 버튼만 띄웁니다. 수천 개 메시지가 쌓인 방은 화면에 보이는 부분만 그리는 가상 스크롤로 메모리를 줄였습니다.

# 알림센터 — 3급 프로젝트 문서
<!--meta: doc=PRJ-NTF-3; doc_type=project; tier=3; topic=NTF; disclosure=public; status=done; stages=1차|2차-->

## 알림센터 1. 긴급 알림 먼저 보내기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-NTF-01-->
알림센터는 푸시, 메일, 문자 요청을 받아 발송합니다. 비밀번호 재설정 같은 긴급 알림이 마케팅 알림 뒤에 밀리지 않도록, 발송 작업자는 우선순위 큐에서 등급이 높은 요청부터 꺼냅니다. 같은 등급 안에서는 먼저 들어온 순서를 지킵니다.

## 알림센터 2. 중복 발송 막기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-NTF-2-->
발송 요청이 재시도되면 사용자가 같은 알림을 두 번 받을 수 있습니다. 요청마다 '사용자 ID + 알림 종류 + 원인 이벤트 ID'의 해시를 만들어 24시간 동안 기록하고, 같은 해시가 다시 오면 버립니다. 기록은 Redis에 두되 만료 시간을 꼭 붙여 메모리가 끝없이 늘지 않게 합니다.

## 알림센터 3. 예약 알림 타이머 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-NTF-01-->
'내일 오전 9시에 보내기' 같은 예약 알림이 하루 수백만 건입니다. 발송 시각을 키로 하는 우선순위 큐에 넣고 가장 이른 것부터 꺼내지만, 한 서버의 메모리에 다 들어가지 않아 시각 구간별로 버킷을 나눈 타이밍 휠 구조로 바꿨습니다. 서버가 죽어도 예약이 사라지지 않게 버킷은 DB에도 기록하고, 다시 켜지면 지난 버킷부터 처리합니다.

## 알림센터 4. 앱 알림 화면 이동 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-NTF-2-->
앱은 알림을 받으면 종류에 따라 다른 화면으로 이동해야 합니다. 알림에 화면 경로(딥링크)를 함께 넣고, 앱이 꺼져 있다가 알림으로 켜진 경우에도 로그인 확인 뒤 해당 화면으로 보내도록 처리합니다.

# 파인드 — 3급 프로젝트 문서
<!--meta: doc=PRJ-SRC-3; doc_type=project; tier=3; topic=SRC; disclosure=public; status=done; stages=1차|2차-->

## 파인드 1. 검색 결과 정렬 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-SRC-01-->
상품 검색은 검색어와 상품명·설명이 얼마나 맞는지를 BM25 점수로 계산하고 점수순으로 정렬해 보여 줍니다. 점수가 같으면 최근 판매량이 많은 상품을 먼저 보여 주고 품절 상품은 맨 뒤로 보냅니다. 한국어는 nori 형태소 분석기로 '운동화를'을 '운동화'로 잘라 색인합니다.

## 파인드 2. 상위 결과만 고르기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->
검색 결과 첫 페이지에는 상위 20개만 필요합니다. 수만 개 후보를 모두 정렬하지 않고 크기 20의 우선순위 큐(최소 힙)를 유지하면서 더 높은 점수가 나올 때만 바꿔 넣으면 계산량을 크게 줄일 수 있습니다. 검색 엔진 내부도 이 방식으로 상위 결과를 고릅니다.

## 파인드 3. 샤드 결과 병합 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-SRC-01-->
상품 색인이 8개 샤드에 나뉘어 있어, 각 샤드가 자기 상위 결과를 보내면 조정 노드가 이를 합칩니다. 샤드별 결과는 이미 점수순이므로 우선순위 큐로 k개 목록을 병합합니다. 다만 샤드마다 단어 빈도가 달라 같은 상품도 샤드에 따라 점수가 달라지는 문제가 있어, 전역 단어 통계를 쓰는 옵션과 비용을 비교했습니다.

## 파인드 4. 검색어 자동 완성 (중)
<!--meta: sec=s4; dept=AI|FE; level=신입|주니어; ct_band=중; related=PRJ-SRC-2-->
검색어 자동 완성은 사용자가 입력한 앞부분으로 인기 검색어를 추천합니다. 오타가 있는 검색어는 자모 단위 편집 거리로 가까운 검색어를 찾아 '이것을 찾으셨나요'로 제안합니다.

# 픽미 — 3급 프로젝트 문서
<!--meta: doc=PRJ-REC-3; doc_type=project; tier=3; topic=REC; disclosure=public; status=done; stages=1차|2차-->

## 픽미 1. 이미 산 상품 빼기 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-REC-01-->
추천 목록을 만들 때 사용자가 이미 산 상품과 방금 본 상품은 빼야 합니다. 사용자별 제외 상품 ID를 해시 집합으로 들고 있으면 후보마다 바로 제외 여부를 확인할 수 있습니다. 집합은 최근 90일 구매 기록으로 매일 새로 만듭니다.

## 픽미 2. 추천 상위 N개 고르기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-REC-2-->
협업 필터링 모델이 사용자와 상품을 벡터로 바꿔 두면, 추천은 내적 점수가 높은 상품 N개를 고르는 문제가 됩니다. 후보 수천 개의 점수를 계산하며 크기 N의 우선순위 큐로 상위만 남기고, 결과는 30분 동안 캐시합니다.

## 픽미 3. 비슷한 상품만 나오지 않게 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-REC-01-->
점수만 보고 고르면 비슷한 상품이 줄줄이 추천됩니다. 이미 고른 상품과 너무 비슷한 상품은 점수를 깎아 가며 하나씩 고르는 그리디 재정렬(MMR)로 다양성을 높였습니다. 다양성 가중치는 A/B 시험으로 정했고, 너무 높이면 클릭률이 떨어졌습니다.

## 픽미 4. 학습과 서비스의 같은 특징 (중)
<!--meta: sec=s4; dept=AI|DATA; level=신입|주니어; ct_band=중; related=PRJ-REC-2-->
모델 학습에 쓰는 사용자 특징(최근 본 카테고리, 평균 구매 금액)은 피처 스토어에 모아 학습과 서비스에서 같은 값을 쓰게 합니다. 학습 때와 서비스 때 특징 계산이 달라지는 문제를 막기 위해 계산 코드를 한 곳에 둡니다.

## 로지패스 1. 최단 이동 시간 계산 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-LGS-01-->
배송 기사의 다음 목적지까지 걸리는 시간을 계산할 때 도로망을 그래프로 봅니다. 교차로를 정점, 도로를 간선, 이동 시간을 가중치로 두고 다익스트라 알고리즘으로 최단 시간을 구합니다. 이동 시간이 음수가 될 일이 없어 다익스트라를 그대로 쓸 수 있습니다.

## 로지패스 2. 교통 상황 반영 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-LGS-2-->
출퇴근 시간에는 도로별 이동 시간이 계속 바뀝니다. 5분마다 들어오는 교통 정보로 간선 가중치를 갱신하고, 기사 앱이 경로를 요청할 때 다익스트라를 다시 돌립니다. 요청이 몰리면 계산이 밀려, 자주 묻는 출발·도착 구역 쌍의 결과를 5분 동안 캐시합니다.

## 로지패스 3. 여러 배송지 순서 정하기 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-LGS-01-->
기사 한 명이 30곳을 들르는 순서를 정하는 문제는 외판원 문제라 정확한 답을 구하기 어렵습니다. 모든 배송지 쌍의 이동 시간을 다익스트라로 미리 구해 표를 만들고, OR-Tools의 근사 탐색으로 순서를 정합니다. 배송 시간 약속이 있는 주문은 제약 조건으로 넣습니다.

## 로지패스 4. 기사 앱 지도 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-LGS-2-->
기사 앱은 지도 위에 배송지와 경로를 그립니다. 배송지가 수백 개인 날은 가까운 점을 묶어 하나로 보여 주고 확대하면 풀어 보여 주는 군집 표시로 화면이 멈추지 않게 했습니다.

# 스톡키퍼 — 3급 프로젝트 문서
<!--meta: doc=PRJ-INV-3; doc_type=project; tier=3; topic=INV; disclosure=public; status=done; stages=1차|2차-->

## 스톡키퍼 1. 재고 조회 캐시 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-INV-01-->
창고별 상품 재고를 조회할 때 '창고 ID:상품 ID'를 키로 하는 해시 구조의 캐시에서 먼저 찾고, 없으면 DB를 읽습니다. 재고가 바뀌면 캐시를 지우고 다음 조회 때 새로 채우는 방식이라 캐시와 DB가 잠깐 다를 수 있어, 화면에 '약 1분 전 기준'으로 표시합니다.

## 스톡키퍼 2. 여러 상품 차감과 교착 상태 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-INV-2-->
주문 하나에 여러 상품이 있으면 상품마다 재고 행을 잠그고 차감합니다. 두 주문이 서로 다른 순서로 잠그면 교착 상태가 생기므로, 잠그기 전에 상품 ID를 정렬해 항상 같은 순서로 잠급니다. 잠금 대기가 2초를 넘으면 주문을 실패시키고 다시 시도하게 합니다.

## 스톡키퍼 3. 한정 판매 재고 차감 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-INV-01-->
인기 상품 한정 판매처럼 같은 재고 행에 초당 수천 건의 차감이 몰리면 DB 잠금이 병목이 됩니다. 재고를 Redis에서 원자적 감소 명령으로 먼저 차감하고, 결과를 Kafka로 보내 DB에 순서대로 반영하는 구조로 바꿨습니다. Redis와 DB가 어긋나면 DB를 기준으로 맞추는 대사 작업이 10분마다 돕니다.

## 스톡키퍼 4. 재고 변경 수집 (중)
<!--meta: sec=s4; dept=DATA; level=신입|주니어; ct_band=중; related=PRJ-INV-2-->
재고 변경은 Debezium으로 DB 변경 로그를 읽어 Kafka로 내보내고(CDC), 분석팀은 이를 받아 상품별 품절 시간을 집계합니다. 애플리케이션 코드를 고치지 않고도 모든 변경을 빠짐없이 받을 수 있어 CDC를 골랐습니다.

# 원패스 — 3급 프로젝트 문서
<!--meta: doc=PRJ-AUT-3; doc_type=project; tier=3; topic=AUT; disclosure=public; status=done; stages=1차|2차-->

## 원패스 1. 로그인 실패 횟수 제한 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-AUT-01-->
비밀번호 대입 공격을 막기 위해 같은 계정의 최근 10분 동안 로그인 실패 횟수를 슬라이딩 윈도우로 셉니다. 5번을 넘으면 그 계정은 10분 동안 추가 인증(문자 코드)을 요구합니다. 고정 구간으로 세면 구간 경계에서 두 배까지 시도할 수 있어 슬라이딩 윈도우를 골랐습니다.

## 원패스 2. 로그아웃된 토큰 막기 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-AUT-2-->
로그인하면 접근 토큰(JWT)과 갱신 토큰을 줍니다. JWT는 서버가 따로 기록하지 않아도 검증되지만 로그아웃해도 만료 전까지 쓸 수 있어, 로그아웃된 토큰 ID를 만료 시각까지 해시 집합(Redis)에 넣어 막습니다. 접근 토큰 유효 시간은 15분으로 짧게 둡니다.

## 원패스 3. 갱신 토큰 회전 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-AUT-01-->
갱신 토큰이 탈취되는 경우에 대비해, 갱신할 때마다 새 갱신 토큰을 주고 이전 것은 폐기하는 회전 방식을 씁니다. 토큰은 원문 대신 해시값만 저장하며, 이미 폐기된 토큰으로 갱신 요청이 오면 탈취로 보고 그 사용자의 모든 토큰을 끊습니다. 여러 탭에서 동시에 갱신할 때 정상 사용자가 끊기지 않게 짧은 유예 시간을 둡니다.

## 원패스 4. 로그인 화면 보안 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-AUT-2-->
로그인 화면은 OAuth 인가 코드 흐름에 PKCE를 붙여 브라우저에서 비밀값 없이도 코드 가로채기를 막습니다. 토큰은 자바스크립트가 읽을 수 없는 HttpOnly 쿠키에 두고, 다른 사이트에서 오는 요청은 SameSite 설정으로 막습니다.

# 게이트키퍼 — 3급 프로젝트 문서
<!--meta: doc=PRJ-GWY-3; doc_type=project; tier=3; topic=GWY; disclosure=public; status=done; stages=1차|2차-->

## 게이트키퍼 1. 고객사별 요청 수 제한 (하)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-GWY-01-->
API 게이트웨이는 고객사별로 분당 요청 수를 제한합니다. 최근 60초 동안의 요청을 슬라이딩 윈도우로 세고, 한도를 넘으면 429 응답과 함께 다시 시도할 시각을 알려 줍니다. 요청이 많은 고객사는 요청 시각을 모두 기록하는 대신 1초 단위 카운터 60개로 근사합니다.

## 게이트키퍼 2. 같은 사용자는 같은 서버로 (중)
<!--meta: sec=s2; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-GWY-2-->
게이트웨이 뒤의 서버가 여러 대일 때 같은 사용자의 요청을 같은 서버로 보내면 서버 캐시를 잘 쓸 수 있습니다. 사용자 ID의 일관된 해싱으로 서버를 고르고, 서버가 빠지면 그 서버 몫만 다른 서버로 옮겨 갑니다.

## 게이트키퍼 3. 여러 게이트웨이의 한도 공유 (상)
<!--meta: sec=s3; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-GWY-01-->
게이트웨이가 10대로 늘자 각 서버가 따로 세면 고객사 한도가 열 배로 늘어나는 문제가 생겼습니다. 카운터를 Redis에 모아 원자적으로 증가시키는 분산 슬라이딩 윈도우로 바꾸되, Redis 왕복이 지연을 늘리지 않도록 서버마다 몫을 미리 나눠 받아 쓰는 방식과 비교했습니다.

## 게이트키퍼 4. 개발자 포털 (중)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=중; related=PRJ-GWY-2-->
고객사 개발자가 쓰는 API 포털은 OpenAPI 문서로 화면을 자동 생성하고, 브라우저에서 바로 요청을 보내 볼 수 있게 했습니다.
