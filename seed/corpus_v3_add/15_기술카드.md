## CARD-BE-01 Redis 정렬된 집합 대기열
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=TKT; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-TKT-3-->
- 키워드: 정렬된 집합, Sorted Set, ZSET, 대기열, waiting queue, ZADD, ZRANK, ZPOPMIN, 순번 대기
- 시스템에서 맡는 역할: 접속 시각을 점수로 넣어 순번을 매긴다. 앞에서부터 일정 인원씩 꺼내 예매 화면으로 들여보낸다.
- 대안: Redis 리스트, Kafka 토픽, DB 테이블 기반 대기열.
- 트레이드오프: 순번 조회가 빠르지만 메모리에 모두 올라간다. 장애 시 순번 유실을 막으려면 복제와 영속화 설정이 필요하다.
- 자주 하는 오해: "리스트로도 똑같다"고 믿는다. 리스트는 중간 위치 조회가 느려서 내 순번을 자주 묻는 화면에 맞지 않다.
- 파고들 지점: 같은 시각 점수 충돌 처리, 이탈자 정리 방법, 키 하나에 몰리는 부하 분산.
- 좋은 답변의 신호: ZRANK가 로그 시간이라는 점과 입장 속도를 서버가 조절한다는 점을 함께 말한다.
- 새벽소프트 사례: 줄서기는 오픈 순간 수십만 명을 정렬된 집합 대기열로 받는다.
- 기준 버전: 해당 없음

## CARD-BE-02 분산 락과 좌석 선점(SET NX + 만료)
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=TKT; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-TKT-3-->
- 키워드: 분산 락, distributed lock, SET NX, SET NX PX, 만료 시간, TTL, 좌석 선점, 임시 점유, Redlock
- 시스템에서 맡는 역할: 한 좌석을 한 사람만 잠시 잡게 한다. 결제가 끝나지 않으면 만료로 자동 해제된다.
- 대안: DB 행 잠금(SELECT FOR UPDATE), 낙관적 잠금(버전 열), ZooKeeper 같은 합의 기반 락.
- 트레이드오프: 빠르지만 Redis 장애나 시계 문제에서 락이 완벽하지 않다. 최종 확정은 DB 제약으로 한 번 더 막아야 한다.
- 자주 하는 오해: "SET NX 뒤에 EXPIRE를 따로 걸어도 된다"고 믿는다. 두 명령 사이에 서버가 죽으면 만료 없는 락이 남는다.
- 파고들 지점: 해제 시 내 락인지 값 비교, 만료 전 작업 지연, 최종 확정 단계의 이중 방어.
- 좋은 답변의 신호: 한 명령으로 원자적으로 걸고, 해제는 소유 값을 확인한 뒤 지운다고 말한다.
- 새벽소프트 사례: 줄서기는 좌석을 SET NX로 선점하고 7분 뒤 자동으로 풀어 준다.
- 기준 버전: 해당 없음

## CARD-BE-03 캐시 무효화(cache-aside)
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=TKT; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-TKT-3-->
- 키워드: 캐시 무효화, cache invalidation, cache-aside, 지연 로딩, lazy loading, TTL, 캐시 스탬피드, cache stampede
- 시스템에서 맡는 역할: 읽을 때 캐시를 먼저 보고, 없으면 DB에서 읽어 채운다. 자주 읽는 공연 정보의 DB 부하를 줄인다.
- 대안: write-through, write-behind, 짧은 TTL만 두는 방식.
- 트레이드오프: 구현이 단순하지만 잠깐 오래된 값이 보일 수 있다. 인기 키가 만료되면 요청이 한꺼번에 DB로 몰린다.
- 자주 하는 오해: "쓰기 때 캐시 값을 새 값으로 바꾸면 안전하다"고 믿는다. 동시 쓰기 순서가 꼬이면 옛 값이 남아 삭제가 더 안전하다.
- 파고들 지점: 수정 후 삭제 순서, 만료 순간 몰림 대응, 잔여 좌석처럼 캐시하면 안 되는 값.
- 좋은 답변의 신호: 캐시할 값과 하지 않을 값을 정확도 요구로 구분한다.
- 새벽소프트 사례: 줄서기는 공연 소개는 캐시하고, 잔여 좌석 수는 짧게만 둔다.
- 기준 버전: 해당 없음

## CARD-BE-04 Kafka 파티션 순서와 중복 소비
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=TKT; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-TKT-3-->
- 키워드: 카프카, Kafka, 파티션, partition, 메시지 순서, ordering, 중복 소비, at-least-once, 컨슈머 그룹, 오프셋 커밋
- 시스템에서 맡는 역할: 예매·결제 이벤트를 다른 서비스로 전달한다. 같은 주문 키는 같은 파티션에 넣어 순서를 지킨다.
- 대안: RabbitMQ 같은 메시지 브로커, DB 아웃박스 테이블 폴링.
- 트레이드오프: 처리량이 크지만 순서는 파티션 안에서만 지켜진다. 파티션 수를 늘리면 키 배치가 바뀐다.
- 자주 하는 오해: "토픽 전체 순서가 보장된다"고 믿는다. 파티션이 여러 개면 파티션 사이 순서는 없다.
- 파고들 지점: 오프셋 커밋 시점, 재배치 중 중복 처리, 소비자 쪽 멱등 처리.
- 좋은 답변의 신호: 최소 한 번 전달을 전제로 소비자가 중복을 견디게 만든다고 말한다.
- 새벽소프트 사례: 줄서기는 결제 완료 이벤트를 주문 번호 키로 Kafka에 보낸다.
- 기준 버전: 해당 없음

## CARD-BE-05 결제 멱등 키
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=TKT; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-TKT-3-->
- 키워드: 멱등 키, idempotency key, 멱등성, idempotent, 중복 결제, 재시도, Idempotency-Key 헤더
- 시스템에서 맡는 역할: 같은 결제 요청이 여러 번 와도 한 번만 처리한다. 두 번째부터는 처음 결과를 그대로 돌려준다.
- 대안: 주문 번호 고유 제약, 결제 상태 머신으로 중복 전이 차단.
- 트레이드오프: 키와 결과를 저장할 공간과 보관 기간 정책이 필요하다. 키 생성 주체를 잘못 정하면 효과가 없다.
- 자주 하는 오해: "버튼을 비활성화하면 서버 멱등은 필요 없다"고 믿는다. 네트워크 재시도와 타임아웃 뒤 재요청은 화면에서 막을 수 없다.
- 파고들 지점: 처리 중 상태에서 같은 키 요청, 키 보관 기간, 요청 본문이 다를 때 처리.
- 좋은 답변의 신호: 키 저장과 결제 처리를 같은 흐름에서 원자적으로 묶는다고 설명한다.
- 새벽소프트 사례: 줄서기는 결제 요청마다 멱등 키를 받아 중복 결제를 막는다.
- 기준 버전: 해당 없음

## CARD-BE-06 트랜잭션 격리 수준
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=COMMON; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public-->
- 키워드: 격리 수준, isolation level, Read Committed, Repeatable Read, Serializable, 팬텀 읽기, phantom read, 쓰기 왜곡, write skew, MVCC
- 시스템에서 맡는 역할: 동시에 도는 트랜잭션이 서로의 중간 결과를 얼마나 보는지 정한다. PostgreSQL은 MVCC(다중 버전 동시성 제어)로 트랜잭션마다 데이터 스냅샷을 보여 줘, 읽기와 쓰기가 서로 막지 않는다.
- 대안: 높은 격리 수준 대신 행 잠금, 고유 제약, 낙관적 잠금으로 필요한 곳만 막는다.
- 트레이드오프: 격리가 높을수록 이상 현상은 줄지만 대기나 직렬화 실패가 늘어난다.
- 자주 하는 오해: "Repeatable Read면 모든 동시성 문제가 사라진다"고 믿는다. PostgreSQL에서도 쓰기 왜곡은 Serializable에서만 막힌다.
- 파고들 지점: PostgreSQL 기본값(Read Committed), 직렬화 실패 시 재시도, 이상 현상 예시 설명.
- 좋은 답변의 신호: 실제 사례 하나로 어떤 이상이 생기고 어느 수준에서 막히는지 말한다.
- 새벽소프트 사례: 루미스캔과 줄서기는 PostgreSQL을 쓰며 기본 격리 수준(Read Committed)에서 시작한다.
- 기준 버전: 해당 없음

## CARD-BE-07 인덱스 설계와 실행 계획

- 키워드: 인덱스, index, 복합 인덱스, composite index, B-tree, 실행 계획, EXPLAIN, EXPLAIN ANALYZE, 풀 스캔, seq scan
- 시스템에서 맡는 역할: 자주 쓰는 조회 조건과 정렬을 빠르게 한다. 실행 계획으로 인덱스를 실제로 타는지 확인한다.
- 대안: 부분 인덱스, 커버링 인덱스, 조회용 요약 테이블.
- 트레이드오프: 읽기는 빨라지지만 쓰기마다 인덱스도 갱신된다. 저장 공간도 늘어난다.
- 자주 하는 오해: "인덱스는 많을수록 좋다"고 믿는다. 쓰기가 느려지고, 플래너가 안 쓰는 인덱스도 생긴다.
- 파고들 지점: 복합 인덱스 열 순서, 선택도가 낮은 열, 예상 행 수와 실제 행 수 차이.
- 좋은 답변의 신호: EXPLAIN ANALYZE 결과를 보고 판단했다는 경험을 말한다.
- 새벽소프트 사례: 루미스캔은 병원별·상태별 판독 요청 목록을 최신순으로 자주 조회한다.
- 기준 버전: 해당 없음

## CARD-BE-08 작업 대기열 재시도와 데드레터

- 키워드: 작업 대기열, job queue, task queue, 재시도, retry, 지수 백오프, exponential backoff, 데드레터 큐, DLQ, dead letter
- 시스템에서 맡는 역할: 오래 걸리는 추론 작업을 요청과 분리해 뒤에서 처리한다. 계속 실패하는 작업은 데드레터로 옮긴다.
- 대안: 동기 처리, 스케줄러가 DB 상태를 주기적으로 훑는 방식.
- 트레이드오프: 응답은 빨라지지만 결과를 따로 알려야 한다. 재시도가 겹치면 같은 작업이 두 번 돌 수 있다.
- 자주 하는 오해: "실패하면 무한 재시도가 안전하다"고 믿는다. 고칠 수 없는 입력은 계속 실패해 대기열을 막는다.
- 파고들 지점: 일시 오류와 영구 오류 구분, 재시도 간격, 데드레터 작업을 누가 언제 보는지.
- 좋은 답변의 신호: 재시도 횟수 상한과 작업의 멱등성을 함께 설계한다.
- 새벽소프트 사례: 루미스캔은 영상 업로드 뒤 추론을 작업 대기열로 넘긴다.
- 기준 버전: 해당 없음

## CARD-BE-09 커넥션 풀
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=COMMON; dept=BE; level=신입|주니어|시니어; ct_band=하; disclosure=public-->
- 키워드: 커넥션 풀, connection pool, DB 연결, HikariCP, SQLAlchemy pool, 풀 크기, pool size, 연결 대기, pgbouncer
- 시스템에서 맡는 역할: DB 연결을 미리 만들어 두고 빌려 쓴다. 요청마다 연결을 새로 여는 비용을 없앤다.
- 대안: 앞단 연결 프록시(pgbouncer), 서버리스용 데이터 API.
- 트레이드오프: 풀이 작으면 요청이 줄을 서고, 크면 DB가 연결 처리에 자원을 쓴다. 서버 대수만큼 연결 수가 곱해진다.
- 자주 하는 오해: "풀 크기를 키우면 처리량이 늘어난다"고 믿는다. 활성 연결이 DB 코어 수의 작은 배수(대략 2~3배)를 넘으면 경합이 늘어 오히려 느려질 수 있다.
- 파고들 지점: 긴 트랜잭션의 연결 점유, 연결 대기 시간 지표, 서버 증설 시 총 연결 수.
- 좋은 답변의 신호: 서버 수와 DB 최대 연결 수를 함께 계산해 풀 크기를 정한다.
- 새벽소프트 사례: 줄서기는 Spring Boot, 루미스캔은 FastAPI에서 각자 풀을 둔다.
- 기준 버전: 해당 없음

## CARD-BE-10 서킷 브레이커와 타임아웃
<!--meta: doc=CRT-CARD-BE; doc_type=criteria; tier=0; topic=MED; dept=BE; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-MED-3-->
- 키워드: 서킷 브레이커, circuit breaker, 타임아웃, timeout, half-open, 장애 전파, cascading failure, Resilience4j, 재시도 폭주
- 시스템에서 맡는 역할: 외부 시스템이 느리거나 죽었을 때 호출을 잠시 끊는다. 타임아웃으로 스레드와 연결이 묶이는 것을 막는다.
- 대안: 벌크헤드로 자원 분리, 큐에 넣고 나중에 처리.
- 트레이드오프: 장애 전파는 막지만 차단 중에는 기능 일부를 포기한다. 기준값을 잘못 잡으면 정상 상황에서도 열린다.
- 자주 하는 오해: "재시도를 늘리면 안정성이 오른다"고 믿는다. 이미 느린 상대에게 요청을 몰아 장애를 키운다.
- 파고들 지점: 닫힘·열림·반열림 전이 조건, 타임아웃 값의 근거, 차단 중 사용자 안내.
- 좋은 답변의 신호: 타임아웃을 상대 응답 시간 분포로 정하고 대체 동작을 말한다.
- 새벽소프트 사례: 루미스캔은 병원 PACS 연동 호출에 타임아웃과 차단 기준을 둔다.
- 기준 버전: 해당 없음

<!--meta: doc=CRT-CARD-AI; doc_type=criteria; tier=0; topic=MED; dept=AI; level=신입|주니어|시니어; ct_band=하; disclosure=public; related=PRJ-MED-3-->
- 키워드: 클래스 불균형, class imbalance, 불균형 데이터, imbalanced data, 가중 손실, weighted loss, focal loss, 오버샘플링, oversampling, 언더샘플링
- 시스템에서 맡는 역할: 드문 소견도 놓치지 않게 학습 데이터와 손실을 조정한다.
- 대안: 클래스 가중치, 초점 손실, 재샘플링, 판정 기준값 조정.
- 트레이드오프: 드문 클래스를 키우면 거짓 양성이 늘 수 있다. 오버샘플링은 같은 영상에 과적합할 위험이 있다.
- 자주 하는 오해: "정확도가 95%면 좋은 모델이다"라고 믿는다. 양성이 5%면 전부 음성이라 해도 95%가 나온다.
- 파고들 지점: 클래스별 지표 확인, 재샘플링과 증강의 순서, 평가 세트는 원래 분포 유지.
- 좋은 답변의 신호: 평가 세트 비율은 건드리지 않고 학습 쪽만 조정한다고 말한다.
- 새벽소프트 사례: 루미스캔의 5종 소견 중 기흉은 다른 소견보다 영상 수가 적다.
- 기준 버전: 해당 없음

## CARD-AI-02 민감도·특이도·AUROC
<!--meta: doc=CRT-CARD-AI; doc_type=criteria; tier=0; topic=MED; dept=AI; level=신입|주니어|시니어; ct_band=하; disclosure=public; related=PRJ-MED-3-->
- 키워드: 민감도, sensitivity, 재현율, recall, 특이도, specificity, AUROC, ROC 곡선, AUC, 양성 예측도, PPV, precision
- 시스템에서 맡는 역할: 모델이 이상을 얼마나 잡고, 정상을 얼마나 정상으로 두는지 잰다.
- 대안: 정밀도-재현율 곡선(AUPRC), F1 점수, 특정 민감도에서의 특이도.
- 트레이드오프: 기준값을 낮추면 민감도는 오르고 특이도는 떨어진다. AUROC는 기준값 하나를 고르지 않는다.
- 자주 하는 오해: "AUROC가 높으면 실제 운영에서도 좋다"고 믿는다. 운영 기준값의 성능과 유병률에 따른 양성 예측도는 따로 봐야 한다.
- 파고들 지점: 유병률이 낮을 때 PPV, 기준값 선택 근거, 신뢰 구간.
- 좋은 답변의 신호: 놓침과 과잉 알림 중 무엇이 더 비싼지로 기준값을 정한다.
- 새벽소프트 사례: 루미스캔은 보조 도구라서 놓침을 줄이는 쪽 민감도를 먼저 본다.
- 기준 버전: 해당 없음

## CARD-AI-03 데이터 분할과 누수(환자 단위 분할)
<!--meta: doc=CRT-CARD-AI; doc_type=criteria; tier=0; topic=MED; dept=AI; level=신입|주니어|시니어; ct_band=하; disclosure=public; related=PRJ-MED-3-->
- 키워드: 데이터 누수, data leakage, 환자 단위 분할, patient-level split, group split, GroupKFold, 학습/검증/평가 분할, train/val/test
- 시스템에서 맡는 역할: 평가 점수가 실제 새 환자에서의 성능을 반영하게 한다.
- 대안: 기관 단위 분할, 시간 순 분할, 외부 기관 검증 세트.
- 트레이드오프: 환자나 기관 단위로 나누면 세트 크기와 클래스 비율이 고르지 않을 수 있다.
- 자주 하는 오해: "영상 단위로 무작위 분할하면 된다"고 믿는다. 같은 환자의 영상이 양쪽에 들어가 점수가 부풀려진다.
- 파고들 지점: 정규화 통계 계산 시점, 같은 환자 재촬영, 평가 세트를 몇 번 봤는지.
- 좋은 답변의 신호: 분할 키를 먼저 정하고 전처리 통계는 학습 세트로만 낸다.
- 새벽소프트 사례: 루미스캔은 한 환자가 여러 번 찍은 흉부 X-ray를 한 세트에만 둔다.
- 기준 버전: 해당 없음

- 키워드: 도메인 이동, domain shift, 분포 이동, distribution shift, 데이터셋 이동, 장비 차이, scanner variation, 외부 검증, external validation, 도메인 적응
- 시스템에서 맡는 역할: 다른 병원, 다른 장비의 영상에서도 성능이 유지되는지 확인하고 대응한다.
- 대안: 다기관 학습 데이터, 강도·대비 증강, 정규화 통일, 도메인 적응, 기관별 미세 조정.

- 자주 하는 오해: "내부 평가 점수가 높으면 다른 병원에서도 같다"고 믿는다. 장비, 촬영 자세, 환자군이 달라 점수가 떨어질 수 있다.

- 새벽소프트 사례: 루미스캔은 새 병원 도입 전 그 병원 영상으로 따로 검증한다.

## CARD-AI-05 모델 양자화·변환 시 판정 변화

- 키워드: 양자화, quantization, INT8, FP16, 학습 후 양자화, PTQ, 양자화 인식 학습, QAT, ONNX, TensorRT, 모델 변환
- 시스템에서 맡는 역할: 모델을 가볍게 바꿔 작은 장치나 서버에서 빠르게 돌린다.
- 대안: 지식 증류로 작은 모델 학습, 가지치기, 원래 정밀도 유지.
- 트레이드오프: 속도와 메모리는 좋아지지만 출력 값이 조금 바뀐다. 보정용 데이터가 부족하면 손실이 커진다.
- 자주 하는 오해: "평균 정확도가 같으면 판정도 같다"고 믿는다. 기준값 근처 샘플은 작은 차이로 판정이 뒤집힌다.
- 파고들 지점: 변환 전후 판정 일치율, 지원 안 되는 연산자 처리, 장치에서 실측한 지연.
- 좋은 답변의 신호: 평균 지표와 함께 샘플별로 뒤집힌 판정 수를 비교한다.
- 새벽소프트 사례: 스카이패스는 드론 장애물 인식 모델을 기체에서 돌리기 위해 경량화한다.

## CARD-AI-06 확률 보정과 판정 기준값
<!--meta: doc=CRT-CARD-AI; doc_type=criteria; tier=0; topic=MED; dept=AI; level=주니어|시니어; ct_band=중; disclosure=public; related=PRJ-MED-3-->
- 키워드: 확률 보정, calibration, 온도 스케일링, temperature scaling, 신뢰도 다이어그램, reliability diagram, ECE, 판정 기준값, threshold, 컷오프
- 시스템에서 맡는 역할: 모델 점수를 실제 확률에 가깝게 맞추고, 판정을 나누는 기준값을 정한다.
- 대안: 플랫 스케일링, 등위 회귀, 소견별 기준값 따로 두기.
- 트레이드오프: 온도·플랫 스케일링처럼 엄격히 단조 증가하는 변환을 소견별 시그모이드 출력에 따로 걸면 순위가 같아 AUROC는 그대로다. 등위 회귀는 동점을 만들어 AUROC가 바뀔 수 있다. 다중 클래스 소프트맥스에 온도를 걸면 클래스별 샘플 순위가 바뀔 수 있다. 보정용 검증 세트가 따로 필요하다.
- 자주 하는 오해: "출력 0.9는 실제로 90% 확률"이라고 믿는다. 깊은 신경망은 대개 과신하는 경향이 있어 보정 확인이 필요하다.
- 파고들 지점: 보정 세트와 평가 세트 분리, 기관별 보정 차이, 기준값 재설정 주기.
- 좋은 답변의 신호: 신뢰도 다이어그램으로 확인하고 기준값은 운영 목표로 정한다.
- 새벽소프트 사례: 루미스캔은 소견별 기준값을 두고 화면에 점수 구간을 표시한다.
- 기준 버전: 해당 없음

- 시스템에서 맡는 역할: 모델이 판정에 영향을 받은 영역을 영상 위에 색으로 보여 준다.
- 대안: 원본 CAM, Grad-CAM++, 적분 기울기, 가리기 실험(occlusion).
- 트레이드오프: 계산이 가볍지만 마지막 합성곱 층 해상도라 거칠다. 작은 결절은 위치가 흐리게 나올 수 있다.

- 새벽소프트 사례: 루미스캔은 소견별 히트맵을 판독 화면에 겹쳐 보여 준다.

- 새벽소프트 사례: 새벽소프트 면접 시스템은 이 기술 카드를 검색해 평가 근거로 쓴다.
- 기준 버전: 2026-11 기준 LangChain 1.x 계열. 0.x 시절 예제와 클래스 이름이 다를 수 있다.

- 키워드: 캔버스, Canvas 2D, WebGL, 웹지엘, GPU 렌더링, 셰이더, shader, 텍스처, texture, OffscreenCanvas, 대용량 영상
- 시스템에서 맡는 역할: 큰 의료 영상과 많은 도형을 브라우저에서 끊김 없이 그린다.
- 대안: DOM·SVG 렌더링, 서버에서 타일로 잘라 보내기, WebGPU.
- 트레이드오프: WebGL은 밝기·대비(창 조절)처럼 모든 픽셀을 다시 계산하는 일을 셰이더로 GPU에서 처리해 빠르지만, 코드가 복잡하고 컨텍스트 유실 처리가 필요하다. Canvas 2D는 단순하고 확대·이동은 drawImage와 변환 행렬로 대개 충분하다. 다만 getImageData 같은 픽셀 단위 연산은 CPU에서 돈다.
- 자주 하는 오해: "WebGL이면 항상 빠르다"고 믿는다. 매 프레임 텍스처를 다시 올리면 오히려 느려진다.
- 파고들 지점: 밝기·대비 조절 위치, 텍스처 크기 제한, 컨텍스트 유실 복구.
- 좋은 답변의 신호: 무엇을 GPU에 한 번 올리고 무엇을 매번 바꾸는지 구분한다.
- 새벽소프트 사례: 루미스캔 판독 화면은 흉부 X-ray를 Canvas·WebGL로 표시한다.
- 기준 버전: 해당 없음

- 대안: 서버가 정한 간격의 폴링, 푸시 알림.
- 트레이드오프: WebSocket은 양방향이지만 연결 유지 비용이 크다. 폴링은 단순하고 캐시와 부하 분산에 유리하다.

- 새벽소프트 사례: 줄서기 대기 화면은 서버가 알려 준 간격으로 순번을 폴링한다.

- 시스템에서 맡는 역할: 같은 요청이 여러 번 나가지 않게 막고, 응답 전에 화면을 먼저 바꿀지 정한다.
- 대안: 요청 중 버튼 비활성화, 요청 단위 키 전송, 서버 응답 후 갱신.
- 트레이드오프: 낙관적 업데이트는 빠르게 느껴지지만 실패하면 되돌려야 한다. 되돌림이 사용자에게 혼란을 준다.
- 자주 하는 오해: "결제도 낙관적으로 성공 표시하면 된다"고 믿는다. 돈과 좌석처럼 되돌리기 어려운 동작은 서버 확인 뒤 표시한다.
- 파고들 지점: 실패 시 되돌림 방식, 화면 차단과 서버 멱등의 역할 분담, 느린 응답 안내.
- 좋은 답변의 신호: 동작별로 낙관적 처리 여부를 나누고 서버 멱등을 전제로 둔다.
- 새벽소프트 사례: 줄서기는 관심 공연 표시는 즉시 바꾸고, 결제는 확인 뒤에 바꾼다.
