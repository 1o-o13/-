# 페이브릿지 — 3급 프로젝트 문서
<!--meta: doc=PRJ-PAY-3; doc_type=project; tier=3; topic=PAY; disclosure=public; status=done; stages=1차|2차-->

## 페이브릿지 문서 안내
<!--meta: sec=ov; dept=BE|FE|EMB; level=신입|주니어|시니어; ct_band=하-->
페이브릿지는 새벽마켓의 모든 결제를 받는 결제 승인 게이트웨이입니다. 온라인 주문 결제(카드·간편결제·계좌이체)와 오프라인 매장의 결제 단말 결제를 한곳에서 받아 카드사·간편결제사에 승인을 요청하고, 결과를 주문 서비스와 정산 쪽에 넘깁니다.
구성은 세 부분입니다. 백엔드팀이 맡는 승인 API·결제 원장·카드사 연동, 프론트엔드팀이 맡는 결제창(웹·앱), 임베디드팀이 맡는 매장 결제 단말 펌웨어입니다. 이 문서는 각 부서가 다루는 기본 기술을 난이도(하·중·상)별로 정리한 공개 문서입니다.

## 페이브릿지 BE-하1. 결제 요청 중복 막기 (멱등성 키)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=INC-PAY-01-->
사용자가 결제 버튼을 두 번 누르거나 네트워크가 끊겨 앱이 같은 요청을 다시 보내면, 같은 주문이 두 번 승인될 수 있습니다. 페이브릿지는 결제 요청마다 클라이언트가 만든 멱등성 키(Idempotency-Key)를 받습니다.
서버는 키를 Redis에 먼저 저장(SET NX, 24시간 만료)하고, 이미 있는 키면 승인을 다시 요청하지 않고 처음 결과를 그대로 돌려줍니다. 키 조회는 해시 기반이라 요청 수가 늘어도 O(1)에 가깝습니다. 처리 중인 키에 같은 요청이 오면 409와 함께 "처리 중"을 돌려줍니다.

## 페이브릿지 BE-하2. 결제 상태 흐름
<!--meta: sec=s2; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
결제 한 건은 READY → AUTH_REQUESTED → APPROVED / FAILED → (취소 시) CANCELED 순서로만 바뀝니다. 상태는 결제 원장 테이블(PostgreSQL)의 status 칸에 저장되고, 허용되지 않은 전이(예: FAILED → APPROVED)는 애플리케이션과 DB 제약 둘 다에서 막습니다.
상태가 바뀔 때마다 payment_event 테이블에 한 줄씩 남겨, 나중에 "언제 누가 왜 바꿨는지"를 따라갈 수 있게 합니다.

## 페이브릿지 BE-하3. 하루 결제 내역 대사 (정렬과 투 포인터)
<!--meta: sec=s3; dept=BE; level=신입|주니어; ct_band=하; related=TST-PAY-01-->
매일 새벽 카드사가 보내 주는 승인 내역 파일과 우리 결제 원장을 맞춰 보는 "대사" 작업이 있습니다. 두 목록을 승인번호로 정렬한 뒤, 투 포인터로 한 번씩만 훑으며 한쪽에만 있는 건(누락)과 금액이 다른 건(불일치)을 찾습니다.
하루 약 80만 건이라, 이중 반복문으로 비교하면 몇 시간이 걸리지만 정렬 + 투 포인터는 몇 초 안에 끝납니다. 찾은 건은 대사 예외 목록에 올려 담당자가 확인합니다.

## 페이브릿지 BE-중1. 카드사 응답 지연 감시와 타임아웃
<!--meta: sec=s4; dept=BE; level=신입|주니어|시니어; ct_band=중; related=INC-PAY-02-->
카드사 승인 API는 보통 300ms 안에 응답하지만, 장애가 나면 수십 초씩 늦어집니다. 페이브릿지는 카드사별로 연결 타임아웃 1초, 응답 타임아웃 5초를 두고, 최근 1분간 실패율이 30%를 넘으면 서킷 브레이커를 열어 그 카드사로 가는 요청을 바로 실패시킵니다.
타임아웃이 난 결제는 "승인됐는지 모름" 상태라 바로 실패로 처리하지 않고, 승인 조회 API로 다시 확인한 뒤 결정합니다.

## 페이브릿지 BE-중2. 결제 승인 결과를 주문 서비스에 전달 (Kafka)
<!--meta: sec=s5; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
승인 결과는 Kafka 토픽 payment.approved로 보냅니다. 주문 서비스와 정산 배치가 이 토픽을 구독합니다. 같은 결제의 이벤트 순서가 섞이지 않도록 결제 ID를 파티션 키로 씁니다.
DB 저장과 메시지 발행이 따로 실패하지 않게 트랜잭셔널 아웃박스 방식을 씁니다. 결제 원장과 같은 트랜잭션으로 outbox 테이블에 이벤트를 쓰고, 별도 발행기가 outbox를 읽어 Kafka에 보냅니다.

## 페이브릿지 BE-중3. 결제 수단 라우팅 (우선순위 큐)
<!--meta: sec=s6; dept=BE; level=신입|주니어|시니어; ct_band=중; related=TST-PAY-01-->
같은 카드라도 연결된 경로(카드사 직접 연동, PG 경유)가 여러 개라, 페이브릿지는 경로마다 최근 성공률·평균 지연·수수료로 점수를 매겨 가장 좋은 경로로 보냅니다. 경로 후보는 점수 기준 우선순위 큐에 넣고, 1초마다 점수를 갱신합니다.
가장 좋은 경로가 실패하면 큐에서 다음 경로를 꺼내 한 번만 재시도합니다. 재시도는 멱등성 키를 그대로 써서 이중 승인을 막습니다.

## 페이브릿지 BE-상1. 결제 원장 샤딩
<!--meta: sec=s7; dept=BE; level=신입|주니어|시니어; ct_band=상; related=PRJ-PAY-2-->
결제 원장은 하루 300만 건씩 쌓여 테이블 하나로는 조회와 인덱스 관리가 어려워졌습니다. 가맹점 ID 해시로 16개 샤드에 나눠 저장하고, 같은 가맹점의 결제는 한 샤드에 모이게 했습니다.
가맹점 하나가 전체 거래의 20%를 차지하는 대형 행사 때는 한 샤드에만 부하가 몰려, 대형 가맹점은 가맹점 ID + 날짜로 다시 나누는 방식을 검토 중입니다.

## 페이브릿지 BE-상2. 부분 취소와 금액 계산 (DP)
<!--meta: sec=s8; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-01-->
주문 하나에 쿠폰·포인트·카드가 섞여 결제되면, 상품 일부만 취소할 때 어느 수단에서 얼마를 돌려줄지 정해야 합니다. 규칙은 "포인트 먼저, 수수료가 적은 순서로, 쿠폰 최소 주문 금액 조건을 깨지 않게"입니다.
조건을 모두 지키는 조합 중 고객에게 유리하고 수수료가 적은 것을 찾기 위해, 남은 금액을 상태로 두는 DP로 계산합니다. 수단이 많아도 금액 단위(10원)로 상태 수가 정해져 시간 안에 끝납니다.

## 페이브릿지 BE-상3. 이중 승인 탐지 (해시와 Union-Find)
<!--meta: sec=s9; dept=BE; level=신입|주니어|시니어; ct_band=상; related=INC-PAY-01-->
멱등성 키가 없는 오래된 앱 버전에서 같은 주문이 다른 결제 ID로 두 번 승인되는 일이 남아 있습니다. 매시간 같은 카드 해시·같은 금액·5분 안의 승인을 해시 묶음으로 모으고, 주문 번호나 기기 ID가 겹치는 건끼리 Union-Find로 한 덩어리로 합칩니다.
한 덩어리에 승인이 둘 이상이면 이중 승인 의심으로 보고, 늦은 쪽을 자동 취소 후보로 올립니다.

## 페이브릿지 FE-하1. 결제창 화면 구성
<!--meta: sec=s10; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
결제창은 주문 금액 확인, 결제 수단 선택, 약관 동의, 결제하기 버튼 순서로 되어 있습니다. React + TypeScript로 만들고, 웹과 앱(웹뷰)이 같은 코드를 씁니다.
결제하기 버튼은 누르는 순간 비활성화하고 로딩 표시를 보여, 사용자가 두 번 누르지 못하게 합니다. 서버로 보내는 요청에는 화면을 열 때 만든 멱등성 키를 붙입니다.

## 페이브릿지 FE-하2. 카드 번호 입력 검사
<!--meta: sec=s11; dept=FE; level=신입|주니어; ct_band=하; related=INC-PAY-03-->
카드 번호는 4자리씩 끊어 보여 주고, 입력하는 동안 숫자 외 문자는 막습니다. 마지막 자리 검증은 룬(Luhn) 알고리즘으로 브라우저에서 먼저 확인해, 잘못 입력한 번호로 서버 요청이 나가지 않게 합니다.
카드 번호 원문은 화면 상태에만 잠깐 두고, 서버에는 결제사 SDK가 암호화한 값만 보냅니다. 로그와 오류 리포트에는 앞 6자리·뒤 4자리만 남깁니다.

## 페이브릿지 FE-하3. 결제 결과 화면과 새로고침
<!--meta: sec=s12; dept=FE; level=신입|주니어; ct_band=하; related=INC-PAY-03-->
결제가 끝나면 결과 화면으로 이동하는데, 사용자가 이 화면에서 새로고침하거나 뒤로 가기를 누르면 결제가 다시 요청되면 안 됩니다. 결과 화면은 주소에 결제 ID만 들고 와서 서버에서 결과를 조회해 보여 주고, 결제 요청 화면은 기록(history)에서 교체(replace)해 뒤로 가기로 돌아가지 않게 합니다.

## 페이브릿지 FE-중1. 간편결제 팝업과 창 사이 통신
<!--meta: sec=s13; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
간편결제를 고르면 결제사 인증 화면이 팝업(모바일은 새 탭)으로 뜹니다. 인증이 끝나면 팝업이 postMessage로 결과를 결제창에 알려 주는데, 다른 사이트가 보낸 메시지를 받지 않도록 origin을 결제사 주소 목록과 비교합니다.
사용자가 팝업을 그냥 닫으면 메시지가 오지 않으므로, 1초마다 팝업이 닫혔는지 확인해 "결제를 취소했어요" 상태로 바꿉니다.

## 페이브릿지 FE-중2. 결제창 로딩 속도
<!--meta: sec=s14; dept=FE; level=신입|주니어|시니어; ct_band=중; related=TST-PAY-01-->
결제창이 늦게 뜨면 이탈이 늘어서, 첫 화면 표시(LCP) 1.5초 이내를 목표로 합니다. 결제사 SDK는 크기가 커서 결제 수단을 고른 뒤에 불러오고(지연 로딩), 카드사 로고 이미지는 한 장의 스프라이트로 묶었습니다.
번들 분석 결과 날짜 라이브러리가 전체의 18%를 차지해, 필요한 기능만 직접 구현해 뺐습니다.

## 페이브릿지 FE-중3. 할부 개월 목록 정렬
<!--meta: sec=s15; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
카드사마다 무이자 할부 개월과 조건(최소 금액, 기간)이 달라, 서버가 내려 준 행사 목록에서 지금 주문에 맞는 것만 골라 보여 줍니다. 목록은 무이자 여부 → 개월 수 순서로 정렬하고, 같은 개월이 여러 행사에 걸치면 조건이 가장 좋은 것 하나만 남깁니다(해시로 개월별 최선값 유지).
행사 조건은 자주 바뀌어, 화면에 숫자를 직접 쓰지 않고 서버 값만 씁니다.

## 페이브릿지 FE-상1. 결제창 상태 관리
<!--meta: sec=s16; dept=FE; level=신입|주니어|시니어; ct_band=상; related=PRJ-PAY-2-->
결제창의 상태는 "수단 선택 → 인증 중 → 승인 요청 중 → 완료/실패" 같은 단계가 엮여 있어, 화면 곳곳에서 불(boolean) 값으로 관리하다 보니 "로딩 중인데 버튼이 켜짐" 같은 모순 상태가 생겼습니다.
지금은 상태 기계(state machine)로 바꿔, 허용된 전이만 일어나게 하고 각 상태에서 보여 줄 화면을 한곳에서 정합니다. 서버의 결제 상태 흐름과 이름을 맞췄습니다.

## 페이브릿지 FE-상2. 결제 화면 접근성과 보안 입력
<!--meta: sec=s17; dept=FE; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-02-->
화면 낭독기 사용자를 위해 결제 단계가 바뀔 때마다 aria-live로 안내하고, 오류 문구는 입력 칸과 연결합니다. 한편 카드 번호 칸은 보안 키패드를 쓰는데, 키 배열을 매번 섞기 때문에 낭독기와 충돌합니다.
보안 요구(키 입력 가로채기 방지)와 접근성을 함께 만족하는 방법을 정해야 합니다.

## 페이브릿지 FE-상3. 결제 실패 원인 수집 (실시간 모니터링)
<!--meta: sec=s18; dept=FE; level=신입|주니어|시니어; ct_band=상; related=TST-PAY-01-->
결제 실패가 서버 오류인지, 사용자가 인증을 포기한 것인지, 브라우저 문제인지 구분하려고 결제창 단계별 이벤트를 수집합니다. 이벤트는 사용자당 순서대로 쌓이고, 단계 사이 이탈을 BFS처럼 단계 그래프를 따라가며 어느 지점에서 가장 많이 빠지는지 계산합니다.
개인정보가 섞이지 않도록 이벤트에는 결제 ID 해시와 단계 이름만 담습니다.

## 페이브릿지 EMB-하1. 매장 결제 단말 구성
<!--meta: sec=s19; dept=EMB; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
새벽마켓 오프라인 매장의 결제 단말은 ARM Cortex-M 계열 MCU, 카드 리더(IC·NFC), 영수증 프린터, LTE 모뎀으로 되어 있습니다. 펌웨어는 C로 작성하고 FreeRTOS 위에서 카드 읽기·통신·화면 작업을 나눠 돌립니다.
단말은 승인 요청을 페이브릿지 승인 API로 보내고, 통신이 끊기면 정해진 금액 이하만 오프라인 승인 후 나중에 전송합니다.

## 페이브릿지 EMB-하2. 카드 리더 데이터 받기 (링 버퍼)
<!--meta: sec=s20; dept=EMB; level=신입|주니어; ct_band=하; related=INC-PAY-04-->
카드 리더는 UART로 데이터를 보내는데, 인터럽트마다 한 바이트씩 들어옵니다. 인터럽트 처리 함수에서는 받은 바이트를 링 버퍼에 넣기만 하고, 해석은 별도 작업에서 합니다.
읽는 위치와 쓰는 위치 두 포인터로 버퍼를 돌려 쓰는 방식(투 포인터)이라 메모리를 새로 잡지 않고, 버퍼가 가득 차면 가장 오래된 데이터부터 버리고 오류 횟수를 셉니다.

## 페이브릿지 EMB-하3. 영수증 프린터 제어
<!--meta: sec=s21; dept=EMB; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
영수증 프린터는 ESC/POS 명령으로 제어합니다. 글자 크기·굵기·정렬과 바코드 출력을 명령 바이트로 보내고, 용지가 없거나 덮개가 열리면 상태 바이트로 알려 줍니다.
인쇄 중 용지가 떨어지면 결제는 이미 승인된 상태이므로, 결제를 취소하지 않고 "영수증 재출력" 버튼으로 다시 뽑게 합니다.

## 페이브릿지 EMB-중1. 단말 오프라인 승인 큐
<!--meta: sec=s22; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=INC-PAY-04-->
LTE가 끊기면 단말은 5만 원 이하 결제만 오프라인 승인하고, 승인 내역을 플래시 메모리의 큐에 저장합니다. 통신이 돌아오면 오래된 순서대로 서버에 보내고, 서버가 받았다고 응답한 건만 큐에서 지웁니다.
전원이 갑자기 꺼져도 큐가 깨지지 않게, 쓰기는 "새 블록에 쓰고 → 완료 표시"의 두 단계로 합니다.

## 페이브릿지 EMB-중2. 펌웨어 원격 업데이트 (OTA)
<!--meta: sec=s23; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
펌웨어는 원격으로 업데이트합니다. 플래시를 A/B 두 영역으로 나눠 새 펌웨어를 안 쓰는 쪽에 받고, 서명(ECDSA)을 확인한 뒤 다음 부팅부터 그쪽으로 시작합니다. 새 펌웨어가 3번 연속 정상 부팅을 못 하면 이전 영역으로 돌아갑니다.
매장 영업 중에는 업데이트하지 않도록, 서버가 매장별 영업 시간을 보고 새벽에만 배포합니다.

## 페이브릿지 EMB-중3. 단말 작업 우선순위
<!--meta: sec=s24; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=TST-PAY-01-->
FreeRTOS 작업은 카드 읽기(가장 높음), 통신, 화면, 로그 전송(가장 낮음) 순서로 우선순위를 줍니다. 로그 전송이 공용 SPI 버스를 오래 잡고 있으면 카드 읽기가 늦어지는 우선순위 역전이 생겨, 뮤텍스에 우선순위 상속을 켰습니다.
작업마다 스택 사용량을 측정해 최대값의 1.5배로 잡았습니다.

## 페이브릿지 EMB-상1. 단말 전력 관리
<!--meta: sec=s25; dept=EMB; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-03-->
배터리형 휴대 단말은 하루 영업(12시간)을 버텨야 합니다. 결제가 없을 때는 LTE 모뎀을 절전 모드(PSM)로, MCU는 저전력 대기로 두고, 카드가 닿거나 화면을 누르면 인터럽트로 깨어납니다.
모뎀이 깨어나 다시 연결하는 데 2~4초가 걸려 첫 결제가 늦어지는 문제가 있어, 언제 미리 깨울지 정하는 규칙이 필요합니다.

## 페이브릿지 EMB-상2. 단말-서버 통신 보안
<!--meta: sec=s26; dept=EMB; level=신입|주니어|시니어; ct_band=상; related=PRJ-PAY-2-->
단말과 서버는 TLS 1.3 상호 인증으로 통신하고, 단말 인증서의 개인키는 보안 칩(Secure Element) 안에서만 씁니다. MCU 메모리가 작아 TLS 핸드셰이크에 1초 넘게 걸려, 세션 재개(resumption)를 써서 두 번째 연결부터 짧게 합니다.
인증서 만료가 다가오면 서버가 새 인증서 발급을 요청하고, 단말은 보안 칩 안에서 새 키를 만듭니다.

## 페이브릿지 EMB-상3. 매장 단말 상태 수집과 재배치 경로 (다익스트라)
<!--meta: sec=s27; dept=EMB; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-03-->
단말은 5분마다 배터리·신호 세기·오류 횟수를 보냅니다. 고장 단말이 생기면 근처 매장의 예비 단말을 보내는데, 매장과 물류 거점을 정점으로, 이동 시간을 간선 가중치로 둔 그래프에서 다익스트라로 가장 빨리 도착하는 예비 단말을 고릅니다.
펌웨어는 상태 메시지를 50바이트 안에 담도록 비트 단위로 압축합니다.


## 페이브릿지 BE-하4. 결제 금액 검증
<!--meta: sec=s28; dept=BE; level=신입|주니어; ct_band=하; related=INC-PAY-03-->
화면이 보낸 결제 금액을 그대로 믿으면 조작된 요청으로 적은 금액이 결제될 수 있습니다. 승인 요청이 오면 서버가 주문 서비스에서 주문 금액을 다시 가져와 비교하고, 다르면 승인하지 않습니다. 금액은 원 단위 정수(long)로만 다루고 실수(double)를 쓰지 않습니다.

## 페이브릿지 BE-중4. 결제 대기 만료 정리
<!--meta: sec=s29; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-PAY-2-->
결제창을 열고 결제하지 않은 READY 상태 결제가 하루 수십만 건 쌓입니다. 15분이 지나면 EXPIRED로 바꾸는데, 만료 시각 순으로 정렬된 인덱스에서 만료된 것만 1천 건씩 가져와 처리합니다. 처리 중 사용자가 결제를 진행하면 충돌하지 않도록 "READY일 때만 바꾸기" 조건부 업데이트를 씁니다.

## 페이브릿지 BE-상4. 정산 마감과 시간대
<!--meta: sec=s30; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-01-->
카드사는 하루 정산 마감을 23시 30분으로 두는데, 우리 원장의 날짜는 자정 기준입니다. 23시 30분~자정 결제가 카드사와 우리 쪽에서 다른 날로 잡혀 대사 예외가 매일 수천 건 생겼습니다. 결제마다 "카드사 영업일"을 따로 계산해 저장하고, 대사는 그 날짜로 맞춥니다.

## 페이브릿지 FE-하4. 결제 수단 기억하기
<!--meta: sec=s31; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
지난번에 쓴 결제 수단을 기본으로 골라 두면 결제가 빨라집니다. 카드 정보 자체는 저장하지 않고, 결제사가 준 토큰과 카드사 이름·뒤 4자리만 서버에 저장해 목록으로 보여 줍니다. 토큰이 만료되면 목록에서 회색으로 보이고 다시 등록하게 합니다.

## 페이브릿지 FE-중4. 결제 오류 문구
<!--meta: sec=s32; dept=FE; level=신입|주니어|시니어; ct_band=중; related=INC-PAY-03-->
카드사 오류 코드가 200개가 넘어 그대로 보여 주면 사용자가 이해하지 못합니다. 오류 코드를 "한도 초과", "카드 정보 오류", "잠시 후 다시", "다른 수단 사용" 네 묶음으로 나눠 묶음마다 다음 행동을 안내합니다. 코드–묶음 대응표는 서버에서 내려받아 화면 배포 없이 고칩니다.

## 페이브릿지 FE-상4. 결제창 시험 자동화
<!--meta: sec=s33; dept=FE; level=신입|주니어|시니어; ct_band=상; related=TST-PAY-01-->
결제창은 브라우저·앱 웹뷰·결제 수단 조합이 60가지가 넘어 사람이 다 시험할 수 없습니다. 결제사 시험 환경과 가짜 결제 서버를 두고, 화면 자동 시험이 조합마다 결제 → 결과 → 취소까지 돌립니다. 결제사 시험 환경이 자주 멈춰, 시험 실패가 우리 문제인지 구분하는 것이 어렵습니다.

## 페이브릿지 EMB-하4. 단말 화면 표시
<!--meta: sec=s34; dept=EMB; level=신입|주니어; ct_band=하; related=PRJ-PAY-2-->
단말 화면은 320×240 LCD로, 금액·안내 문구·진행 상태를 보여 줍니다. 한글 글꼴 전체는 플래시에 너무 커서, 단말에서 쓰는 문구에 들어간 글자 약 900자만 비트맵으로 넣었습니다. 서버에서 새 문구를 내려보내면 없는 글자가 있는지 미리 검사합니다.

## 페이브릿지 EMB-중4. 카드 리더 오류 재시도
<!--meta: sec=s35; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=INC-PAY-04-->
IC 카드를 덜 꽂거나 NFC를 너무 빨리 떼면 읽기 오류가 납니다. 오류 종류별로 재시도 여부를 정해, 접촉 불량은 바로 다시 읽고, 카드 응답 오류는 카드를 다시 대 달라고 안내합니다. 같은 카드로 연속 3번 실패하면 다른 결제 수단을 권합니다.

## 페이브릿지 EMB-상4. 단말 로그 압축과 전송
<!--meta: sec=s36; dept=EMB; level=신입|주니어|시니어; ct_band=상; related=ISS-PAY-03-->
장애 분석에 단말 로그가 필요하지만 LTE 요금과 플래시 수명 때문에 다 보낼 수 없습니다. 로그를 등급(오류·경고·정보)으로 나눠 오류만 바로 보내고, 나머지는 링 형태로 최근 2일치만 보관합니다. 반복되는 로그 문구는 번호로 바꿔 저장해(사전 압축) 크기를 1/5로 줄였습니다.

# 파인드 — 3급 프로젝트 문서
<!--meta: doc=PRJ-SRC-3; doc_type=project; tier=3; topic=SRC; disclosure=public; status=done; stages=1차|2차-->

## 파인드 문서 안내
<!--meta: sec=ov; dept=BE|AI|DATA; level=신입|주니어|시니어; ct_band=하-->
파인드는 새벽마켓의 상품 검색과 추천을 맡는 프로젝트입니다. 상품 약 1,200만 개를 검색 엔진(OpenSearch)에 색인하고, 사용자가 검색어를 넣으면 관련도 순으로 보여 줍니다. 홈 화면과 상품 상세의 "함께 본 상품", "이런 상품은 어때요" 추천도 파인드가 만듭니다.
백엔드팀은 검색 API·색인 파이프라인, ML팀은 순위 모델·추천 모델, 데이터팀은 클릭·구매 로그와 피처 데이터를 맡습니다.

## 파인드 BE-하1. 검색 API 기본 흐름
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-SRC-2-->
검색 API는 검색어를 받아 ① 정규화(공백·대소문자·전각 문자 정리) ② OpenSearch 질의 ③ 품절·판매 중지 상품 걸러내기 ④ 결과 20개 반환 순서로 처리합니다. 결과에는 상품 ID, 이름, 가격, 썸네일만 담고 상세 정보는 상품 서비스에서 따로 가져옵니다.
같은 검색어가 1분 안에 반복되면 Redis 캐시 결과를 돌려줘, 인기 검색어의 질의 부하를 줄입니다.

## 파인드 BE-하2. 검색 결과 페이지 나누기
<!--meta: sec=s2; dept=BE; level=신입|주니어; ct_band=하; related=INC-SRC-01-->
처음에는 from/size로 페이지를 나눴는데, 50페이지 넘게 넘기면 엔진이 앞의 결과를 모두 계산해야 해서 느려졌습니다. 지금은 마지막 결과의 (점수, 상품 ID)를 다음 요청에 넘기는 search_after 방식을 씁니다.
정렬 기준에 상품 ID를 꼭 넣어, 점수가 같은 상품이 페이지 사이에서 중복되거나 빠지지 않게 합니다.

## 파인드 BE-하3. 자동완성 (정렬과 이분 탐색)
<!--meta: sec=s3; dept=BE; level=신입|주니어; ct_band=하; related=TST-SRC-01-->
자동완성은 인기 검색어 30만 개를 사전순으로 정렬해 메모리에 두고, 입력한 접두어로 시작하는 범위를 이분 탐색으로 찾습니다. 범위 안에서 검색량이 많은 10개를 골라 보여 줍니다.
검색어 목록은 매시간 새로 만들고, 서버는 새 목록을 다 읽은 뒤 한 번에 바꿔(교체) 읽는 도중 빈 결과가 나가지 않게 합니다.

## 파인드 BE-하4. 검색어 오타 교정 후보
<!--meta: sec=s4; dept=BE|AI; level=신입|주니어; ct_band=하; related=PRJ-SRC-2-->
"아이퐁"처럼 오타가 난 검색어는 결과가 거의 없습니다. 결과가 5개 미만이면 인기 검색어 중 편집 거리가 1~2인 것을 찾아 "혹시 ○○을 찾으세요?"를 보여 줍니다. 편집 거리는 DP 표로 계산하고, 후보를 줄이려고 첫 글자와 길이가 비슷한 검색어만 비교합니다.

## 파인드 BE-중1. 색인 파이프라인 (CDC → 색인)
<!--meta: sec=s5; dept=BE|DATA; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->
상품 DB가 바뀌면 CDC(Debezium)가 변경을 Kafka로 보내고, 색인기가 받아 OpenSearch 문서를 고칩니다. 가격·재고처럼 자주 바뀌는 값은 부분 업데이트로, 이름·카테고리가 바뀌면 문서 전체를 다시 넣습니다.
같은 상품의 변경이 순서가 뒤바뀌어 도착하면 옛 값으로 덮일 수 있어, 문서에 버전(변경 시각)을 두고 더 오래된 변경은 버립니다.

## 파인드 BE-중2. 전체 재색인과 별칭 교체
<!--meta: sec=s6; dept=BE; level=신입|주니어|시니어; ct_band=중; related=INC-SRC-02-->
형태소 분석기 사전을 바꾸면 전체 상품을 다시 색인해야 합니다. 새 인덱스(products_v42)를 따로 만들어 채우고, 다 채워지면 검색이 보는 별칭(alias) products를 새 인덱스로 한 번에 옮깁니다.
재색인에 4시간이 걸리는 동안 들어온 변경은 Kafka 오프셋을 기억해 두었다가 새 인덱스에 다시 적용한 뒤 별칭을 옮깁니다.

## 파인드 BE-중3. 검색 결과 필터와 집계
<!--meta: sec=s7; dept=BE; level=신입|주니어|시니어; ct_band=중; related=TST-SRC-01-->

## 파인드 BE-중4. 추천 API와 후보 합치기 (우선순위 큐)
<!--meta: sec=s8; dept=BE|AI; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->
추천 API는 여러 후보 생성기(최근 본 상품과 비슷한 상품, 함께 구매, 인기 상품)에서 각각 점수가 매겨진 후보 목록을 받아 하나로 합칩니다. 각 목록은 점수순으로 정렬돼 있어, 우선순위 큐로 k개 목록을 합치며 이미 넣은 상품은 해시로 걸러 상위 50개를 만듭니다.
후보 생성기 하나가 늦으면 100ms에서 끊고 나머지로만 만듭니다.

## 파인드 BE-상1. 검색 응답 지연 줄이기
<!--meta: sec=s9; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-SRC-01-->
검색 p99 목표는 300ms인데, 순위 모델 재정렬을 붙인 뒤 450ms까지 늘었습니다. 엔진에서 상위 200개를 받아 모델로 다시 매기는데, 200개의 피처를 피처 저장소에서 가져오는 데 가장 오래 걸립니다.
피처를 한 번에 묶어 조회하고, 자주 검색되는 상품의 피처는 검색 서버 메모리에 두는 방법을 쓰고 있습니다.

## 파인드 BE-상2. 검색 클러스터 샤드 설계
<!--meta: sec=s10; dept=BE; level=신입|주니어|시니어; ct_band=상; related=PRJ-SRC-1-->
상품 인덱스는 샤드 12개 × 복제 2로 운영합니다. 샤드가 너무 적으면 한 샤드가 커져 재배치가 오래 걸리고, 너무 많으면 질의마다 모든 샤드를 돌아 합치는 비용이 커집니다.
카테고리별로 검색량 차이가 커서, 인기 카테고리만 따로 인덱스를 나누고 질의 라우팅으로 보내는 방안을 시험했습니다.

## 파인드 BE-상3. 연관 검색어 묶기 (Union-Find)
<!--meta: sec=s11; dept=BE|DATA; level=신입|주니어|시니어; ct_band=상; related=PRJ-SRC-2-->
같은 세션 안에서 30초 안에 이어서 검색한 검색어 쌍을 모아, 자주 함께 나온 쌍끼리 Union-Find로 묶어 연관 검색어 그룹을 만듭니다. 그룹이 너무 커지지 않게, 함께 나온 횟수가 기준보다 적은 쌍은 합치지 않고, 그룹 크기가 200을 넘으면 더 합치지 않습니다.
"아이폰 케이스"와 "갤럭시 케이스"처럼 비슷하지만 다른 상품군이 섞이는 문제가 있습니다.

## 파인드 BE-상4. 카테고리 경로 계산 (BFS)
<!--meta: sec=s12; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-SRC-02-->
카테고리는 부모가 여럿일 수 있는 그래프(예: "캠핑 의자"는 "캠핑"과 "가구" 둘 다 아래)입니다. 검색 결과의 카테고리 이동 경로(빵부스러기)를 보여 주려고 최상위부터 BFS로 가장 짧은 경로를 구합니다.
카테고리 편집 실수로 순환이 생기면 BFS가 끝나지 않아, 방문 표시와 최대 깊이(8)를 둡니다.

## 파인드 AI-하1. 검색 순위 기본 점수 (BM25)
<!--meta: sec=s13; dept=AI; level=신입|주니어; ct_band=하; related=PRJ-SRC-2-->
검색의 1차 점수는 BM25입니다. 검색어 단어가 상품 이름에 많이 나올수록, 그 단어가 전체 상품에서 드물수록 점수가 높습니다. 상품 이름이 짧은데 단어가 들어 있으면 긴 이름보다 높게 칩니다.
한국어는 형태소 분석기(nori)로 "무선이어폰"을 "무선 + 이어폰"으로 나눠 색인해야 검색이 됩니다.

## 파인드 AI-하2. 클릭 로그로 정답 만들기
<!--meta: sec=s14; dept=AI|DATA; level=신입|주니어; ct_band=하; related=INC-SRC-03-->
순위 모델을 학습하려면 "이 검색어에 이 상품이 좋은 결과인가"라는 정답이 필요합니다. 사람이 일일이 정할 수 없어 클릭·장바구니·구매 로그로 점수를 매깁니다(구매 3, 장바구니 2, 클릭 1, 노출만 0).
위에 보인 상품일수록 많이 클릭되는 위치 편향이 있어, 같은 상품이 다른 위치에 보였을 때의 클릭률로 보정합니다.

## 파인드 AI-하3. 추천 평가 지표
<!--meta: sec=s15; dept=AI; level=신입|주니어; ct_band=하; related=TST-SRC-01-->
추천 모델은 오프라인에서 Recall@20(실제 다음에 산 상품이 추천 20개 안에 있는 비율)과 NDCG@20(위에 있을수록 높게)으로 평가합니다. 오프라인 점수가 좋아도 실제 클릭이 늘지 않을 수 있어, 배포 전 A/B 시험으로 클릭률·구매 전환율을 확인합니다.

## 파인드 AI-하4. 함께 구매한 상품 추천 (해시로 세기)
<!--meta: sec=s16; dept=AI|BE; level=신입|주니어; ct_band=하; related=PRJ-SRC-2-->
가장 단순한 추천은 같은 주문에 함께 담긴 상품 쌍을 세는 것입니다. 주문마다 상품 쌍을 만들어 해시 맵에 (A, B) 횟수를 더하고, 상품 A마다 횟수 상위 20개를 추천합니다.
배송비 맞추려고 함께 담는 생필품(휴지, 생수)이 모든 상품의 추천에 나오는 문제가 있어, 전체 인기도로 나눠 보정합니다.

## 파인드 AI-중1. 순위 학습 모델 (LTR)
<!--meta: sec=s17; dept=AI; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->
BM25로 뽑은 상위 200개를 그래디언트 부스팅 순위 모델(LambdaMART)로 다시 매깁니다. 피처는 BM25 점수, 상품 클릭률, 가격대 적합도, 리뷰 수, 최근 판매량 등 40개입니다.
학습은 검색어 단위로 묶어(같은 검색어 안에서의 순서만 비교) 합니다. 판매량 피처가 너무 강해 신상품이 위로 못 오는 문제가 있습니다.

## 파인드 AI-중2. 벡터 검색 추가
<!--meta: sec=s18; dept=AI|BE; level=신입|주니어|시니어; ct_band=중; related=INC-SRC-03-->
"출근할 때 입을 가벼운 겉옷"처럼 상품 이름에 없는 표현은 BM25로 못 찾습니다. 상품 이름·설명을 문장 임베딩 모델로 벡터로 만들어 근사 최근접 이웃(HNSW) 인덱스에 넣고, 검색어 벡터와 가까운 상품을 함께 가져옵니다.
BM25 결과와 벡터 결과는 순위를 합치는 RRF로 섞습니다. 벡터 쪽은 모델 번호(예: 모델명 일부)를 잘 못 맞춥니다.

## 파인드 AI-중3. 콜드 스타트 상품
<!--meta: sec=s19; dept=AI; level=신입|주니어|시니어; ct_band=중; related=ISS-SRC-03-->
새로 올라온 상품은 클릭·구매 기록이 없어 추천과 순위에서 밀립니다. 상품 이미지·이름 임베딩으로 비슷한 기존 상품을 찾아 그 상품들의 반응을 빌려 쓰고, 첫 7일은 노출 기회를 일부러 조금 주는 탐색 슬롯을 둡니다.
탐색 슬롯이 너무 많으면 전체 클릭률이 떨어져, 비율을 실험으로 정합니다.

## 파인드 AI-중4. 검색어 의도 분류
<!--meta: sec=s20; dept=AI; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->
검색어를 "상품명", "카테고리", "브랜드", "상황·용도"로 분류해, 브랜드 검색이면 그 브랜드 상품을 먼저, 상황 검색이면 벡터 검색 비중을 높입니다. 분류 모델은 검색어 2만 개에 사람이 붙인 정답으로 학습했습니다.
"애플"처럼 브랜드와 과일이 겹치는 검색어는 최근 클릭 분포로 판단합니다.

지금은 시간 기준으로 나누고(마지막 7일은 평가만), 피처도 그 시점까지의 값만 쓰도록 시점 조인을 합니다.

인기 상품이 너무 많은 이웃을 가져 모든 벡터가 인기 상품 쪽으로 쏠리는 문제가 있습니다.

## 파인드 AI-상4. 검색 품질 자동 평가 (LLM 판정)
<!--meta: sec=s24; dept=AI; level=신입|주니어|시니어; ct_band=상; related=ISS-SRC-03-->

LLM 판정을 그대로 정답으로 쓰면 모델이 LLM의 버릇을 배울 수 있어, 사람 판정과 섞는 비율을 정해야 합니다.

## 파인드 DATA-중1. 피처 저장소
<!--meta: sec=s29; dept=DATA|AI; level=신입|주니어|시니어; ct_band=중; related=PRJ-SRC-2-->

같은 계산 코드로 두 곳을 채우고, 매일 표본을 뽑아 두 값이 같은지 비교합니다.

## 파인드 DATA-중2. 클릭률 계산과 표본이 적은 상품
<!--meta: sec=s30; dept=DATA|AI; level=신입|주니어|시니어; ct_band=중; related=ISS-SRC-03-->
노출 3번에 클릭 2번인 상품의 클릭률은 67%지만 믿기 어렵습니다. 전체 평균을 사전 값으로 두는 베이지안 평균으로 표본이 적은 상품의 클릭률을 평균 쪽으로 당겨 계산합니다.
카테고리마다 평균 클릭률이 크게 달라, 사전 값을 카테고리별로 둡니다.

## 파인드 DATA-중3. 검색 로그 품질 검사
<!--meta: sec=s31; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=INC-SRC-03-->
앱 업데이트로 클릭 이벤트에 검색 ID가 빠진 적이 있어, 시간마다 "검색 ID가 있는 클릭 비율", "노출 없는 클릭 비율"을 검사합니다. 기준을 벗어나면 그 시간 데이터에 표시를 하고, 학습 데이터 생성에서 뺍니다.
앱 버전별로 지표를 나눠 보면 어느 버전 문제인지 바로 알 수 있습니다.

## 파인드 DATA-중4. A/B 시험 분석
<!--meta: sec=s32; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=TST-SRC-01-->
검색 순위 실험은 사용자 ID 해시로 두 그룹을 나눠 2주 동안 돌립니다. 구매 전환율 차이가 우연인지 보려고 신뢰구간을 계산하는데, 구매를 많이 하는 소수 사용자가 결과를 흔들어 사용자 단위로 묶어 계산합니다.
실험 도중 행사가 시작되면 두 그룹 모두 지표가 크게 움직여, 기간을 늘리거나 행사 기간을 빼고 봅니다.

## 파인드 DATA-상1. 학습 데이터 생성 파이프라인
<!--meta: sec=s33; dept=DATA; level=신입|주니어|시니어; ct_band=상; related=PRJ-SRC-1-->
순위 모델 학습 데이터는 "검색 → 노출 → 클릭 → 구매"를 검색 ID로 이어 붙이고, 그 시점의 피처를 붙여 만듭니다. 하루 20억 건 노출을 Spark로 조인하는 데 3시간이 걸리고, 검색 ID 일부에 이벤트가 몰려 작업 하나만 오래 걸리는(데이터 쏠림) 문제가 있습니다.
쏠린 키는 소금(salt) 값을 붙여 나눠 처리한 뒤 다시 합칩니다.

## 파인드 DATA-상2. 시점 조인 (Point-in-time join)
<!--meta: sec=s34; dept=DATA|AI; level=신입|주니어|시니어; ct_band=상; related=INC-SRC-03-->
피처는 시간이 지나며 바뀌어, 학습 데이터에는 "그 검색이 일어난 시각 직전"의 피처 값을 붙여야 합니다. 이벤트와 피처 이력을 사용자·상품별로 시간순 정렬한 뒤, 각 이벤트보다 이전인 가장 최근 피처를 이분 탐색으로 찾아 붙입니다.
피처 이력을 모두 보관하면 저장 용량이 커서, 값이 바뀔 때만 기록합니다.

## 파인드 DATA-상3. 실시간 피처 (스트리밍)
<!--meta: sec=s35; dept=DATA; level=신입|주니어|시니어; ct_band=상; related=ISS-SRC-01-->
"지난 10분 동안 이 상품의 클릭 수" 같은 실시간 피처는 Flink로 계산해 Redis에 씁니다. 늦게 도착한 이벤트(모바일 오프라인 후 전송)는 워터마크 이후 5분까지만 받고 그 뒤는 버립니다.
Flink 작업이 재시작되면 체크포인트에서 이어 계산하는데, Redis에는 같은 값이 두 번 더해질 수 있어 덮어쓰기 방식으로 씁니다.

## 파인드 DATA-상4. 상품 중복 묶기
<!--meta: sec=s36; dept=DATA|AI; level=신입|주니어|시니어; ct_band=상; related=RES-SRC-01-->
판매자가 같은 상품을 여러 번 올려 검색 결과가 같은 상품으로 채워집니다. 이름·이미지 임베딩이 아주 가까운 상품 쌍을 찾고, 쌍을 Union-Find로 묶어 대표 상품 하나만 보여 줍니다.
1,200만 개끼리 모두 비교할 수 없어, 근사 최근접 이웃으로 상품마다 가까운 30개만 비교합니다.

## 파인드 BE-중5. 검색 요청 로그와 재현
<!--meta: sec=s37; dept=BE|DATA; level=신입|주니어|시니어; ct_band=중; related=TST-SRC-02-->
검색 품질 문제를 신고받으면 그때의 결과를 다시 봐야 하는데, 색인과 모델이 계속 바뀌어 재현이 어렵습니다. 검색 요청마다 검색어, 필터, 인덱스 버전, 모델 버전, 상위 결과 ID를 로그로 남기고, 같은 버전 조합으로 다시 돌려 볼 수 있는 재현 도구를 둡니다.

# 톡허브 — 3급 프로젝트 문서
<!--meta: doc=PRJ-CHT-3; doc_type=project; tier=3; topic=CHT; disclosure=public; status=done; stages=1차|2차-->

## 톡허브 문서 안내
<!--meta: sec=ov; dept=BE|FE|AI; level=신입|주니어|시니어; ct_band=하-->
톡허브는 새벽마켓 고객 상담 채팅입니다. 구매자가 앱·웹에서 상담을 시작하면 챗봇이 먼저 답하고, 해결이 안 되면 상담원에게 연결합니다. 상담원 화면에는 주문·결제·배송 정보와 상담 요약이 함께 보입니다. 하루 상담 약 6만 건, 동시 접속 상담원 400명입니다.
백엔드팀은 채팅 서버·메시지 저장·상담 배정, 프론트엔드팀은 구매자 채팅 화면과 상담원 화면, ML팀은 챗봇 답변·상담 요약·문의 분류를 맡습니다.

## 톡허브 BE-하1. 채팅 연결 (WebSocket)
<!--meta: sec=s1; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
채팅은 WebSocket 연결 하나로 주고받습니다. 연결할 때 로그인 토큰을 확인하고, 30초마다 핑을 보내 끊긴 연결을 정리합니다. 연결이 끊기면 앱은 1초, 2초, 4초… 간격을 늘려 다시 연결하고, 마지막으로 받은 메시지 번호를 보내 그 뒤 메시지만 다시 받습니다.

## 톡허브 BE-하2. 메시지 번호와 순서
<!--meta: sec=s2; dept=BE; level=신입|주니어; ct_band=하; related=INC-CHT-01-->
대화방마다 메시지에 1부터 늘어나는 번호를 붙입니다. 번호는 Redis INCR로 받아 동시에 보낸 메시지도 번호가 겹치지 않습니다. 화면은 번호순으로 보여 주고, 중간 번호가 빠졌으면 서버에 그 구간을 다시 요청합니다.

## 톡허브 BE-하3. 상담 대기열 배정
<!--meta: sec=s3; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
상담원 연결을 누르면 문의 종류(주문·결제·배송·반품)별 대기열에 들어갑니다. 상담원이 손이 비면 자기 담당 대기열에서 가장 오래 기다린 상담부터 가져갑니다. 대기 순번은 대기열 안 위치로 계산해 구매자 화면에 "앞에 n명"으로 보여 줍니다.

## 톡허브 BE-하4. 금칙어와 개인정보 가리기 (해시)
<!--meta: sec=s4; dept=BE|AI; level=신입|주니어; ct_band=하; related=INC-CHT-03-->
메시지를 저장하기 전에 카드 번호·주민번호·전화번호 형태를 정규식으로 찾아 가리고, 욕설 금칙어는 해시 집합으로 단어마다 O(1)에 확인합니다. 원문은 저장하지 않고 가린 문장만 남깁니다.
띄어쓰기를 바꾸거나 특수 문자를 섞은 욕설은 놓쳐, 정규화 후 검사합니다.

## 톡허브 BE-중1. 여러 서버 사이 메시지 전달 (Pub/Sub)
<!--meta: sec=s5; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-2-->
채팅 서버는 12대이고, 구매자와 상담원이 서로 다른 서버에 붙을 수 있습니다. 메시지를 받은 서버는 Redis Pub/Sub의 대화방 채널에 발행하고, 그 방 참가자가 붙은 서버들이 구독해 각자 연결로 내려보냅니다.
Pub/Sub은 구독자가 잠깐 끊기면 메시지를 잃어, 화면은 번호가 빈 구간을 다시 요청해 메웁니다.

## 톡허브 BE-중2. 상담원 배정 우선순위 (우선순위 큐)
<!--meta: sec=s6; dept=BE; level=신입|주니어|시니어; ct_band=중; related=TST-CHT-01-->
단순히 오래 기다린 순서로만 배정하면 결제 오류처럼 급한 문의가 밀립니다. 대기 시간, 문의 종류 가중치, 회원 등급, 재문의 여부로 점수를 매겨 우선순위 큐에서 꺼냅니다. 기다리는 동안 점수가 계속 올라 오래 기다린 상담이 끝없이 밀리지 않게 합니다.

## 톡허브 BE-중3. 메시지 저장소
<!--meta: sec=s7; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-2-->
메시지는 (대화방 ID, 메시지 번호)를 키로 하는 와이드 컬럼 저장소에 저장합니다. 한 대화방의 메시지가 한 파티션에 모여 번호 구간 조회가 빠릅니다. 3년 지난 상담은 압축 보관소로 옮깁니다.
상담 하나가 수천 개 메시지가 되는 경우가 있어 파티션이 너무 커지지 않게 월 단위로 나눕니다.

## 톡허브 BE-중4. 상담원 화면에 주문 정보 붙이기
<!--meta: sec=s8; dept=BE|FE; level=신입|주니어|시니어; ct_band=중; related=INC-CHT-02-->
상담이 배정되면 서버가 구매자의 최근 주문 5건, 결제 상태, 배송 위치를 각 서비스에서 동시에 가져와 상담원 화면에 붙입니다. 한 서비스가 늦으면 그 칸만 "불러오는 중"으로 두고 나머지를 먼저 보냅니다. 상담원 권한으로는 카드 번호 등 민감 정보는 가린 값만 받습니다.

## 톡허브 BE-상1. 연결 수 늘리기
<!--meta: sec=s9; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-01-->
행사 때 동시 연결이 30만까지 늘어 서버당 2.5만 연결을 버텨야 합니다. 연결마다 스레드를 쓰면 메모리가 모자라 이벤트 루프 방식 서버로 바꿨고, 연결당 메모리를 줄이려 버퍼를 필요할 때만 잡습니다.
서버 하나를 재배포하면 그 서버의 연결 2.5만 개가 한꺼번에 다시 붙어 다른 서버에 부하가 몰립니다.

## 톡허브 BE-상2. 상담 이관 흐름 (상태 기계)
<!--meta: sec=s10; dept=BE; level=신입|주니어|시니어; ct_band=상; related=PRJ-CHT-1-->
상담은 챗봇 → 대기 → 상담원 → (이관) → 다른 상담원 → 종료로 흐릅니다. 이관 중 원래 상담원과 새 상담원이 동시에 답하면 구매자가 혼란스러워, 이관 중에는 두 사람 모두 보내기를 잠그고 새 상담원이 수락해야 풀립니다.
이관 요청 뒤 새 상담원이 3분 안에 수락하지 않으면 원래 상담원에게 되돌립니다.

## 톡허브 BE-상3. 상담 흐름 분석 (BFS)
<!--meta: sec=s11; dept=BE|AI; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-02-->
챗봇 시나리오는 질문 노드와 선택지 간선으로 된 그래프입니다. 시작 노드에서 BFS로 각 노드까지 최소 몇 번 눌러야 하는지 계산해, 5번 넘게 눌러야 닿는 답변 노드를 찾아 시나리오를 고칩니다. 어느 노드에서도 닿지 않는 고아 노드도 함께 찾습니다.

## 톡허브 BE-상4. 반복 문의 묶기 (Union-Find)
<!--meta: sec=s12; dept=BE|AI; level=신입|주니어|시니어; ct_band=상; related=PRJ-CHT-2-->
같은 구매자가 같은 주문으로 채팅·전화·게시판에 따로 문의하면 상담원 셋이 같은 일을 합니다. 구매자 ID, 주문 번호, 연락처가 겹치는 문의끼리 Union-Find로 묶어 한 건으로 보여 주고, 먼저 맡은 상담원에게 몰아줍니다.

## 톡허브 FE-하1. 채팅 메시지 목록 화면
<!--meta: sec=s13; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
메시지 목록은 아래에서 위로 쌓이고, 새 메시지가 오면 맨 아래로 스크롤합니다. 사용자가 위로 올려 예전 메시지를 보고 있을 때는 스크롤을 움직이지 않고 "새 메시지 n개" 버튼만 띄웁니다. 메시지마다 보냄·읽음 상태를 표시합니다.

## 톡허브 FE-하2. 보내는 중 메시지 처리
<!--meta: sec=s14; dept=FE; level=신입|주니어; ct_band=하; related=INC-CHT-01-->
보내기를 누르면 서버 응답을 기다리지 않고 바로 목록에 "보내는 중"으로 그립니다(낙관적 업데이트). 서버가 번호를 붙여 돌려주면 그 메시지로 바꾸고, 10초 안에 응답이 없으면 "다시 보내기"를 보여 줍니다. 화면이 만든 임시 ID를 함께 보내 서버가 중복을 걸러냅니다.

## 톡허브 FE-하3. 사진 첨부
<!--meta: sec=s15; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
불량 상품 사진을 올릴 때 원본이 10MB 넘는 경우가 많아, 브라우저에서 긴 변을 1600px로 줄이고 JPEG 80%로 다시 압축해 올립니다. 올리는 동안 진행률을 보여 주고, 위치 정보 같은 사진 메타데이터는 지웁니다.

## 톡허브 FE-하4. 입력 중 표시
<!--meta: sec=s16; dept=FE|BE; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
상대가 입력 중이면 "입력 중…"을 보여 줍니다. 글자를 칠 때마다 보내면 메시지가 너무 많아, 처음 입력할 때 한 번 보내고 3초 동안은 다시 보내지 않습니다(스로틀). 5초 동안 새 신호가 없으면 표시를 끕니다.

## 톡허브 FE-중1. 긴 대화 목록 성능 (가상 스크롤)
<!--meta: sec=s17; dept=FE; level=신입|주니어|시니어; ct_band=중; related=TST-CHT-01-->
상담원 화면에서 메시지가 수천 개인 대화를 열면 브라우저가 멈췄습니다. 화면에 보이는 메시지와 위아래 조금만 실제로 그리는 가상 스크롤로 바꿨습니다. 메시지마다 높이가 달라, 그린 뒤 잰 높이를 저장하고 아직 안 그린 메시지는 평균 높이로 어림합니다. 스크롤 위치에 해당하는 메시지는 누적 높이 배열에서 이분 탐색으로 찾습니다.

## 톡허브 FE-중2. 상담원 여러 대화 동시 처리
<!--meta: sec=s18; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-2-->
상담원은 대화 최대 5개를 탭으로 동시에 맡습니다. 탭마다 WebSocket을 따로 열지 않고 연결 하나로 받은 뒤 대화방 ID로 나눠 각 탭 상태에 넣습니다. 보이지 않는 탭에 새 메시지가 오면 탭에 숫자 배지를 띄우고, 30초 넘게 답이 없으면 탭을 빨갛게 바꿉니다.

## 톡허브 FE-중3. 브라우저 탭 사이 동기화
<!--meta: sec=s19; dept=FE; level=신입|주니어|시니어; ct_band=중; related=INC-CHT-02-->
상담원이 같은 화면을 두 브라우저 탭으로 열면 연결이 둘이 되어 알림이 두 번 울렸습니다. BroadcastChannel로 탭끼리 대표 탭 하나를 정해 대표 탭만 서버와 연결하고, 다른 탭은 대표 탭에게서 메시지를 받습니다. 대표 탭이 닫히면 남은 탭 중 하나가 이어받습니다.

## 톡허브 FE-중4. 상담 위젯 다른 화면에 넣기
<!--meta: sec=s20; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-1-->
상담 버튼은 새벽마켓 모든 화면에 들어가야 해서, 채팅 화면을 iframe 위젯으로 만들고 바깥 페이지와는 postMessage로만 주고받습니다. 위젯이 바깥 페이지의 CSS에 영향을 받지 않도록 분리하고, 위젯 스크립트는 사용자가 상담 버튼을 누를 때 내려받습니다.

## 톡허브 FE-상1. 상담원 화면 상태 관리
<!--meta: sec=s21; dept=FE; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-03-->
상담원 화면은 대화 5개, 각 대화의 주문 정보, 요약, 추천 답변, 이관 상태가 얽혀 있습니다. 서버에서 온 이벤트(새 메시지, 이관 요청, 요약 완료)를 하나의 이벤트 처리기로 받아 상태를 바꾸고, 화면 조각은 필요한 부분만 구독하게 해 메시지 하나에 화면 전체가 다시 그려지지 않게 했습니다.

## 톡허브 FE-상2. 접속이 나쁜 환경
<!--meta: sec=s22; dept=FE; level=신입|주니어|시니어; ct_band=상; related=INC-CHT-01-->
지하철처럼 연결이 자주 끊기는 곳에서 구매자가 보낸 메시지가 사라졌다는 문의가 많았습니다. 보내지 못한 메시지는 IndexedDB에 저장해 두고, 다시 연결되면 순서대로 보냅니다. 같은 메시지가 두 번 가지 않게 임시 ID를 유지하고, 오래 끊긴 뒤에는 상담이 이미 끝났을 수 있어 보내기 전에 상태를 먼저 확인합니다.

## 톡허브 FE-상3. 추천 답변 끼워 넣기
<!--meta: sec=s23; dept=FE|AI; level=신입|주니어|시니어; ct_band=상; related=PRJ-CHT-2-->
ML 모델이 상담원에게 답변 후보 3개를 추천합니다. 추천은 구매자 메시지가 온 뒤 1~2초 걸려, 상담원이 이미 입력을 시작했으면 입력창을 덮지 않고 아래에 작게 보여 줍니다. 추천을 골랐는지, 고쳐서 보냈는지를 기록해 모델 평가에 씁니다.

## 톡허브 FE-상4. 상담원 화면 접근성과 단축키
<!--meta: sec=s24; dept=FE; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-03-->
상담원은 하루 수백 건을 처리해 마우스보다 키보드가 빠릅니다. 탭 이동, 추천 답변 고르기, 이관, 종료에 단축키를 두었는데 브라우저·화면 낭독기 단축키와 겹쳐 충돌했습니다. 단축키를 설정에서 바꿀 수 있게 하고, 포커스가 입력창에 있을 때와 아닐 때 동작을 나눴습니다.

## 톡허브 AI-하1. 문의 종류 분류
<!--meta: sec=s25; dept=AI; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
구매자의 첫 메시지로 문의를 주문·결제·배송·반품·기타로 분류해 대기열을 정합니다. 지난 상담 30만 건의 상담원 분류를 정답으로 써서 학습했습니다. "환불 언제 돼요"는 결제인지 반품인지 애매해, 주문 상태(반품 접수 여부)를 함께 넣습니다.

## 톡허브 AI-하2. 자주 묻는 질문 찾기
<!--meta: sec=s26; dept=AI|BE; level=신입|주니어; ct_band=하; related=TST-CHT-01-->
챗봇은 구매자 질문과 가장 비슷한 FAQ 문서를 찾아 답합니다. 질문과 FAQ를 임베딩해 코사인 유사도가 가장 높은 것을 고르고, 점수가 0.7보다 낮으면 답하지 않고 상담원 연결을 권합니다. 키워드가 정확히 맞는 경우를 놓치지 않으려 BM25 결과와 함께 봅니다.

## 톡허브 AI-하3. 감정 신호 감지
<!--meta: sec=s27; dept=AI; level=신입|주니어; ct_band=하; related=PRJ-CHT-2-->
화가 난 구매자는 빨리 상담원에게 연결해야 합니다. 메시지의 부정 표현, 느낌표 반복, 같은 말 반복을 신호로 점수를 매기고, 점수가 높으면 배정 우선순위를 올립니다. 판단 근거를 상담원 화면에 보여 주지는 않고 순위에만 씁니다.

## 톡허브 AI-하4. 상담 품질 지표
<!--meta: sec=s28; dept=AI|BE; level=신입|주니어; ct_band=하; related=TST-CHT-01-->
챗봇 성능은 해결률(상담원 연결 없이 끝난 비율), 재문의율(24시간 안 같은 주제 재문의), 만족도 설문으로 봅니다. 해결률만 보면 챗봇이 답을 대충 하고 끝내도 오르므로, 재문의율을 함께 봅니다.

## 톡허브 AI-중1. 상담 요약 (LLM)
<!--meta: sec=s29; dept=AI; level=신입|주니어|시니어; ct_band=중; related=PRJ-CHT-2-->
상담이 이관되거나 끝나면 LLM이 대화를 "문의 내용 / 확인한 사실 / 처리 결과 / 남은 일" 네 줄로 요약합니다. 요약에 대화에 없는 내용이 들어가면 안 되어, 요약 문장마다 근거가 된 메시지 번호를 함께 내게 하고 번호가 없는 문장은 지웁니다.

## 톡허브 AI-중2. 추천 답변 생성
<!--meta: sec=s30; dept=AI; level=신입|주니어|시니어; ct_band=중; related=INC-CHT-03-->
상담원 추천 답변은 지난 상담에서 비슷한 질문에 상담원이 보낸 답을 검색해 가져오고, LLM이 지금 주문 정보(배송 예정일 등)에 맞게 고쳐 씁니다. 숫자(금액·날짜)는 LLM이 만들지 않고 주문 정보에서 그대로 넣도록 칸을 비워 둔 틀을 씁니다.

## 톡허브 AI-중3. 챗봇 답변 근거 확인
<!--meta: sec=s31; dept=AI|BE; level=신입|주니어|시니어; ct_band=중; related=ISS-CHT-02-->
챗봇이 FAQ에 없는 환불 규정을 지어내 말한 적이 있어, 답변을 내기 전에 답변 문장이 검색된 FAQ 문서 안에 근거가 있는지 확인합니다. 근거가 약하면 "상담원이 확인해 드릴게요"로 바꿉니다. 확인에 걸리는 시간 때문에 답변이 0.5초 늦어집니다.

## 톡허브 AI-중4. 대화 데이터 가명 처리
<!--meta: sec=s32; dept=AI; level=신입|주니어|시니어; ct_band=중; related=INC-CHT-03-->
모델 학습에 상담 대화를 쓰려면 이름·주소·연락처를 가려야 합니다. 정규식으로 잡히지 않는 이름·주소는 개체명 인식 모델로 찾아 "[이름]", "[주소]"로 바꿉니다. 가린 뒤에도 "○○동 3층 꽃집"처럼 조합으로 사람을 알아볼 수 있는 경우가 있어 사람이 표본 검사를 합니다.

## 톡허브 AI-상1. 챗봇 다단계 대화
<!--meta: sec=s33; dept=AI; level=신입|주니어|시니어; ct_band=상; related=PRJ-CHT-1-->
"주문한 거 사이즈 바꾸고 싶은데 이미 출고됐나요"처럼 여러 단계가 필요한 문의는 FAQ 하나로 답할 수 없습니다. LLM이 주문 조회·배송 조회·교환 접수 도구를 순서대로 부르며 답을 만드는 구조를 시험 중입니다. 교환 접수처럼 되돌리기 어려운 동작은 구매자 확인을 받은 뒤에만 실행합니다.

## 톡허브 AI-상2. 요약 품질 평가
<!--meta: sec=s34; dept=AI; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-02-->
요약이 맞는지 사람이 다 볼 수 없어, 다른 LLM이 "요약 문장이 대화에 근거가 있는가", "중요한 내용이 빠졌는가"를 판정하게 했습니다. 판정 모델이 요약 모델과 같으면 같은 실수를 놓쳐, 다른 모델을 쓰고 사람 판정 500건과 일치율을 확인했습니다(83%).

## 톡허브 AI-상3. 응답 지연과 비용
<!--meta: sec=s35; dept=AI|BE; level=신입|주니어|시니어; ct_band=상; related=TST-CHT-01-->
LLM 요약·추천은 상담 한 건에 평균 4번 호출되어 비용이 큽니다. 자주 나오는 문의는 작은 모델로, 복잡한 문의만 큰 모델로 보내는 라우팅을 두었고, 같은 FAQ에 대한 답은 캐시합니다. 작은 모델로 잘못 보낸 경우를 줄이는 것이 과제입니다.

## 톡허브 AI-상4. 문의 급증 예측 (DP)
<!--meta: sec=s36; dept=AI|BE; level=신입|주니어|시니어; ct_band=상; related=ISS-CHT-01-->
배송 지연이나 결제 장애가 생기면 문의가 몇 배로 늡니다. 시간대별 문의 수를 예측해 상담원 근무 배치를 정하는데, 근무 교대 규칙(최소 4시간 연속, 휴게 시간)을 지키면서 예측 대기 시간을 최소로 하는 배치를 DP로 계산합니다. 예측이 틀리면 배치도 틀려, 실시간 문의 증가율로 비상 인력을 부르는 기준을 함께 둡니다.

# 레이크하우스 — 3급 프로젝트 문서
<!--meta: doc=PRJ-DWH-3; doc_type=project; tier=3; topic=DWH; disclosure=public; status=done; stages=1차|2차-->

## 레이크하우스 문서 안내
<!--meta: sec=ov; dept=DATA|BE; level=신입|주니어|시니어; ct_band=하-->
레이크하우스는 새벽마켓의 주문·결제·상품·행동 로그·물류 데이터를 한곳에 모아 분석과 모델 학습에 쓰게 하는 데이터 플랫폼입니다. 원천 DB의 변경을 CDC로 받아 Iceberg 테이블에 쌓고, Airflow가 매일·매시간 변환 작업(dbt, Spark)을 돌립니다. 하루 새로 들어오는 데이터는 약 4TB입니다.
데이터팀은 파이프라인·데이터 모델·품질을, 백엔드팀은 원천 시스템 연동과 데이터 조회 API를 맡습니다.

## 레이크하우스 DATA-하1. 계층 구조 (원천 → 정제 → 집계)
<!--meta: sec=s1; dept=DATA; level=신입|주니어; ct_band=하; related=PRJ-DWH-2-->
데이터는 세 층으로 나눕니다. 원천층은 받은 그대로, 정제층은 중복 제거·형식 통일·개인정보 가리기를 마친 것, 집계층은 "일별 매출", "상품별 판매량"처럼 바로 쓰는 표입니다. 분석가는 집계층만, 데이터 엔지니어는 정제층까지 씁니다. 원천층을 지우지 않아 계산 규칙이 바뀌면 다시 만들 수 있습니다.

## 레이크하우스 DATA-하2. 일별 매출 집계 SQL
<!--meta: sec=s2; dept=DATA; level=신입|주니어; ct_band=하; related=TST-DWH-01-->
일별 매출 = 결제 완료 금액 − 취소 금액입니다. 결제와 취소가 다른 날 일어날 수 있어, 결제일 기준 매출과 취소일 기준 매출 두 가지를 만들고 대시보드에 어느 기준인지 적습니다. 시간대는 모두 한국 시간으로 바꿔 날짜를 자릅니다(UTC로 자르면 오전 9시 전 주문이 전날로 갑니다).

## 레이크하우스 DATA-하3. 중복 행 제거 (정렬과 해시)
<!--meta: sec=s3; dept=DATA; level=신입|주니어; ct_band=하; related=INC-DWH-01-->
CDC와 재시도 때문에 같은 변경이 두 번 들어오는 일이 있습니다. (테이블, 기본키, 변경 순번)이 같은 행은 하나만 남기는데, 변경 순번이 없는 원천은 행 전체 값의 해시가 같으면 같은 행으로 봅니다. 같은 기본키의 최신 값만 필요하면 기본키·변경 시각으로 정렬해 마지막 행만 남깁니다.

## 레이크하우스 DATA-하4. 작업 실행 순서 (위상 정렬)
<!--meta: sec=s4; dept=DATA|BE; level=신입|주니어; ct_band=하; related=PRJ-DWH-2-->
Airflow 작업은 "주문 정제가 끝나야 매출 집계를 돌린다" 같은 선후 관계를 가진 그래프(DAG)입니다. 실행 순서는 위상 정렬로 정합니다. 선행 작업이 없는(진입 차수 0) 작업부터 돌리고, 끝날 때마다 뒤 작업의 진입 차수를 줄여 0이 되면 실행합니다. 순환이 생기면 DAG를 올릴 때 오류로 막습니다.

## 레이크하우스 DATA-중1. CDC로 원천 변경 받기
<!--meta: sec=s5; dept=DATA|BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-DWH-2-->
원천 DB의 변경 로그를 Debezium이 읽어 Kafka 토픽에 보내고, 수집기가 5분마다 Iceberg 테이블에 MERGE로 반영합니다. 원천 테이블에 칼럼이 추가되면 스키마 레지스트리가 새 버전을 기록하고, 정제층은 새 칼럼을 기본값으로 채워 깨지지 않게 합니다. 칼럼 삭제·형 변환은 자동으로 받지 않고 사람이 확인합니다.

## 레이크하우스 DATA-중2. 파티션과 작은 파일 문제
<!--meta: sec=s6; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=INC-DWH-02-->
행동 로그 테이블은 날짜·시간으로 파티션을 나눕니다. 5분마다 MERGE하다 보니 파티션마다 작은 파일이 수천 개 생겨 조회가 느려졌습니다. 매시간 작은 파일을 합치는 정리 작업(compaction)을 돌리고, 오래된 스냅샷은 7일 뒤 지웁니다.

## 레이크하우스 DATA-중3. 늦게 도착한 데이터
<!--meta: sec=s7; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=ISS-DWH-01-->
앱이 오프라인일 때 쌓인 로그는 며칠 뒤에 들어옵니다. 일별 집계를 하루 한 번만 만들면 늦게 온 데이터가 빠지므로, 최근 3일 파티션은 매일 다시 계산합니다. 3일 넘게 늦은 데이터는 별도 표에 모아 주간 보정 작업에서 반영합니다.

## 레이크하우스 AI-중2. 수요 예측 모델 데이터
<!--meta: sec=s30; dept=AI; level=신입|주니어|시니어; ct_band=중; related=TST-DWH-02-->
물류센터 재고를 정하려고 상품별 다음 주 판매량을 예측합니다. 행사·품절 기간의 판매량은 실제 수요가 아니라서(품절이면 0) 그대로 학습하면 수요를 낮게 봅니다. 품절 기간을 표시해 빼고, 행사 여부를 피처로 넣습니다. 상품 수가 많아 상품마다 모델을 두지 않고 하나의 모델로 학습합니다.

## 레이크하우스 AI-중3. 모델 결과를 레이크에 다시 쓰기
<!--meta: sec=s31; dept=AI|BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-DWH-2-->
예측 결과(고객별 재구매 확률 등)를 레이크 표로 다시 쓰면 다른 팀이 분석에 씁니다. 결과 표에는 모델 버전과 예측 날짜를 꼭 넣고, 같은 날 다시 돌리면 덮어쓰기(같은 파티션 교체)로 중복을 막습니다. 결과를 쓰는 작업이 실패하면 반쯤 쓰인 표가 보이지 않도록 한 번의 커밋으로 씁니다.

## 레이크하우스 AI-중4. 데이터 변화 감지 (드리프트)
<!--meta: sec=s32; dept=AI|DATA; level=신입|주니어|시니어; ct_band=중; related=ISS-DWH-04-->
앱 개편으로 행동 로그 이벤트 이름이 바뀌자 "상품 조회 수" 피처가 갑자기 절반이 되었고, 모델 예측이 크게 틀어졌습니다. 피처마다 매일 분포(평균, 분위수, 빈 값 비율)를 기록해 지난주와 비교하고, 차이가 크면 학습·예측을 멈추고 알립니다.

## 레이크하우스 AI-상1. 대규모 학습 데이터 읽기
<!--meta: sec=s33; dept=AI|DATA; level=신입|주니어|시니어; ct_band=상; related=ISS-DWH-02-->
추천 모델 학습 데이터가 3TB라, 학습 서버가 Iceberg 표를 읽는 속도가 GPU를 따라가지 못했습니다. 학습에 필요한 칼럼만 고르고(열 단위 읽기), 파일을 여러 작업이 나눠 읽게 했습니다. 매 학습마다 같은 데이터를 다시 읽지 않도록 학습용 형식으로 한 번 변환해 둡니다.

## 레이크하우스 AI-상2. 라벨이 늦게 확정되는 문제
<!--meta: sec=s34; dept=AI; level=신입|주니어|시니어; ct_band=상; related=PRJ-DWH-1-->
"반품될 주문" 예측의 정답(반품 여부)은 주문 후 최대 30일 뒤에야 확정됩니다. 최근 30일 주문은 정답이 미완성이라 학습에 넣으면 반품을 적게 배웁니다. 정답이 확정된 주문만 학습에 쓰고, 최근 경향은 확정 비율을 보정한 값으로 따로 확인합니다.

## 레이크하우스 AI-상3. 데이터 계보로 모델 영향 찾기 (BFS)
<!--meta: sec=s35; dept=AI|DATA; level=신입|주니어|시니어; ct_band=상; related=INC-DWH-04-->
원천 표 하나에 오류가 있었을 때, 그 표를 거쳐 만든 학습 데이터셋과 그 데이터셋으로 학습한 모델까지 찾아야 합니다. 계보 그래프에 데이터셋과 모델 정점을 추가해 오류 표에서 BFS로 내려가 영향받은 모델 목록을 만듭니다. 영향받은 모델은 다시 학습할지 담당자가 정합니다.

## 레이크하우스 AI-상4. 개인정보를 지키며 학습 (가명 처리)
<!--meta: sec=s36; dept=AI|BE; level=신입|주니어|시니어; ct_band=상; related=ISS-DWH-03-->
모델 학습에는 고객 식별자가 필요하지만 원문을 쓸 수 없습니다. 정제층의 가명 ID만 쓰고, 탈퇴 회원은 학습 데이터에서 지워야 합니다. 이미 학습된 모델에서 특정 회원의 영향을 지우는 것은 어려워, 정해진 주기로 탈퇴 회원을 뺀 데이터로 다시 학습합니다.

## 레이크하우스 DATA-하5. 표 문서화
<!--meta: sec=s37; dept=DATA; level=신입|주니어; ct_band=하; related=PRJ-DWH-2-->
표 900개 중 설명이 있는 표가 절반이었습니다. dbt 모델마다 표 설명, 칼럼 뜻, 담당자, 갱신 주기를 적게 하고, 설명이 없으면 집계층에 올리지 못하게 했습니다. 데이터 카탈로그 화면에서 표를 검색하고 계보를 볼 수 있습니다.

## 레이크하우스 BE-하5. 이벤트 시각 정하기
<!--meta: sec=s38; dept=BE|DATA; level=신입|주니어; ct_band=하; related=INC-DWH-04-->
이벤트에는 "일어난 시각"과 "서버가 받은 시각"이 있습니다. 앱 시계가 틀린 기기가 있어 일어난 시각이 미래로 들어오기도 합니다. 둘 다 저장하고, 일어난 시각이 받은 시각보다 1시간 넘게 미래면 받은 시각을 씁니다.

## 레이크하우스 DATA-중5. 증분 모델 (dbt incremental)
<!--meta: sec=s39; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=ISS-DWH-01-->
큰 표를 매일 처음부터 다시 만들면 비용이 커서, 새로 들어온 행만 처리해 붙이는 증분 방식으로 만듭니다. 늦게 들어온 행을 놓치지 않으려 "마지막 처리 시각 − 3일"부터 다시 읽고, 이미 있는 행은 기본키로 MERGE합니다. 계산 규칙이 바뀌면 전체를 한 번 다시 만들어야 합니다.

## 레이크하우스 BE-상5. 원천 DB 전환 때 데이터 연속성
<!--meta: sec=s40; dept=BE|DATA; level=신입|주니어|시니어; ct_band=상; related=PRJ-DWH-1-->
주문 DB를 새 클러스터로 옮길 때 CDC 위치(로그 번호)가 새 DB에서는 이어지지 않습니다. 전환 순간의 데이터를 양쪽에서 비교해 맞춘 뒤 새 DB의 CDC를 처음부터 시작하고, 전환 전후 겹치는 구간은 기본키로 중복을 지웁니다.

## 레이크하우스 DATA-상5. 표 갱신 시각 약속 (SLA)
<!--meta: sec=s41; dept=DATA|BE; level=신입|주니어|시니어; ct_band=상; related=ISS-DWH-01-->
경영 보고 대시보드는 매일 오전 8시까지 전날 숫자가 나와야 합니다. 표마다 "몇 시까지 갱신" 약속을 두고, 앞 작업이 늦어져 약속을 못 지킬 것 같으면 계보를 거슬러 가장 늦은 작업을 찾아 알립니다. 약속 시각에서 거꾸로 각 작업의 늦어도 되는 시작 시각을 계산해 둡니다(임계 경로).

# 팩토리아이 — 3급 프로젝트 문서
<!--meta: doc=PRJ-IOT-3; doc_type=project; tier=3; topic=IOT; disclosure=public; status=done; stages=1차|2차-->

## 팩토리아이 문서 안내
<!--meta: sec=ov; dept=EMB|DATA|AI|BE; level=신입|주니어|시니어; ct_band=하-->
팩토리아이는 새벽마켓 물류센터 3곳의 컨베이어·자동 분류기·포장기에 붙인 센서로 설비 상태를 실시간으로 보고, 고장 징후를 미리 알려 주는 프로젝트입니다. 센서 약 4,800개가 진동·온도·전류·속도를 1초~100ms 간격으로 보냅니다.
임베디드팀은 센서 장치와 엣지 게이트웨이 펌웨어, 데이터팀은 시계열 저장과 파이프라인, ML팀은 이상 탐지 모델, 백엔드팀은 설비 관리 API와 알림을 맡습니다.

## 팩토리아이 EMB-하1. 센서 장치 구성
<!--meta: sec=s1; dept=EMB; level=신입|주니어; ct_band=하; related=PRJ-IOT-2-->
센서 장치는 MCU, 3축 가속도 센서(진동), 온도 센서, 전류 센서, BLE 무선 칩으로 되어 있습니다. 센서 값은 I2C·SPI로 읽고, 1초마다 평균·최댓값을 계산해 근처 엣지 게이트웨이로 보냅니다. 전원은 설비 전원에서 받되, 정전 대비로 작은 배터리를 둡니다.

## 팩토리아이 EMB-하2. 센서 값 읽기 주기와 타이머
<!--meta: sec=s2; dept=EMB; level=신입|주니어; ct_band=하; related=INC-IOT-01-->
진동은 1kHz로 읽어야 해서 타이머 인터럽트마다 가속도 센서를 읽고 DMA로 버퍼에 모읍니다. 온도는 변화가 느려 1초에 한 번만 읽습니다. 인터럽트 안에서 계산을 하면 다음 인터럽트를 놓쳐, 계산은 버퍼가 찰 때 작업에서 합니다.

## 팩토리아이 EMB-하3. 이동 평균과 잡음 줄이기 (투 포인터)
<!--meta: sec=s3; dept=EMB|DATA; level=신입|주니어; ct_band=하; related=PRJ-IOT-2-->
전류 센서 값은 잡음이 커서 최근 50개 이동 평균을 씁니다. 매번 50개를 다시 더하지 않고, 새 값을 더하고 창 밖으로 나간 값을 빼는 방식(두 포인터로 창의 앞뒤 관리)으로 O(1)에 갱신합니다. 갑자기 튀는 값 하나는 중앙값 필터로 먼저 걸러냅니다.

## 팩토리아이 EMB-하4. 장치 ID와 설정
<!--meta: sec=s4; dept=EMB|BE; level=신입|주니어; ct_band=하; related=PRJ-IOT-2-->
장치는 공장에서 고유 ID와 인증서를 받아 출고됩니다. 설치할 때 설비 번호와 연결하면, 서버가 설비 종류에 맞는 측정 주기·임계값 설정을 내려보냅니다. 설정에는 버전 번호가 있어 장치는 더 새 버전만 받아들입니다.

## 팩토리아이 EMB-중1. 엣지 게이트웨이와 MQTT
<!--meta: sec=s5; dept=EMB|BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-IOT-2-->
게이트웨이는 BLE로 센서 장치 50~100개를 받아 MQTT로 서버에 보냅니다. 토픽은 센터/라인/설비/센서 순으로 나누고, 일반 측정값은 QoS 0, 경보는 QoS 1(최소 한 번 전달)로 보냅니다. 서버 연결이 끊기면 게이트웨이가 최근 30분 값을 저장해 두었다가 다시 보냅니다.

## 팩토리아이 EMB-중2. 진동 주파수 분석 (FFT)
<!--meta: sec=s6; dept=EMB|AI; level=신입|주니어|시니어; ct_band=중; related=TST-IOT-01-->
베어링이 상하면 특정 주파수 진동이 커집니다. 장치에서 1024개 표본마다 FFT를 돌려 주파수 대역별 에너지 8개만 서버로 보내, 원본 1kHz 데이터를 보내는 것보다 통신량을 99% 줄입니다. MCU의 DSP 명령을 써서 FFT 한 번에 4ms 걸립니다.

## 팩토리아이 EMB-중3. BLE 연결 관리
<!--meta: sec=s7; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=INC-IOT-01-->
물류센터는 금속 설비가 많아 무선 신호가 자주 약해집니다. 장치는 신호 세기가 기준 아래로 떨어지면 다른 게이트웨이를 찾아 옮겨 붙습니다. 옮겨 붙는 동안 놓친 값은 장치 메모리(최근 10분)에 두었다가 새 게이트웨이에 보냅니다.

## 팩토리아이 EMB-중4. 엣지에서 먼저 하는 경보 판단
<!--meta: sec=s8; dept=EMB|BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-IOT-2-->
온도가 급격히 오르는 것처럼 바로 멈춰야 하는 경보는 서버를 거치지 않고 게이트웨이가 판단해 설비 PLC에 정지 신호를 보냅니다. 엣지 판단 규칙은 단순 임계값과 변화율만 쓰고, 서버에서 내려받아 바꿀 수 있습니다. 엣지가 잘못 멈추면 라인 전체가 서므로, 같은 경보가 3초 연속일 때만 멈춥니다.

## 팩토리아이 EMB-상1. 저전력 무선 센서
<!--meta: sec=s9; dept=EMB; level=신입|주니어|시니어; ct_band=상; related=ISS-IOT-01-->
전원을 끌어오기 어려운 회전 설비에는 배터리 센서를 붙이는데, 2년을 버텨야 합니다. 평소에는 1분에 한 번만 깨어나 측정하고, 진동이 기준을 넘으면 측정 주기를 늘립니다. BLE 광고 주기, 측정 시간, 대기 전류를 합쳐 전력 예산을 계산하면 지금 설정으로 14개월밖에 못 갑니다.

## 팩토리아이 EMB-상2. 펌웨어 업데이트 수천 대 배포
<!--meta: sec=s10; dept=EMB|BE; level=신입|주니어|시니어; ct_band=상; related=INC-IOT-02-->
장치 4,800대에 펌웨어를 배포할 때 한꺼번에 보내면 BLE 대역이 막힙니다. 게이트웨이별로 동시에 5대씩, 라인이 쉬는 시간에만 보내고, 1%에 먼저 배포해 이상이 없으면 넓힙니다. 업데이트 파일은 바뀐 부분만 담은 차분 파일로 보내 크기를 80% 줄였습니다.

## 팩토리아이 EMB-상3. 시간 동기화
<!--meta: sec=s11; dept=EMB|DATA; level=신입|주니어|시니어; ct_band=상; related=ISS-IOT-02-->
설비 여러 대의 진동을 같은 시각끼리 비교하려면 장치 시계가 맞아야 합니다. 게이트웨이가 NTP로 맞춘 시간을 BLE로 장치에 주는데, 무선 지연 때문에 수 ms씩 틀립니다. 장치 시계가 하루에 2초씩 빨라지는 것도 있어, 동기화 간격과 보정 방식을 정해야 합니다.

## 팩토리아이 EMB-상4. 분류기 경로 재계산 (다익스트라)
<!--meta: sec=s12; dept=EMB|BE; level=신입|주니어|시니어; ct_band=상; related=PRJ-IOT-1-->
자동 분류기는 상자를 컨베이어 구간을 따라 목적지 출구로 보냅니다. 구간 하나가 고장 나면 PLC 제어기가 구간을 정점, 이동 시간을 간선으로 둔 그래프에서 다익스트라로 우회 경로를 다시 계산합니다. 제어기 메모리가 작아 구간 200개 그래프를 배열로만 표현하고, 우선순위 큐 대신 단순 배열 탐색을 씁니다.

## 팩토리아이 DATA-하1. 시계열 저장
<!--meta: sec=s13; dept=DATA; level=신입|주니어; ct_band=하; related=PRJ-IOT-2-->
센서 값은 TimescaleDB에 (센서 ID, 시각, 값)으로 저장하고, 하루 단위로 청크를 나눕니다. 원본은 30일만 두고, 1분 평균·최댓값은 2년 보관합니다. 최근 값 조회가 대부분이라 최근 청크만 빠른 디스크에 둡니다.

## 팩토리아이 DATA-하2. 다운샘플링
<!--meta: sec=s14; dept=DATA; level=신입|주니어; ct_band=하; related=TST-IOT-01-->

## 팩토리아이 BE-상1. 장치 설정 배포 (상태 맞추기)
<!--meta: sec=s41; dept=BE|EMB; level=신입|주니어|시니어; ct_band=상; related=INC-IOT-02-->
장치 4,800대의 설정과 펌웨어 버전을 서버가 "원하는 상태"로 두고, 장치가 보고한 "실제 상태"와 다르면 맞추는 방식(쿠버네티스와 비슷)으로 관리합니다. 장치가 오래 꺼져 있다가 켜지면 여러 버전 뒤의 설정을 한 번에 받는데, 중간 버전을 건너뛰면 안 되는 설정이 있어 순서를 지켜 적용합니다.

## 팩토리아이 BE-상2. 경보 우선순위 (우선순위 큐)
<!--meta: sec=s42; dept=BE|AI; level=신입|주니어|시니어; ct_band=상; related=ISS-IOT-03-->
엔지니어 화면에는 확인할 경보를 중요한 순서로 보여 줍니다. 점수 = 이상 점수 × 설비 중요도(라인 전체를 멈추는 설비는 높게) + 대기 시간 보정입니다. 새 경보가 계속 들어와 우선순위 큐에서 위로 올라오고, 엔지니어가 맡으면 큐에서 빠집니다.

## 팩토리아이 EMB-중5. 센서 장치 자가 진단
<!--meta: sec=s43; dept=EMB; level=신입|주니어|시니어; ct_band=중; related=INC-IOT-01-->
센서가 망가졌는지 설비가 이상한지 구분하려고, 장치는 부팅할 때와 하루 한 번 자가 진단을 합니다. 가속도 센서는 자체 시험 모드로 알려진 힘을 가해 값이 기준 범위인지 보고, 온도 센서는 MCU 내부 온도와 비교합니다. 진단 결과는 측정값과 함께 보내 서버가 센서 고장을 따로 표시합니다.

# 스토어프론트 — 3급 프로젝트 문서
<!--meta: doc=PRJ-WEB-3; doc_type=project; tier=3; topic=WEB; disclosure=public; status=done; stages=1차|2차-->

## 스토어프론트 문서 안내
<!--meta: sec=ov; dept=FE|BE; level=신입|주니어|시니어; ct_band=하-->
스토어프론트는 새벽마켓의 웹·앱 화면(홈, 검색 결과, 상품 상세, 장바구니, 주문서)과, 화면이 필요한 데이터를 여러 서비스에서 모아 주는 BFF(Backend for Frontend)입니다. 하루 방문자 약 400만 명, 페이지 조회 6천만 회입니다.
프론트엔드팀은 Next.js 웹과 앱 공통 화면, 백엔드팀은 BFF·캐시·화면 구성 API를 맡습니다.

## 스토어프론트 FE-하1. 페이지 렌더링 방식
<!--meta: sec=s1; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
홈과 상품 상세는 검색 엔진 노출과 첫 화면 속도가 중요해 서버에서 HTML을 만들어 보내고(SSR), 장바구니·주문서처럼 로그인 사용자 화면은 브라우저에서 그립니다. 카테고리 페이지처럼 자주 안 바뀌는 화면은 미리 만들어 두고 10분마다 다시 만듭니다.

## 스토어프론트 FE-하2. 상품 목록 이미지 지연 로딩
<!--meta: sec=s2; dept=FE; level=신입|주니어; ct_band=하; related=TST-WEB-01-->
검색 결과에 상품 이미지가 수십 개라 한꺼번에 받으면 첫 화면이 늦습니다. 화면 안 첫 줄만 바로 받고 나머지는 화면에 가까워질 때 받습니다(지연 로딩). 이미지 자리에는 미리 크기를 정해 두어, 이미지가 들어올 때 레이아웃이 밀리지 않게 합니다.

## 스토어프론트 FE-하3. 장바구니 수량 변경
<!--meta: sec=s3; dept=FE|BE; level=신입|주니어; ct_band=하; related=INC-WEB-01-->
수량 버튼을 빠르게 여러 번 누르면 요청이 여러 개 나가 순서가 뒤바뀌면 최종 수량이 틀립니다. 화면은 마지막 누름 후 300ms 동안 기다렸다가(디바운스) 한 번만 보내고, 응답이 오기 전 새 요청을 보내면 이전 요청을 취소합니다. 서버는 "수량을 n으로 설정" 방식으로 받아 순서 문제를 줄입니다.

## 스토어프론트 FE-하4. 최근 본 상품 (해시와 순서)
<!--meta: sec=s4; dept=FE; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
최근 본 상품 20개를 브라우저 저장소에 둡니다. 이미 있는 상품을 다시 보면 맨 앞으로 옮기고, 20개를 넘으면 가장 오래된 것을 지웁니다. 상품 ID로 위치를 바로 찾도록 해시 맵과 순서 목록을 함께 씁니다(LRU 캐시와 같은 구조).

## 스토어프론트 FE-중1. 웹 성능 지표
<!--meta: sec=s5; dept=FE; level=신입|주니어|시니어; ct_band=중; related=TST-WEB-01-->
LCP(가장 큰 요소 표시), INP(입력 반응), CLS(레이아웃 밀림)를 실제 사용자 브라우저에서 모아 봅니다. 상품 상세 LCP가 저사양 안드로이드에서 4초가 넘어, 큰 상품 이미지를 미리 불러오고(preload) 화면 밖 스크립트는 늦게 실행합니다.

## 스토어프론트 FE-중2. 화면 상태와 서버 데이터 캐시
<!--meta: sec=s6; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-2-->
서버에서 받은 데이터(상품, 장바구니)는 서버 상태 캐시 라이브러리로 관리하고, 화면 안에서만 쓰는 값(열린 메뉴)은 컴포넌트 상태로 둡니다. 장바구니에 상품을 담으면 장바구니 캐시를 무효화해 다시 받게 하고, 배지 숫자는 응답 전에 먼저 올립니다.

## 스토어프론트 FE-중3. 무한 스크롤과 뒤로 가기
<!--meta: sec=s7; dept=FE; level=신입|주니어|시니어; ct_band=중; related=INC-WEB-02-->
검색 결과를 무한 스크롤로 보다가 상품을 눌렀다 뒤로 오면 처음부터 다시 보여 불만이 많았습니다. 불러온 페이지들과 스크롤 위치를 세션 저장소에 두었다가 뒤로 오면 복원합니다. 오래 지나 돌아오면 가격이 바뀌었을 수 있어 5분 넘으면 새로 받습니다.

## 스토어프론트 FE-중4. 앱과 웹 공통 화면
<!--meta: sec=s8; dept=FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-1-->
앱의 일부 화면(행사 페이지, 주문서)은 웹뷰로 웹 화면을 띄웁니다. 앱 기능(공유, 결제 앱 호출)은 앱이 제공하는 브리지 함수로 부르고, 웹에서 열렸을 때는 같은 기능을 웹 방식으로 대신합니다. 앱 버전마다 브리지 함수가 달라 기능 확인 후 부릅니다.

## 스토어프론트 FE-상1. 홈 화면 개인화 조각
<!--meta: sec=s9; dept=FE|BE; level=신입|주니어|시니어; ct_band=상; related=ISS-WEB-01-->
홈 화면은 "추천 상품", "최근 본 상품과 비슷한", "행사" 등 조각 20여 개로 되어 있고, 사용자마다 조각 순서와 내용이 다릅니다. 모두 서버에서 그리면 캐시를 못 써 느리고, 모두 브라우저에서 그리면 첫 화면이 비어 보입니다. 공통 틀은 캐시된 HTML로, 개인화 조각은 나중에 흘려보내는(스트리밍) 방식을 씁니다.

## 스토어프론트 FE-상2. 번들 크기 관리
<!--meta: sec=s10; dept=FE; level=신입|주니어|시니어; ct_band=상; related=TST-WEB-01-->
기능이 늘며 첫 페이지 자바스크립트가 900KB를 넘었습니다. 페이지별로 나눠 내려받고, 무거운 라이브러리(차트, 지도)는 필요할 때 받습니다. 배포마다 번들 크기를 재서 이전보다 10% 넘게 커지면 CI에서 경고합니다. 공통 모듈이 여러 덩어리에 중복 포함된 것을 찾아 합쳤습니다.

## 스토어프론트 FE-상3. 주문서 폼 검증과 상태 기계
<!--meta: sec=s11; dept=FE; level=신입|주니어|시니어; ct_band=상; related=INC-WEB-01-->
주문서는 배송지, 쿠폰, 포인트, 결제 수단이 서로 영향을 줍니다(쿠폰을 바꾸면 결제 금액과 쓸 수 있는 포인트가 바뀜). 각 칸을 따로 관리하니 순서에 따라 금액이 다르게 보이는 버그가 났습니다. 주문서 상태를 하나로 두고, 값이 바뀌면 금액 계산을 서버에 한 번 물어 그 결과로만 화면을 그립니다.

## 스토어프론트 FE-상4. 카테고리 메뉴 트리 렌더링 (DFS·BFS)
<!--meta: sec=s12; dept=FE; level=신입|주니어|시니어; ct_band=상; related=PRJ-WEB-2-->
전체 카테고리 메뉴는 9천 개 노드의 트리입니다. 모두 그리면 느려 펼친 노드의 자식만 그리고, 검색어로 메뉴를 거를 때는 BFS로 맞는 노드와 그 조상만 남깁니다. 키보드로 위아래 이동할 때는 펼쳐진 노드를 DFS 순서로 펼친 목록을 만들어 다음 노드를 찾습니다.

## 스토어프론트 BE-하1. BFF가 하는 일
<!--meta: sec=s13; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
상품 상세 화면 하나에 상품, 가격, 재고, 리뷰 요약, 배송 예정일, 쿠폰 정보가 필요합니다. 화면이 서비스 6개를 따로 부르면 느리고 복잡해, BFF가 한 번의 요청으로 모아 화면에 맞는 모양으로 돌려줍니다. BFF는 Node.js(TypeScript)로 만들었습니다.

## 스토어프론트 BE-하2. 동시 호출과 시간 제한
<!--meta: sec=s14; dept=BE; level=신입|주니어; ct_band=하; related=INC-WEB-03-->
BFF는 서비스 6개를 동시에 부르고, 각각 시간 제한(300ms)을 둡니다. 리뷰 요약처럼 없어도 되는 정보가 늦으면 그 칸만 비우고 응답하고, 가격·재고처럼 꼭 필요한 정보가 실패하면 화면 전체를 오류로 처리합니다. 어떤 정보가 필수인지는 화면마다 정해 둡니다.

## 스토어프론트 BE-하3. 응답 캐시 (해시 키)
<!--meta: sec=s15; dept=BE; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
로그인하지 않은 사용자의 상품 상세 응답은 (상품 ID, 화면 버전)을 키로 30초 캐시합니다. 로그인 사용자는 쿠폰·회원가 때문에 응답이 달라, 공통 부분만 캐시하고 개인 부분은 따로 붙입니다. 캐시 키에 사용자 정보가 섞이지 않게 키 만드는 함수를 하나로 정했습니다.

## 스토어프론트 BE-하4. 상품 목록 정렬 옵션
<!--meta: sec=s16; dept=BE; level=신입|주니어; ct_band=하; related=TST-WEB-01-->
카테고리 페이지는 인기순, 최신순, 낮은 가격순, 리뷰 많은 순으로 정렬합니다. 정렬은 검색 엔진에 맡기되, 가격이 같으면 상품 ID로 한 번 더 정렬해 페이지를 넘겨도 순서가 흔들리지 않게 합니다. 할인 가격으로 정렬할 때는 할인이 끝난 상품이 남지 않게 시각 조건을 함께 겁니다.

## 스토어프론트 BE-중1. 캐시 무효화
<!--meta: sec=s17; dept=BE; level=신입|주니어|시니어; ct_band=중; related=INC-WEB-02-->
가격이 바뀌었는데 캐시 때문에 옛 가격이 보이면 주문서에서 금액이 달라 민원이 생깁니다. 가격 변경 이벤트를 받으면 해당 상품 캐시를 지우고, 주문서·장바구니는 캐시를 쓰지 않고 항상 원본에서 가격을 다시 확인합니다. 캐시를 한꺼번에 지우면 원본 서비스로 요청이 몰려 순차적으로 지웁니다.

## 스토어프론트 BE-중2. 행사 시작 순간 트래픽
<!--meta: sec=s18; dept=BE; level=신입|주니어|시니어; ct_band=중; related=TST-WEB-01-->
타임 세일 시작 정각에 평소의 15배 요청이 몰립니다. 행사 페이지는 미리 만들어 CDN에 올리고, 재고 숫자만 BFF가 1초 캐시로 내려줍니다. 같은 상품 재고 요청이 동시에 수천 개 오면 원본에는 하나만 보내고 나머지는 그 결과를 함께 받게 합니다(요청 합치기).

## 스토어프론트 BE-중3. 화면 구성 API
<!--meta: sec=s19; dept=BE|FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-1-->
홈과 행사 페이지는 운영자가 관리 화면에서 조각을 배치하면 바로 바뀌어야 합니다. 화면 구성 API가 "어떤 조각을 어떤 순서로, 각 조각의 데이터는 어디서"를 JSON으로 내려주고, 웹·앱이 그 구성대로 그립니다. 앱이 모르는 새 조각 종류가 오면 건너뛰도록 약속했습니다.

## 스토어프론트 BE-중4. 배송 예정일 계산 (BFS)
<!--meta: sec=s20; dept=BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-2-->
상품 상세에 "내일 도착"을 보여 주려면 재고가 있는 물류센터와 고객 주소 사이의 배송 단계를 알아야 합니다. 센터·거점·지역을 정점, 하루에 갈 수 있는 이동을 간선으로 두고 BFS로 최소 며칠이 걸리는지 계산합니다. 주소마다 계산하면 느려, 지역 단위로 미리 계산한 표를 씁니다.

## 스토어프론트 BE-상1. BFF 장애 격리
<!--meta: sec=s21; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-WEB-02-->
BFF는 모든 화면이 거쳐서, BFF 하나가 느려지면 새벽마켓 전체가 느려집니다. 화면별로 BFF 서버 묶음을 나눠(홈, 상품, 주문) 한 화면의 문제가 다른 화면으로 번지지 않게 하고, 서비스별 동시 요청 수에 한도를 두어 느린 서비스가 BFF 자원을 다 쓰지 못하게 합니다.

## 스토어프론트 BE-상2. 장바구니 금액 계산 (그리디의 한계)
<!--meta: sec=s22; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-WEB-01-->

## 스토어프론트 BE-상3. 스키마 변경과 하위 호환
<!--meta: sec=s23; dept=BE|FE; level=신입|주니어|시니어; ct_band=상; related=INC-WEB-03-->
앱은 사용자가 업데이트하지 않아 1년 전 버전도 남아 있습니다. BFF 응답 필드를 바꾸면 옛 앱이 깨질 수 있어, 필드는 추가만 하고 지우거나 뜻을 바꾸지 않습니다. 앱 버전을 요청 머리에 담아, 오래된 버전에는 옛 모양 응답을 따로 만들어 줍니다.

## 스토어프론트 BE-상4. 엣지 렌더링과 개인정보

첫 화면을 사용자 가까운 CDN 엣지에서 그리는 방식을 시험합니다. 엣지에서는 쿠키의 로그인 정보로 개인화할 수 있지만, 엣지 캐시에 개인 응답이 저장되어 다른 사람에게 보이면 큰 사고입니다. 개인화 응답은 캐시 금지 헤더를 반드시 붙이고, 캐시 키 검사를 배포 전에 자동으로 합니다.

## 스토어프론트 DATA-하1. 화면 행동 로그 설계
<!--meta: sec=s25; dept=DATA; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
웹·앱은 화면 진입, 조각 노출, 클릭, 장바구니 담기 이벤트를 보냅니다. 이벤트 이름과 속성을 표(이벤트 사전)로 정해 두고, 사전에 없는 이벤트는 수집 서버가 따로 모아 담당자에게 알립니다. 화면마다 개발자가 이름을 제각각 지어 같은 행동이 다른 이름으로 쌓이는 것을 막기 위해서입니다.

## 스토어프론트 DATA-하2. 조각별 클릭률 계산
<!--meta: sec=s26; dept=DATA; level=신입|주니어; ct_band=하; related=TST-WEB-02-->
홈 조각마다 클릭률 = 클릭 수 / 노출 수입니다. 노출은 조각이 화면에 절반 이상 보인 채 1초 넘게 있을 때만 셉니다. 스크롤하며 스치기만 한 것까지 세면 아래쪽 조각의 클릭률이 지나치게 낮게 나옵니다.

## 스토어프론트 DATA-하3. 이탈 지점 찾기 (정렬과 투 포인터)
<!--meta: sec=s27; dept=DATA; level=신입|주니어; ct_band=하; related=PRJ-WEB-2-->
상품 상세 → 장바구니 → 주문서 → 결제 완료 단계에서 어디서 많이 빠지는지 봅니다. 사용자별 이벤트를 시각순 정렬하고 두 포인터로 단계 순서를 따라가며 몇 단계까지 갔는지 셉니다. 중간에 다른 상품을 보고 돌아온 경우도 같은 흐름으로 이어 봅니다.

## 스토어프론트 DATA-하4. 페이지 속도 데이터 모으기
<!--meta: sec=s28; dept=DATA|FE; level=신입|주니어; ct_band=하; related=TST-WEB-01-->
실제 사용자 브라우저의 LCP·INP·CLS를 모아 페이지·기기·통신 종류별로 75분위 값을 매일 계산합니다. 평균은 아주 느린 몇 명에 끌려가 75분위를 씁니다. 수집량을 줄이려 사용자 10%만 표본으로 보냅니다.

## 스토어프론트 DATA-중1. A/B 시험 배정
<!--meta: sec=s29; dept=DATA|BE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-2-->
화면 실험은 사용자 ID와 실험 이름을 함께 해시해 0~99 칸으로 나누고, 칸 범위로 그룹을 정합니다. 실험마다 해시가 달라 같은 사람이 모든 실험에서 같은 그룹에 몰리지 않습니다. 로그인 전 방문자는 기기 ID로 배정하고, 로그인하면 사용자 ID 배정으로 바뀌어 그룹이 바뀔 수 있습니다.

## 스토어프론트 DATA-중2. 실험 결과 분석
<!--meta: sec=s30; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=INC-WEB-04-->
구매 전환율 차이를 볼 때 한 사람이 여러 번 방문하면 방문을 독립으로 볼 수 없어 사용자 단위로 묶어 계산합니다. 실험을 매일 들여다보다 유리할 때 멈추면 우연한 차이를 효과로 착각해, 시작 전에 기간과 판정 기준을 정해 둡니다.

## 스토어프론트 DATA-중3. 세션 재구성과 앱·웹 연결
<!--meta: sec=s31; dept=DATA; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-2-->
같은 사람이 앱에서 상품을 보고 웹에서 주문하는 경우가 많습니다. 로그인한 이벤트는 사용자 ID로 잇고, 로그인 전 기기 ID 이벤트는 같은 기기에서 나중에 로그인한 사용자에게 붙입니다. 기기 하나를 가족이 같이 쓰면 잘못 이어 붙는 문제가 있습니다.

## 스토어프론트 DATA-중4. 조각 성과 대시보드

운영자가 홈 조각 배치를 정할 수 있게 조각별 노출, 클릭률, 클릭 후 구매액을 매일 보여 줍니다. 위에 놓인 조각은 원래 성과가 좋아 보이므로(위치 효과), 같은 조각이 다른 위치에 있었을 때와 비교한 값도 함께 보여 줍니다.

## 스토어프론트 DATA-상1. 위치 효과 보정

조각 순서를 정하려면 조각 자체의 매력을 알아야 하는데, 관찰 데이터는 위치 효과가 섞여 있습니다. 위치별 기본 클릭률을 무작위 배치 실험(트래픽 1%)으로 따로 구하고, 그 값으로 나눠 조각 매력을 추정합니다. 무작위 배치는 매출을 조금 떨어뜨려 비율을 작게 유지합니다.

## 스토어프론트 DATA-상2. 대량 로그 실시간 집계

행사 시작 직후 조각별 클릭률을 1분 단위로 보여 줘야 해서, 초당 20만 이벤트를 스트리밍으로 집계합니다. 사용자 수(중복 제거)를 정확히 세려면 메모리가 많이 들어, 근사 계수 알고리즘(HyperLogLog)으로 오차 1% 안에서 셉니다.

## 스토어프론트 DATA-상3. 봇 트래픽 걸러내기

## 스토어프론트 DATA-상4. 화면 변경 효과 장기 추적
<!--meta: sec=s36; dept=DATA; level=신입|주니어|시니어; ct_band=상; related=PRJ-WEB-1-->
2주 실험에서는 좋았던 화면 변경이 석 달 뒤 재방문을 줄인 사례가 있었습니다. 일부 사용자(1%)는 변경 전 화면을 계속 보게 두는 장기 대조군을 운영해, 재방문·연간 구매액 같은 느린 지표를 비교합니다. 대조군 사용자의 불편을 줄이기 위해 몇 달마다 대조군을 바꿉니다.

## 스토어프론트 FE-하5. 폼 입력 오류 안내
<!--meta: sec=s37; dept=FE; level=신입|주니어; ct_band=하; related=INC-WEB-01-->
배송지 입력에서 우편번호·연락처 형식이 틀리면 칸 바로 아래에 이유를 보여 주고, 제출 버튼을 누르면 첫 오류 칸으로 이동합니다. 오류 문구는 칸과 연결해 화면 낭독기가 읽게 합니다.

## 스토어프론트 FE-중5. 이미지 형식과 크기 고르기
<!--meta: sec=s38; dept=FE; level=신입|주니어|시니어; ct_band=중; related=TST-WEB-01-->
같은 상품 이미지를 기기 화면 크기에 맞는 여러 크기와 형식(AVIF, WebP, JPEG)으로 준비하고, 브라우저가 지원하는 가장 작은 것을 고르게 합니다. 이미지 서버가 요청 순간에 변환하면 첫 요청이 느려, 많이 쓰는 크기는 미리 만들어 둡니다.

## 스토어프론트 FE-상5. 화면 오류 수집과 재현
<!--meta: sec=s39; dept=FE; level=신입|주니어|시니어; ct_band=상; related=INC-WEB-03-->
사용자 화면에서 난 스크립트 오류를 모아 배포 버전·브라우저별로 묶습니다. 압축된 코드의 오류 위치를 원래 코드로 되돌리는 소스맵은 외부에 공개하지 않고 수집 서버에만 둡니다. 오류 직전 사용자의 클릭 순서(개인정보 제외)를 함께 남겨 재현을 돕습니다.

## 스토어프론트 BE-하5. 요청 제한
<!--meta: sec=s40; dept=BE; level=신입|주니어; ct_band=하; related=INC-WEB-04-->
한 IP나 기기가 짧은 시간에 너무 많이 요청하면 BFF가 429로 거절합니다. 토큰 버킷 방식으로 초당 일정량은 허용하고 순간적인 몰림은 버킷 크기만큼 받아 줍니다. 회사 사무실처럼 여러 사람이 같은 IP를 쓰는 곳은 로그인 사용자 기준으로 따로 셉니다.

## 스토어프론트 BE-중5. 화면 구성 미리보기
<!--meta: sec=s41; dept=BE|FE; level=신입|주니어|시니어; ct_band=중; related=PRJ-WEB-2-->
운영자가 홈 구성을 바꾸면 바로 모든 사용자에게 나가지 않고, 미리보기 주소에서 먼저 확인합니다. 미리보기 구성은 버전 번호를 붙여 저장하고, 게시하면 그 버전을 현재 버전으로 가리키게 바꿉니다. 문제가 생기면 이전 버전으로 바로 되돌립니다.

## 스토어프론트 BE-상5. BFF 응답 크기 줄이기
<!--meta: sec=s42; dept=BE; level=신입|주니어|시니어; ct_band=상; related=ISS-WEB-02-->
상품 상세 응답이 180KB로 커서 느린 통신에서 늦었습니다. 화면이 쓰지 않는 필드를 찾으려 화면 코드의 필드 사용을 분석해 30%를 덜어냈고, 화면이 필요한 필드를 요청에 적어 보내는 방식(필드 선택)을 도입하고 있습니다.

## 스토어프론트 FE-중6. 화면 다국어와 글자 길이

상품 상세 주소는 /products/{상품 ID} 하나로 정하고, 옵션·추적 파라미터가 붙은 주소도 대표 주소(canonical)를 알려 검색 엔진에 중복 페이지로 잡히지 않게 합니다. 판매 종료 상품은 404 대신 "판매 종료" 화면과 비슷한 상품을 보여 줍니다.
