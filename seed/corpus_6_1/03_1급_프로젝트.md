# 페이브릿지 — 1급 핵심 설계
<!--meta: doc=PRJ-PAY-1; doc_type=project; tier=1; topic=PAY; disclosure=abstract; status=ongoing; stages=2차-->

## 페이브릿지 핵심 설계 안내
<!--meta: sec=ov; dept=BE|FE|EMB; level=시니어; ct_band=상; related=RES-PAY-01|RES-PAY-02|RES-PAY-03|ISS-PAY-01|ISS-PAY-02|ISS-PAY-03-->
다음 해 결제량 3배 증가와 해외 결제 지원을 앞두고 진행 중인 핵심 설계입니다. 아직 결정되지 않은 부분이 많아 선택지와 판단 기준을 함께 적습니다.

## 1. 다중 리전 승인 구조
<!--meta: sec=s1; dept=BE; level=시니어; ct_band=상; related=RES-PAY-01|ISS-PAY-01-->
<!--forbid: PB-Core-->
한 리전이 통째로 멈춰도 결제가 계속되도록 두 리전에서 승인을 받는 구조를 설계하고 있습니다. 어려운 점은 결제 원장의 일관성입니다. 두 리전이 같은 결제를 동시에 승인하면 안 되므로, 결제 ID를 리전에 고정 배정하고 리전 장애 때만 다른 리전이 넘겨받는 방식을 검토 중입니다.
넘겨받는 순간 아직 복제되지 않은 결제가 있을 수 있어, 카드사 승인 조회로 "실제로 승인됐는지"를 확인한 뒤 원장을 맞추는 절차가 필요합니다.

## 2. 실시간 이상 결제 차단
<!--meta: sec=s2; dept=BE|EMB; level=시니어; ct_band=상; related=RES-PAY-02|ISS-PAY-03-->
지금은 이중 승인과 오프라인 승인 악용을 사후(매시간)로만 찾습니다. 승인 직전 50ms 안에 위험 점수를 계산해 막는 구조로 바꾸려 합니다. 카드 해시·기기·매장 사이의 연결을 그래프로 유지하고, 새 결제가 들어오면 연결된 묶음의 최근 거래를 보고 점수를 냅니다.
오프라인 단말 거래는 승인 순간 서버를 거치지 않아 이 방식으로 막을 수 없어, 단말 안에 간단한 규칙을 넣는 방안도 함께 봅니다.

## 3. 결제창 공통 모듈화
<!--meta: sec=s3; dept=FE; level=시니어; ct_band=상; related=RES-PAY-03|ISS-PAY-02-->
새벽마켓 외에 다른 서비스(상담 채팅 안 결제, 매장 키오스크)도 결제창을 쓰게 되어, 결제창을 화면과 상태 기계로 분리한 공통 모듈로 만들고 있습니다. 화면은 서비스마다 다르게 그리고, 상태 전이·서버 통신·오류 처리만 공통으로 씁니다.
키오스크는 터치 전용이고 낭독기 지원이 필수라, 보안 키패드와 접근성 문제를 여기서 함께 풀어야 합니다.

# 파인드 — 1급 핵심 설계
<!--meta: doc=PRJ-SRC-1; doc_type=project; tier=1; topic=SRC; disclosure=abstract; status=ongoing; stages=2차-->

## 파인드 핵심 설계 안내
<!--meta: sec=ov; dept=BE|AI|DATA; level=시니어; ct_band=상; related=RES-SRC-01|RES-SRC-02|ISS-SRC-01|ISS-SRC-02|ISS-SRC-03-->
대화형 검색 도입과 검색·추천 통합을 앞두고 진행 중인 설계입니다. 결정되지 않은 선택지와 기준을 함께 적습니다.

## 1. 검색과 추천을 하나의 순위 단계로
<!--meta: sec=s1; dept=AI|BE; level=시니어; ct_band=상; related=RES-SRC-01|ISS-SRC-01-->
지금은 검색 순위 모델과 추천 순위 모델이 따로 있어 피처와 운영이 두 배입니다. 검색어가 있으면 검색어 피처를, 없으면 비워 두는 하나의 순위 모델로 합치는 설계를 검토합니다. 문제는 지연입니다. 추천은 후보가 500개라 검색(200개)보다 재정렬 비용이 커서, 후보 수를 줄이는 1단계 모델이 따로 필요할 수 있습니다.

## 2. 대화형 검색 (LLM 질의 재작성)
<!--meta: sec=s2; dept=AI|BE; level=시니어; ct_band=상; related=RES-SRC-02|ISS-SRC-03-->
"3만 원 이하 캠핑용 의자 중에 가벼운 거"처럼 조건이 섞인 검색어를 LLM이 구조화된 질의(카테고리, 가격 범위, 속성)로 바꿔 엔진에 보내는 기능을 만들고 있습니다. LLM 호출이 300~800ms라 검색 예산을 넘어, 조건이 섞인 검색어만 골라 LLM을 부르고 결과는 캐시합니다.
LLM이 없는 속성을 만들어 내면 결과가 0개가 되어, 속성 값은 카탈로그에 있는 값으로만 고르게 제한합니다.

## 3. 데이터 파이프라인 비용 줄이기
<!--meta: sec=s3; dept=DATA; level=시니어; ct_band=상; related=ISS-SRC-01|RES-SRC-01-->
학습 데이터 생성과 피처 계산에 하루 클러스터 비용의 40%가 듭니다. 노출 로그를 표본(클릭 없는 노출의 10%만)으로 줄이고 가중치로 보정하는 방법, 피처를 증분으로만 계산하는 방법을 비교하고 있습니다. 표본을 줄이면 드문 검색어의 학습 데이터가 너무 적어지는 것이 걱정입니다.

## 4. 이미지로 검색
<!--meta: sec=s4; dept=AI|BE; level=시니어; ct_band=상; related=RES-SRC-03|ISS-SRC-04-->
사진을 찍어 비슷한 상품을 찾는 기능을 설계합니다. 상품 이미지 1,200만 장의 벡터를 근사 최근접 이웃 인덱스에 두고, 사용자 사진에서 상품 부분만 잘라 벡터를 만듭니다. 배경·조명 차이를 어떻게 줄일지가 과제입니다.

# 톡허브 — 1급 핵심 설계
<!--meta: doc=PRJ-CHT-1; doc_type=project; tier=1; topic=CHT; disclosure=abstract; status=ongoing; stages=2차-->

## 톡허브 핵심 설계 안내
<!--meta: sec=ov; dept=BE|FE|AI; level=시니어; ct_band=상; related=RES-CHT-01|RES-CHT-02|ISS-CHT-01|ISS-CHT-02|ISS-CHT-03-->
상담 자동화 비율을 40%에서 70%로 올리고, 동시 연결 100만을 견디는 구조를 목표로 하는 설계입니다.

## 1. 도구를 쓰는 상담 에이전트
<!--meta: sec=s1; dept=AI|BE; level=시니어; ct_band=상; related=RES-CHT-01|ISS-CHT-02-->
챗봇이 주문 조회·배송 조회·교환 접수·환불 접수 도구를 직접 부르는 상담 에이전트를 설계하고 있습니다. 조회 도구는 바로 부르고, 되돌리기 어려운 도구는 구매자 확인 단계를 반드시 거칩니다. 도구 호출이 틀렸을 때 누가 책임지는지, 상담원에게 언제 넘기는지 기준을 정해야 합니다.

## 2. 연결 계층 다중화
<!--meta: sec=s2; dept=BE; level=시니어; ct_band=상; related=RES-CHT-02|ISS-CHT-01-->
연결 위치를 기록하는 Redis가 단일 장애 지점이라, 연결 위치 정보를 연결 서버끼리 나눠 갖는 구조(일관된 해싱으로 사용자를 서버에 고정)를 검토합니다. 서버가 늘거나 줄 때 다시 붙어야 하는 사용자 수를 줄이는 것이 관건입니다.

## 3. 상담원 화면 공통 모듈
<!--meta: sec=s3; dept=FE; level=시니어; ct_band=상; related=ISS-CHT-03-->
상담원 화면을 판매자 상담, 매장 상담에도 쓰려고 대화 목록·메시지·추천 답변을 공통 모듈로 나누고 있습니다. 서비스마다 다른 고객 정보 칸을 끼워 넣을 수 있게 하고, 단축키·접근성 규칙은 공통으로 지킵니다.

## 4. 음성 상담 연결
<!--meta: sec=s4; dept=AI|BE; level=시니어; ct_band=상; related=RES-CHT-03|ISS-CHT-04-->
전화 상담도 같은 상담원 화면에서 받도록, 통화를 실시간 STT로 글로 바꿔 채팅 대화처럼 쌓는 구조를 설계합니다. 상담 요약·추천 답변을 그대로 쓸 수 있지만, STT 오류가 요약에 섞이는 문제가 있습니다.

# 레이크하우스 — 1급 핵심 설계
<!--meta: doc=PRJ-DWH-1; doc_type=project; tier=1; topic=DWH; disclosure=abstract; status=ongoing; stages=2차-->

## 레이크하우스 핵심 설계 안내
<!--meta: sec=ov; dept=DATA|BE; level=시니어; ct_band=상; related=RES-DWH-01|RES-DWH-02|ISS-DWH-01|ISS-DWH-02|ISS-DWH-03-->
배치 중심 플랫폼을 준실시간(1분 지연)으로 바꾸고, 지표를 한곳에서 정의하는 구조를 목표로 하는 설계입니다.

## 1. 스트리밍 레이크하우스
<!--meta: sec=s1; dept=DATA|BE; level=시니어; ct_band=상; related=RES-DWH-01|ISS-DWH-01-->
Flink로 CDC를 받아 1분마다 Iceberg에 커밋하는 구조를 시험 중입니다. 커밋이 잦을수록 작은 파일과 스냅샷이 늘어, 쓰기와 정리를 함께 설계해야 합니다. 정확히 한 번 반영을 보장하려면 Flink 체크포인트와 Iceberg 커밋을 묶어야 합니다.

## 2. 시맨틱 계층
<!--meta: sec=s2; dept=BE|DATA; level=시니어; ct_band=상; related=RES-DWH-02|ISS-DWH-02-->
매출·전환율 같은 지표 정의 200여 개를 한곳에 모으고, 대시보드·API·LLM 질의 도구가 모두 이 정의를 쓰게 합니다. 정의가 바뀌면 과거 숫자도 바뀌어, 정의에 버전을 두고 어느 버전으로 계산했는지 화면에 표시하는 방안을 봅니다.

## 3. 피처 정의 하나로 합치기
<!--meta: sec=s3; dept=AI|DATA; level=시니어; ct_band=상; related=RES-DWH-03|ISS-DWH-04-->
학습(레이크 SQL)과 서비스(실시간 코드)에서 같은 피처를 따로 계산하는 문제를 없애려고, 피처를 한 번 정의하면 배치·스트리밍 둘 다로 바꿔 실행하는 구조를 설계합니다. 모든 피처를 이 방식으로 표현할 수 있는지가 관건입니다.

# 팩토리아이 — 1급 핵심 설계
<!--meta: doc=PRJ-IOT-1; doc_type=project; tier=1; topic=IOT; disclosure=abstract; status=ongoing; stages=2차-->

## 팩토리아이 핵심 설계 안내
<!--meta: sec=ov; dept=EMB|DATA|AI|BE; level=시니어; ct_band=상; related=RES-IOT-01|RES-IOT-02|ISS-IOT-01|ISS-IOT-02|ISS-IOT-03-->
물류센터 2곳을 새로 짓는 계획에 맞춰, 고장 예측을 정비 일정과 분류기 제어까지 이어 붙이는 설계입니다.

## 1. 예측 정비 통합
<!--meta: sec=s1; dept=AI|BE; level=시니어; ct_band=상; related=RES-IOT-01|ISS-IOT-01-->
남은 수명 예측 → 정비 일정 계산 → 부품 재고 확인 → 작업 배정을 자동으로 잇는 구조입니다. 예측이 틀렸을 때 일정이 크게 흔들리지 않도록, 확실한 것만 확정하고 나머지는 후보로 두는 단계식 일정을 검토합니다.

## 2. 고장 구간 자동 우회
<!--meta: sec=s2; dept=EMB|BE; level=시니어; ct_band=상; related=RES-IOT-02|ISS-IOT-02-->
설비 이상이 예측되면 정비 전에 그 구간을 덜 쓰도록 분류기 경로 가중치를 미리 바꾸는 방안입니다. 제어기와 서버의 판단이 다를 때 누구를 따를지, 잘못 우회했을 때 처리량 손실을 어떻게 제한할지 정해야 합니다.

## 3. 센터 간 모델 공유
<!--meta: sec=s3; dept=AI|DATA; level=시니어; ct_band=상; related=RES-IOT-01|ISS-IOT-01-->
새 센터는 고장 기록이 없어, 기존 센터 모델을 가져와 새 센터 데이터로 조금씩 맞추는 방식을 씁니다. 설비 모델이 같아도 설치 환경(온도, 바닥 진동)이 달라 얼마나 다시 학습해야 하는지가 과제입니다.

# 스토어프론트 — 1급 핵심 설계
<!--meta: doc=PRJ-WEB-1; doc_type=project; tier=1; topic=WEB; disclosure=abstract; status=ongoing; stages=2차-->

## 스토어프론트 핵심 설계 안내
<!--meta: sec=ov; dept=FE|BE; level=시니어; ct_band=상; related=RES-WEB-01|ISS-WEB-01|ISS-WEB-02-->
웹과 앱 화면을 하나의 화면 구성 체계로 합치고, 첫 화면을 1초 안에 보여 주는 것을 목표로 하는 설계입니다.

## 1. 서버 주도 화면 (Server-Driven UI)
<!--meta: sec=s1; dept=FE|BE; level=시니어; ct_band=상; related=RES-WEB-01|ISS-WEB-01-->
앱 배포 없이 화면을 바꾸려고, 화면 구성 API가 조각 종류·순서·데이터까지 내려주고 웹·앱은 조각 렌더러만 갖는 구조를 넓히고 있습니다. 조각 종류가 늘면 앱 렌더러도 늘어야 하고, 옛 앱이 모르는 조각을 어떻게 대체할지 규칙이 필요합니다.

## 2. 엣지 우선 렌더링
<!--meta: sec=s2; dept=BE|FE; level=시니어; ct_band=상; related=RES-WEB-01|ISS-WEB-02-->
공통 틀은 엣지에서 캐시된 것을 바로 보내고, 개인화 조각만 BFF에서 받아 끼우는 구조입니다. 엣지와 BFF 사이 지연, 개인 응답이 캐시되는 사고를 막는 검사가 핵심입니다.

## 3. 데이터로 화면 배치 자동화
<!--meta: sec=s3; dept=DATA|FE|BE; level=시니어; ct_band=상; related=RES-WEB-02|ISS-WEB-03-->
운영자가 정하던 홈 조각 순서를 조각 성과 데이터로 자동 추천하는 구조입니다. 위치 효과를 뺀 조각 매력, 사용자 그룹별 반응, 행사 우선순위를 함께 고려하고, 자동 배치가 이상하면 운영자가 언제든 고정할 수 있게 합니다.
