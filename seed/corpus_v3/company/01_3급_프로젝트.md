# 루미스캔 — 3급 프로젝트 문서

## 루미스캔 문서 안내
<!--meta: sec=ov; dept=AI|BE|FE; level=신입|주니어|시니어; ct_band=하-->
이 문서는 새벽소프트 의료AI사업부의 루미스캔 프로젝트를 처음 접하는 사람을 위한 3급(공개 수준) 문서입니다. 시스템의 목적과 구성, 부서별 역할, 그리고 각 부서가 다루는 기본 기술을 난이도별로 정리했습니다. 고객 병원 이름, 내부 성능 수치, 장애 기록은 2급 문서에서 다룹니다.

루미스캔은 병원 영상의학과에서 흉부 X-ray를 판독할 때, 이상 소견이 의심되는 영상을 먼저 표시해 판독 순서를 정하도록 돕는 소프트웨어입니다. 최종 판독은 항상 영상의학과 전문의가 하며, 루미스캔은 "판독 보조"로만 쓰입니다. 분류 대상은 결절, 폐렴성 음영, 기흉, 흉수, 심비대의 다섯 가지 소견입니다.

## 루미스캔 1. 시스템 구성
<!--meta: sec=s1; dept=AI|BE|FE; level=신입|주니어; ct_band=하-->
루미스캔은 네 부분으로 이루어집니다.

첫째, 영상 수집기입니다. 병원의 영상 저장 시스템(PACS)에서 새로 촬영된 흉부 X-ray를 받아 옵니다. 의료 영상은 DICOM이라는 표준 형식으로 저장되며, 영상 데이터와 함께 환자 정보, 촬영 장비, 촬영 방향 같은 정보가 태그로 들어 있습니다.

둘째, 추론 서버입니다. 받은 영상을 전처리한 뒤 분류 모델에 넣어 다섯 가지 소견 각각의 확률을 계산합니다. 모델이 영상의 어느 부분을 보고 판단했는지 보여 주는 히트맵도 함께 만듭니다.

셋째, 결과 API 서버입니다. 추론 결과를 저장하고, 판독 화면과 병원 시스템이 결과를 조회할 수 있는 API를 제공합니다.

넷째, 판독 보조 뷰어입니다. 영상의학과 전문의가 쓰는 웹 화면으로, 판독 대기 목록을 의심 소견 우선순위대로 보여 주고 영상 위에 히트맵을 겹쳐 표시합니다.

## 루미스캔 2. 부서별 역할
<!--meta: sec=s2; dept=AI|BE|FE; level=신입|주니어|시니어; ct_band=하-->
| 부서 | 맡는 부분 | 주요 기술 |
| --- | --- | --- |
| AI연구팀 | 분류 모델 학습과 평가, 히트맵 생성 | PyTorch, 합성곱 신경망, 데이터 증강 |
| 백엔드플랫폼팀 | 영상 수집기, 추론 서버 운영, 결과 API | Python(FastAPI), 작업 대기열, PostgreSQL, 객체 저장소 |
| 프론트엔드팀 | 판독 보조 뷰어 | TypeScript, React, Canvas/WebGL 영상 표시 |

세 부서가 만나는 지점은 두 곳입니다. 하나는 "모델이 받는 영상의 형식"으로, AI연구팀이 학습할 때 쓴 전처리와 백엔드가 서비스에서 쓰는 전처리가 정확히 같아야 합니다. 다른 하나는 "히트맵의 좌표"로, 백엔드가 저장한 히트맵을 프론트엔드가 원본 영상 위에 같은 방향과 크기로 겹쳐야 합니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.1 영상 전처리 (하)
<!--meta: sec=s3; dept=AI|BE; level=신입; ct_band=하-->
X-ray 원본은 보통 12비트나 16비트 흑백 영상이고, 장비마다 밝기 범위가 다릅니다. 모델에 넣기 전에 세 단계를 거칩니다. 먼저 DICOM 태그의 창 중심과 창 너비 값으로 밝기 범위를 잘라 사람이 보는 영상과 비슷하게 만듭니다. 다음으로 영상 크기를 512×512로 맞추되, 가로세로 비율이 달라지지 않도록 짧은 쪽에 여백을 붙입니다. 마지막으로 픽셀 값을 0과 1 사이로 정규화합니다. 촬영 방향 태그를 읽어 영상이 뒤집혀 있으면 바로잡는 단계도 이때 들어갑니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.2 클래스 불균형 다루기 (중)
<!--meta: sec=s4; dept=AI; level=주니어; ct_band=중-->
실제 병원 영상의 대부분은 정상입니다. 기흉처럼 드문 소견은 전체의 1~2%에 불과해, 아무 처리 없이 학습하면 모델이 "모두 정상"이라고 답해도 정확도가 높게 나옵니다. 그래서 정확도 대신 소견별 민감도와 특이도, ROC 곡선 아래 면적(AUROC)으로 평가합니다. 학습에서는 드문 소견의 손실에 가중치를 더 주거나, 드문 소견 영상을 더 자주 뽑는 방식을 씁니다. 회전, 밝기 변화, 작은 이동 같은 데이터 증강도 함께 쓰지만, 좌우 반전은 쓰지 않습니다. 심장 위치처럼 좌우가 의미를 가지는 소견이 있기 때문입니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.3 히트맵과 판단 근거 (상)
<!--meta: sec=s5; dept=AI; level=주니어|시니어; ct_band=상-->
판독의는 모델이 왜 그렇게 판단했는지 확인하고 싶어 합니다. 루미스캔은 모델의 마지막 합성곱 층에서 소견별로 어느 영역이 판단에 크게 작용했는지 계산해 히트맵으로 보여 줍니다. 히트맵은 편리하지만 오해도 낳습니다. 모델이 병변이 아니라 영상 구석의 병원 표식이나 튜브 같은 기구를 보고 판단했을 때도 히트맵은 그럴듯하게 그려지기 때문입니다. 그래서 AI연구팀은 히트맵이 실제 병변 위치와 얼마나 겹치는지를 별도 지표로 확인합니다.

## 루미스캔 4. 백엔드플랫폼팀의 기본 기술 > 4.1 영상 수집과 업로드 API (하)
<!--meta: sec=s6; dept=BE; level=신입; ct_band=하-->
영상 수집기는 PACS에서 새 영상이 도착했다는 알림을 받으면 DICOM 파일을 내려받아 객체 저장소에 올리고, 영상 ID와 저장 위치를 데이터베이스에 기록합니다. 같은 영상이 두 번 도착하는 일이 흔해서, 영상마다 고유한 식별자(SOP Instance UID)를 기준으로 이미 받은 영상인지 먼저 확인합니다. 업로드 API는 파일 크기 제한, DICOM 형식 검증, 필수 태그 존재 여부를 검사한 뒤에만 영상을 받습니다.

## 루미스캔 4. 백엔드플랫폼팀의 기본 기술 > 4.2 비동기 추론 대기열 (중)
<!--meta: sec=s7; dept=BE; level=주니어; ct_band=중-->
추론은 영상 한 장에 수백 밀리초가 걸리고, 아침 시간에는 영상이 몰려 들어옵니다. 그래서 업로드 요청이 추론을 직접 기다리지 않고, 추론 작업을 대기열에 넣은 뒤 바로 응답합니다. 추론 작업자는 대기열에서 작업을 꺼내 처리하고 결과를 저장합니다. 작업자가 처리 중에 죽으면 작업이 사라지지 않도록, 처리가 끝났다는 확인을 보낸 뒤에만 대기열에서 지웁니다. 응급실 영상은 별도의 우선 대기열로 보내 일반 영상보다 먼저 처리합니다.

## 루미스캔 4. 백엔드플랫폼팀의 기본 기술 > 4.3 추론 서버 성능 (상)
<!--meta: sec=s8; dept=BE|AI; level=주니어|시니어; ct_band=상-->
GPU 한 장으로 여러 영상을 동시에 처리하려면 영상을 묶어서(배치) 모델에 넣어야 합니다. 그런데 묶음이 찰 때까지 기다리면 첫 영상의 응답이 늦어집니다. 루미스캔은 "묶음이 차거나, 정해진 대기 시간이 지나면" 바로 처리하는 방식으로 두 목표를 함께 맞춥니다. 학습에 쓴 모델 파일을 서비스용 형식으로 변환하고 계산 정밀도를 낮춰 속도를 올리는 작업도 하는데, 이때 변환 전후의 예측 결과가 허용 범위 안에서 같은지 반드시 검사합니다.

## 루미스캔 5. 프론트엔드팀의 기본 기술 > 5.1 판독 대기 목록 (하)
<!--meta: sec=s9; dept=FE; level=신입; ct_band=하-->
판독 대기 목록은 아직 판독되지 않은 영상을 의심 소견의 확률이 높은 순서로 보여 줍니다. 각 행에는 촬영 시각, 촬영 부위, 가장 높은 소견과 그 확률이 표시됩니다. 응급 영상은 확률과 관계없이 맨 위에 고정합니다. 목록은 새 결과가 나올 때마다 갱신되지만, 판독의가 보고 있는 행이 갑자기 아래로 밀려나지 않도록, 마우스가 목록 위에 있는 동안에는 순서 갱신을 잠시 멈춥니다.

## 루미스캔 5. 프론트엔드팀의 기본 기술 > 5.2 영상 위 히트맵 겹치기 (중)
<!--meta: sec=s10; dept=FE; level=주니어; ct_band=중-->
히트맵은 모델 입력 크기(512×512)로 만들어지지만, 원본 영상은 보통 2000~3000픽셀입니다. 뷰어는 히트맵을 원본 크기로 늘리고, 전처리에서 붙였던 여백만큼 위치를 되돌려 맞춘 뒤 반투명하게 겹칩니다. 판독의가 영상을 확대하거나 이동하면 히트맵도 같은 변환을 따라가야 합니다. 히트맵은 켜고 끌 수 있어야 하고, 기본값은 꺼짐입니다. 판독의가 먼저 자기 눈으로 본 뒤 모델 판단을 확인하도록 하기 위해서입니다.

## 루미스캔 5. 프론트엔드팀의 기본 기술 > 5.3 대용량 영상 표시 (상)
<!--meta: sec=s11; dept=FE; level=주니어|시니어; ct_band=상-->
판독의는 하루에 수백 장을 보며, 다음 영상으로 넘어갈 때 기다리는 시간을 매우 싫어합니다. 뷰어는 목록의 다음 영상 몇 장을 미리 받아 두고, 원본 전체를 한 번에 그리는 대신 화면에 보이는 영역만 먼저 그립니다. 밝기와 대비를 바꾸는 창 조절은 영상 픽셀을 매번 다시 계산해야 하므로 GPU에서 처리합니다. 영상을 오래 띄워 두면 메모리가 계속 늘어날 수 있어, 지나간 영상의 메모리를 정리하는 규칙이 중요합니다.

## 루미스캔 6. 용어
<!--meta: sec=s12; dept=AI|BE|FE; level=신입|주니어|시니어; ct_band=하-->
- PACS: 병원의 의료 영상 저장·전송 시스템
- DICOM: 의료 영상의 표준 파일 형식과 통신 규약. 영상과 함께 환자, 장비, 촬영 방향 정보를 태그로 담는다
- 창 조절(windowing): 넓은 밝기 범위 중 보고 싶은 구간만 화면 밝기에 대응시키는 처리
- 민감도: 실제 이상 영상 중 모델이 이상으로 판단한 비율
- 특이도: 실제 정상 영상 중 모델이 정상으로 판단한 비율
- AUROC: 판정 기준을 바꿔 가며 민감도와 특이도의 관계를 그린 곡선 아래 면적. 1에 가까울수록 좋다

## 루미스캔 3. AI연구팀의 기본 기술 > 3.4 성능 지표 읽기 (하)
<!--meta: sec=s13; dept=AI; level=신입; ct_band=하-->
판독 보조 모델은 정확도 하나로 평가하지 않습니다. 소견마다 AUROC를 보고, 실제 운영 기준값에서의 민감도(놓치지 않는 비율)와 특이도(정상을 정상으로 보는 비율)를 함께 적습니다. 이상 비율이 낮은 소견은 정확도가 높아도 쓸모없는 모델일 수 있기 때문입니다. 신입은 혼동 행렬에서 네 칸의 뜻을 설명하고, 기준값을 바꿀 때 민감도와 특이도가 어떻게 움직이는지 그림으로 보여 줄 수 있어야 합니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.5 데이터 증강의 기본 (하)
<!--meta: sec=s14; dept=AI; level=신입; ct_band=하-->
학습 영상에 작은 회전, 이동, 밝기 변화를 주어 모델이 촬영 자세나 노출 차이에 덜 흔들리게 합니다. 흉부 영상은 좌우 뒤집기를 쓰지 않습니다. 심장 위치처럼 좌우가 의미를 가지는 구조가 있기 때문입니다. 증강은 학습 데이터에만 적용하고, 검증·시험 데이터에는 적용하지 않습니다. 어떤 증강을 왜 넣고 왜 뺐는지 실험 기록에 남기는 것이 팀 규칙입니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.6 확률 보정과 기준값 고르기 (중)
<!--meta: sec=s15; dept=AI; level=주니어; ct_band=중-->
모델이 0.8이라고 낸 영상 중 실제로 80% 정도가 이상이어야 판독의가 확률을 믿을 수 있습니다. 학습이 끝난 뒤 검증 데이터로 온도 조정 같은 보정을 하고, 보정 곡선과 보정 오차를 함께 기록합니다. 기준값은 소견마다 민감도 목표를 먼저 정하고 그 목표를 맞추는 값으로 고릅니다. 보정 전후에 기준값을 다시 골라야 하는 이유를 설명할 수 있어야 합니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.7 라벨 품질 점검 (중)
<!--meta: sec=s16; dept=AI|DATA; level=주니어; ct_band=중-->
학습 라벨에는 오류가 섞여 있습니다. 모델 예측과 라벨이 크게 어긋나는 영상, 같은 환자의 비슷한 영상인데 라벨이 다른 경우를 모아 판독의에게 다시 확인받습니다. 다시 확인한 라벨은 원래 라벨을 덮어쓰지 않고 버전을 붙여 따로 저장해, 어떤 라벨로 학습했는지 언제든 재현할 수 있게 합니다.

## 루미스캔 3. AI연구팀의 기본 기술 > 3.8 모델 경량화와 변환 검증 (상)

추론 속도를 높이거나 작은 장치에 올리려면 모델을 낮은 정밀도로 바꾸거나 일부 연산을 합칩니다. 변환 뒤에는 평균 지표만 보지 않고, 소견별로 판정이 바뀐 영상의 비율과 기준값 근처 영상의 변화를 따로 봅니다. 변환 결과를 배포할 때는 이전 모델로 바로 되돌릴 수 있게 두 버전을 함께 유지합니다. 시니어는 어떤 시험 세트로 변환을 승인할지 기준을 세울 수 있어야 합니다.

## 루미스캔 4. 백엔드플랫폼팀의 기본 기술 > 4.4 DICOM 태그 검사와 오류 응답 (하)

영상이 들어오면 환자 식별자, 촬영 부위, 촬영 방향, 영상 크기 같은 필수 태그를 먼저 검사합니다. 빠진 태그가 있으면 추론 작업을 만들지 않고, 어떤 태그가 없는지 오류 코드와 함께 돌려줍니다. 오류 응답의 형식을 통일해 두면 병원 쪽 담당자와 장치 쪽 담당자가 같은 표를 보고 원인을 찾을 수 있습니다.

## 루미스캔 5. 프론트엔드팀의 기본 기술 > 5.6 밝기·대비 조절 도구 (중)

판독의는 영상의 밝기와 대비를 마우스로 끌어 바꿉니다. 원본 픽셀 값은 그대로 두고 화면에 그릴 때만 변환해야 히트맵 위치와 측정값이 흔들리지 않습니다. 변환은 GPU에서 처리해 끄는 동안에도 끊김이 없게 하고, 소견별로 자주 쓰는 설정을 저장해 두었다가 한 번에 불러옵니다.

## 루미스캔 5. 프론트엔드팀의 기본 기술 > 5.7 웹 워커로 영상 디코딩 (상)

## 루미스캔 7. 촬영실 영상 게이트웨이 장치 > 7.1 장치 구성과 부팅 (하)

병원 촬영실마다 작은 게이트웨이 장치를 두어, 촬영 장비에서 나온 영상을 받아 클라우드로 보냅니다. 장치는 리눅스 기반 보드와 저장 장치로 이루어져 있고, 전원이 들어오면 네트워크 설정을 확인한 뒤 영상 수신 프로그램을 자동으로 띄웁니다. 신입은 부팅 순서와 서비스 자동 시작 설정을 설명할 수 있어야 합니다.

<!--meta: sec=s31; dept=EMB; level=주니어; ct_band=중-->
장치가 병원마다 흩어져 있어 업데이트는 원격으로 합니다. 새 버전은 일부 장치에 먼저 배포해 하루 동안 지켜본 뒤 나머지에 배포합니다. 업데이트 파일은 서명을 확인한 뒤에만 설치하고, 촬영이 적은 밤 시간에만 재시작합니다.

## 루미스캔 7. 촬영실 영상 게이트웨이 장치 > 7.6 장치 위 경량 추론과 열 관리 (상)

응급 영상은 클라우드 결과를 기다리지 않도록 장치에서 가벼운 모델로 먼저 선별하는 기능을 시험하고 있습니다. 작은 보드에서 추론을 계속 돌리면 온도가 올라 처리 속도가 떨어지므로, 온도와 처리량을 함께 기록하고 일정 온도를 넘으면 장치 추론을 멈추고 클라우드로 넘깁니다. 시니어는 장치 결과와 클라우드 결과가 다를 때의 처리 규칙을 정할 수 있어야 합니다.

## 루미스캔 7. 촬영실 영상 게이트웨이 장치 > 7.7 업데이트 실패 시 되돌리기 (상)

장치 저장 공간을 두 구역으로 나눠, 새 버전은 쓰지 않는 구역에 설치하고 그 구역으로 부팅합니다. 부팅 뒤 일정 시간 안에 상태 보고가 성공하지 않으면 자동으로 이전 구역으로 돌아갑니다. 병원 현장에 사람이 가지 않고도 복구되게 만드는 것이 목표입니다.

## 스카이패스 문서 안내
<!--meta: sec=ov; dept=AI|EMB|BE|FE; level=신입|주니어|시니어; ct_band=하-->
스카이패스는 새벽소프트 로보틱스사업부가 만든 실내 설비 점검 드론 시스템입니다. 물류 창고와 공장처럼 GPS 신호가 닿지 않는 실내에서, 드론이 정해진 경로를 스스로 비행하며 계기판, 배관, 선반 상태를 촬영하고 이상 징후를 찾아냅니다. 이 문서는 시스템을 처음 접하는 사람을 위한 3급(공개 수준) 문서이며, 고객사 이름과 운영 기록은 2급 문서에서 다룹니다.

## 스카이패스 1. 시스템 구성
<!--meta: sec=s1; dept=AI|EMB|BE|FE; level=신입|주니어; ct_band=하-->
스카이패스는 네 부분으로 이루어집니다. 드론 본체에는 비행 제어기, 카메라 두 대, 관성 측정 장치(IMU), 거리 센서가 실려 있습니다. 기체 위의 온보드 컴퓨터는 위치 추정과 장애물 회피를 실시간으로 계산합니다. 지상의 임무 서버는 점검 임무를 만들어 드론에 내려 보내고, 드론이 보내는 텔레메트리(위치, 배터리, 상태)와 촬영 영상을 받아 저장합니다. 관제 웹 화면은 운영자가 드론의 위치와 상태를 실시간으로 보고, 점검 결과를 확인하는 화면입니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.1 좌표계 (하)
<!--meta: sec=s2; dept=EMB|AI|FE; level=신입|주니어; ct_band=하-->
드론 시스템에는 좌표계가 여러 개 있습니다. 카메라 좌표계는 카메라 렌즈를 기준으로, 기체 좌표계는 드론의 앞·오른쪽·아래를 기준으로, 지도 좌표계는 창고 바닥의 한 지점을 원점으로 합니다. 비행 제어 쪽은 북-동-아래(NED) 방향을, 지도와 3D 화면 쪽은 동-북-위(ENU) 방향을 쓰는 경우가 많아, 두 방식 사이를 바꿀 때 축 순서와 부호를 정확히 맞추어야 합니다. 스카이패스는 모든 변환을 한 곳의 변환 모듈에서만 하도록 정해 두었습니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.2 실내 위치 추정 (중)
<!--meta: sec=s3; dept=AI|EMB; level=주니어; ct_band=중-->
실내에서는 GPS를 쓸 수 없어, 카메라 영상과 관성 측정 장치의 값을 함께 써서 위치를 추정합니다. 영상에서 특징점을 찾아 프레임 사이의 움직임을 계산하고, 관성 측정 장치의 가속도와 회전 속도로 그 사이를 메웁니다. 이렇게 구한 위치는 시간이 지날수록 오차가 조금씩 쌓이므로, 창고 기둥에 붙여 둔 표식(AprilTag)을 지날 때마다 위치를 바로잡습니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.3 장애물 회피와 안전 착륙 (상)
<!--meta: sec=s4; dept=EMB|AI; level=주니어|시니어; ct_band=상-->
드론은 경로 위에 예상하지 못한 장애물(지게차, 사람, 새로 놓인 짐)이 나타나면 멈추고 피해 가는 경로를 다시 계산합니다. 거리 센서와 카메라의 장애물 정보를 기체 주변의 작은 3차원 격자 지도에 표시하고, 격자 위에서 짧은 우회 경로를 찾습니다. 위치 추정이 불안정해지거나 배터리가 정해진 값 아래로 떨어지면, 임무를 멈추고 가장 가까운 안전 지점에 착륙합니다. 안전 기능은 온보드 컴퓨터가 멈추더라도 비행 제어기 혼자 동작해야 합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.1 텔레메트리 수집 (하)
<!--meta: sec=s5; dept=BE; level=신입; ct_band=하-->
드론은 위치와 배터리, 상태 값을 초당 10번 MQTT로 보냅니다. MQTT는 작은 메시지를 자주 주고받는 데 맞춘 메시지 방식으로, 드론은 자기 ID가 들어간 주제(topic)로 메시지를 올리고, 임무 서버는 그 주제를 구독해 받습니다. 받은 값은 시계열 데이터베이스에 저장하고, 관제 화면에는 최신 값만 바로 전달합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.2 임무 관리 API (중)
<!--meta: sec=s6; dept=BE; level=주니어; ct_band=중-->
점검 임무는 "어느 경로를, 어떤 순서로, 어디서 무엇을 촬영할지"를 담은 문서입니다. 운영자가 관제 화면에서 임무를 만들면 임무 서버가 경로의 안전성(금지 구역 통과 여부, 배터리로 다녀올 수 있는지)을 먼저 검사한 뒤 드론에 내려 보냅니다. 임무는 대기, 비행 중, 일시 정지, 완료, 실패 상태를 가지며, 상태가 바뀔 때마다 기록을 남깁니다. 한 드론에 임무가 여러 개 쌓이면 대기열 순서대로 실행합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.3 메시지 순서와 중복 (상)
<!--meta: sec=s7; dept=BE|EMB; level=주니어|시니어; ct_band=상-->
창고 안의 무선 연결은 자주 끊깁니다. MQTT의 "최소 한 번 전달" 설정에서는 연결이 끊겼다 이어질 때 같은 메시지가 두 번 오거나, 늦게 보낸 메시지가 먼저 도착할 수 있습니다. 그래서 드론이 메시지마다 일련번호와 기체 시각을 붙이고, 서버는 이미 받은 번호를 버리고 시각 순서로 정렬해 저장합니다. 명령(이륙, 정지, 귀환)은 텔레메트리와 달리 정확히 한 번 실행되어야 하므로 명령 ID로 중복 실행을 막습니다.

## 스카이패스 4. 관제 화면 기본 기술 > 4.1 실시간 위치 표시 (하)
<!--meta: sec=s8; dept=FE; level=신입; ct_band=하-->
관제 화면은 창고 평면도 위에 드론 위치를 점으로 표시합니다. 서버에서 WebSocket으로 받은 최신 위치를 화면 좌표로 바꾸어 그리는데, 위치가 초당 10번 들어와도 화면은 초당 60번 그리므로, 두 위치 사이를 부드럽게 이어 그립니다. 연결이 끊기면 마지막 위치에 회색 표시를 하고 "연결 끊김"을 띄웁니다.

## 스카이패스 4. 관제 화면 기본 기술 > 4.2 3D 지도와 경로 편집 (중)
<!--meta: sec=s9; dept=FE; level=주니어; ct_band=중-->
운영자는 3D 지도에서 점검 경로를 직접 그립니다. 선반 높이까지 고려해야 하므로 평면이 아니라 3차원으로 점을 찍고, 화면은 경로가 금지 구역이나 선반과 너무 가깝게 지나가면 빨간색으로 경고합니다. 3D 지도의 좌표는 지도 좌표계(ENU)를 그대로 쓰고, 화면에 그릴 때만 화면 좌표로 바꿉니다.

## 스카이패스 4. 관제 화면 기본 기술 > 4.3 점검 결과 검토 화면 (상)
<!--meta: sec=s10; dept=FE|AI; level=주니어|시니어; ct_band=상-->
한 번의 점검 비행에서 사진이 수천 장 나옵니다. 검토 화면은 AI가 이상으로 판단한 사진만 먼저 보여 주고, 사진을 누르면 지도에서 그 사진을 찍은 위치와 방향을 함께 보여 줍니다. 운영자가 "정상"이나 "이상"으로 확정한 결과는 다시 AI 학습 데이터로 쓰이므로, 확정 버튼을 누를 때 실수를 줄이는 화면 설계가 중요합니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.4 관성 센서 보정 (하)
<!--meta: sec=s11; dept=EMB|AI; level=신입; ct_band=하-->
관성 측정 장치(IMU)의 가속도와 각속도 값에는 장치마다 다른 치우침이 있습니다. 비행 전 기체를 평평한 곳에 가만히 두고 값을 모아 치우침을 빼고, 온도에 따라 달라지는 정도도 기록합니다. 보정 값이 저장되지 않으면 기체가 이륙 직후 한쪽으로 기우는 증상이 나타납니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.5 카메라 보정과 왜곡 (하)
<!--meta: sec=s12; dept=AI|EMB; level=신입; ct_band=하-->
카메라 렌즈는 화면 가장자리를 휘어 보이게 합니다. 바둑판 무늬를 여러 각도에서 찍어 초점 거리와 왜곡 계수를 구하고, 위치 추정에 쓰기 전에 영상을 펴 줍니다. 카메라를 다시 조립하거나 교체하면 보정을 다시 해야 합니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.6 센서 융합 필터 (중)
<!--meta: sec=s13; dept=AI|EMB; level=주니어; ct_band=중-->
카메라로 구한 움직임은 느리지만 누적 오차가 적고, 관성 센서는 빠르지만 오래 쓰면 오차가 쌓입니다. 칼만 필터 계열의 융합 필터로 둘을 합쳐, 관성 센서로 예측하고 카메라 값이 들어올 때마다 고칩니다. 두 센서 값의 시각을 맞추지 않으면 융합 결과가 오히려 나빠집니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.7 비행 제어 루프 (중)
<!--meta: sec=s14; dept=EMB; level=주니어; ct_band=중-->
비행 제어기는 목표 자세와 현재 자세의 차이로 모터 출력을 정합니다. 제어 루프는 정해진 주기로 돌아야 하므로, 다른 작업이 제어 루프를 늦추지 않게 우선순위를 나눕니다. 제어 이득을 바꿀 때는 시뮬레이터에서 먼저 시험하고, 실제 기체에서는 줄에 묶어 시험합니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.8 계기판 판독 모델 (중)
<!--meta: sec=s15; dept=AI; level=주니어; ct_band=중-->
점검 드론은 압력계, 온도계 같은 바늘 계기판을 찍어 값을 읽습니다. 계기판 영역을 먼저 찾고, 바늘 각도를 눈금으로 바꾸는 두 단계로 처리합니다. 비스듬히 찍힌 영상은 원근 보정을 한 뒤 읽고, 읽은 값의 신뢰도가 낮으면 사람이 확인하도록 표시합니다.

## 스카이패스 2. 임베디드·위치 추정 기본 기술 > 2.9 안전 기능 시험 체계 (상)
<!--meta: sec=s16; dept=EMB|AI; level=주니어|시니어; ct_band=상-->
위치 추정 실패, 통신 끊김, 배터리 부족 같은 상황마다 드론이 해야 할 행동(멈춤, 귀환, 착륙)을 표로 정하고, 상황마다 시뮬레이터 시험과 실제 비행 시험을 짝지어 둡니다. 새 기능을 넣을 때는 이 표의 모든 상황을 다시 시험해야 배포할 수 있습니다. 시니어는 시험으로 다 덮을 수 없는 상황을 어떻게 줄일지 설명할 수 있어야 합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.4 비행 기록 조회 API (하)
<!--meta: sec=s17; dept=BE|FE; level=신입; ct_band=하-->
관제 화면은 지난 비행 기록을 날짜, 드론, 임무로 찾아봅니다. 기록이 많아 한 번에 모두 주지 않고, 마지막으로 받은 항목 다음부터 이어 받는 방식으로 나눠 줍니다. 쪽 번호 방식은 중간에 새 기록이 들어오면 항목이 겹치거나 빠지기 때문입니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.5 임무 예약과 스케줄러 (하)
<!--meta: sec=s18; dept=BE; level=신입; ct_band=하-->
점검 임무는 매일 같은 시각에 반복되는 경우가 많습니다. 반복 규칙을 저장해 두고 스케줄러가 시각이 되면 임무를 만듭니다. 서버가 두 대여도 같은 임무가 두 번 만들어지지 않게, 임무를 만들기 전에 데이터베이스에 예약 시각과 규칙 번호로 한 번만 기록되게 합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.6 드론 상태 머신과 명령 검증 (중)
<!--meta: sec=s19; dept=BE|EMB; level=주니어; ct_band=중-->
드론은 대기, 이륙, 임무 중, 귀환, 착륙, 점검 필요 같은 상태를 가집니다. 서버는 현재 상태에서 허용된 명령만 보내고, 기체도 같은 표로 한 번 더 확인합니다. 두 곳의 상태 표가 어긋나면 명령이 거절되므로, 표는 한 곳에서 만들어 양쪽에 배포합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.7 점검 영상 저장과 썸네일 (중)
<!--meta: sec=s20; dept=BE|FE; level=주니어; ct_band=중-->
점검 한 번에 사진 수백 장이 올라옵니다. 원본은 객체 저장소에 두고, 업로드가 끝나면 비동기 작업이 작은 썸네일을 만듭니다. 관제 화면은 목록에서 썸네일만 받고, 사용자가 누를 때 원본을 받습니다. 썸네일 작업이 실패해도 원본 업로드는 성공으로 처리합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.8 창고별 데이터 분리와 권한 (상)
<!--meta: sec=s21; dept=BE; level=주니어|시니어; ct_band=상-->
고객사마다 여러 창고가 있고, 운영자는 맡은 창고의 드론과 기록만 봐야 합니다. 모든 API가 요청자의 창고 권한을 확인하고, 권한 확인을 각 API에 흩어 두지 않고 공통 계층에서 처리합니다. 시니어는 권한 변경이 실시간 메시지 구독에도 바로 반영되게 하는 방법을 설계할 수 있어야 합니다.

## 스카이패스 3. 백엔드 기본 기술 > 3.9 경로 충돌 검사 API (상)
<!--meta: sec=s22; dept=BE|FE; level=주니어|시니어; ct_band=상-->
운영자가 새 경로를 저장하기 전에 서버가 지도 위 장애물, 비행 금지 구역, 같은 시간대의 다른 임무 경로와 겹치는지 검사합니다. 검사는 경로를 짧은 구간으로 나눠 공간 색인으로 빠르게 찾습니다. 화면은 겹치는 구간을 빨간색으로 표시하고 저장 버튼을 막습니다.

## 스카이패스 4. 관제 화면 기본 기술 > 4.4 경보 표시와 우선순위 (중)
<!--meta: sec=s23; dept=FE; level=주니어; ct_band=중-->
여러 드론에서 경보가 동시에 올라오면 중요한 경보가 묻힙니다. 경보를 안전(즉시 대응), 임무(확인 필요), 정보 세 단계로 나누고, 안전 경보는 화면 맨 위에 고정하고 소리로 알립니다. 같은 원인의 경보가 반복되면 하나로 묶어 횟수만 늘립니다.

## 스카이패스 4. 관제 화면 기본 기술 > 4.5 3D 화면 렌더링 최적화 (상)
<!--meta: sec=s24; dept=FE; level=주니어|시니어; ct_band=상-->
창고의 선반 수천 개를 하나씩 그리면 화면이 느려집니다. 같은 모양의 선반은 한 번에 여러 개를 그리는 방식(인스턴싱)으로 바꾸고, 멀리 있는 물체는 단순한 모양으로 그립니다. 프레임마다 그리는 물체 수와 걸린 시간을 기록해 성능이 떨어진 변경을 찾습니다.

줄서기는 새벽소프트 커머스사업부가 운영하는 공연·스포츠 티켓 예매 플랫폼입니다. 인기 공연의 예매가 열리는 순간에는 수십만 명이 동시에 접속하고, 좌석 수천 개가 몇 분 안에 팔립니다. 이 문서는 줄서기의 구조와 기본 기술을 정리한 3급(공개 수준) 문서입니다. 공연 기획사 이름과 실제 장애 기록은 2급 문서에서 다룹니다.

## 줄서기 1. 시스템 구성
<!--meta: sec=s1; dept=BE|FE; level=신입|주니어; ct_band=하-->
줄서기는 다섯 부분으로 이루어집니다. 입장 대기열은 예매가 열릴 때 몰려드는 사용자를 순서대로 줄 세우고, 한 번에 정해진 수만 예매 화면으로 들여보냅니다. 좌석 서비스는 좌석 지도와 좌석별 상태(빈 좌석, 선점, 판매 완료)를 관리합니다. 주문·결제 서비스는 선점한 좌석으로 주문을 만들고 외부 결제사와 연동합니다. 예매 화면은 사용자가 대기 순번을 보고, 좌석을 고르고, 결제하는 웹 화면입니다. 데이터팀은 비정상적인 예매 패턴을 분석합니다.

| 부서 | 맡는 부분 | 주요 기술 |
| --- | --- | --- |
| 백엔드플랫폼팀 | 입장 대기열, 좌석 서비스, 주문·결제 | Kotlin, Spring Boot, Redis, PostgreSQL, Kafka |
| 프론트엔드팀 | 대기 화면, 좌석 지도, 결제 화면 | TypeScript, React, Canvas |

## 줄서기 2. 백엔드 기본 기술 > 2.1 입장 대기열 (하)
<!--meta: sec=s2; dept=BE; level=신입; ct_band=하-->
예매가 열리면 모든 사용자는 먼저 대기열에 들어갑니다. 대기열은 Redis의 정렬된 집합에 사용자별 도착 시각을 점수로 넣어 만들고, 매초 정해진 수의 사용자를 앞에서부터 꺼내 입장 토큰을 줍니다. 예매 화면으로 들어가는 모든 요청은 이 토큰을 함께 보내야 하며, 토큰이 없거나 만료된 요청은 대기열로 돌려보냅니다. 이렇게 하면 뒤쪽 서비스가 감당할 수 있는 만큼만 사용자가 들어옵니다.

## 줄서기 2. 백엔드 기본 기술 > 2.2 좌석 선점 (중)
<!--meta: sec=s3; dept=BE; level=주니어; ct_band=중-->
사용자가 좌석을 고르면 결제가 끝날 때까지 다른 사람이 그 좌석을 고르지 못하게 "선점"합니다. 선점은 Redis에 좌석 키를 "없을 때만 쓰기" 명령과 만료 시간(7분)으로 기록하는 방식입니다. 두 사람이 같은 좌석을 동시에 고르면 한 사람만 기록에 성공합니다. 7분 안에 결제하지 않으면 선점이 자동으로 풀립니다. 선점 정보는 빠르지만 사라질 수 있는 저장소에 있으므로, 최종 판매 기록은 반드시 데이터베이스에 남깁니다.

## 줄서기 2. 백엔드 기본 기술 > 2.3 결제 중복 방지 (상)
<!--meta: sec=s4; dept=BE; level=주니어|시니어; ct_band=상-->
결제 버튼을 누른 뒤 응답이 늦으면 사용자는 버튼을 다시 누르고, 앱은 네트워크 오류로 요청을 다시 보냅니다. 같은 결제가 두 번 처리되지 않도록, 주문마다 고유한 멱등 키를 만들어 결제사에 함께 보냅니다. 서버는 이 키로 이미 처리한 요청인지 먼저 확인하고, 처리 중이면 기다렸다가 같은 결과를 돌려줍니다. 결제사 응답을 받지 못한 결제는 "확인 필요" 상태로 두고, 결제사에 조회해 최종 상태를 맞춥니다.

## 줄서기 3. 프론트엔드 기본 기술 > 3.1 대기 화면 (하)
<!--meta: sec=s5; dept=FE; level=신입; ct_band=하-->
대기 화면은 사용자의 현재 순번과 예상 대기 시간을 보여 줍니다. 수십만 명이 몇 초마다 순번을 물으면 서버에 큰 부담이 되므로, 화면은 서버가 알려 준 간격(처음에는 5초, 순번이 앞으로 갈수록 1초)으로만 다시 묻습니다. 새로고침하면 대기열 맨 뒤로 간다고 오해하는 사용자가 많아, 화면에 "새로고침해도 순번은 유지됩니다"를 함께 표시합니다.

## 줄서기 3. 프론트엔드 기본 기술 > 3.2 좌석 지도 그리기 (중)
<!--meta: sec=s6; dept=FE; level=주니어; ct_band=중-->
공연장 좌석은 수천에서 수만 개입니다. 좌석마다 HTML 요소를 만들면 화면이 느려지므로, 좌석 지도는 Canvas 한 장에 그리고 마우스 위치로 어느 좌석인지 계산합니다. 좌석 상태는 몇 초마다 바뀐 좌석만 받아 다시 그립니다. 사용자가 고른 좌석이 그 사이 다른 사람에게 선점되면, 결제 단계로 넘어가기 전에 바로 알려 줍니다.

## 줄서기 3. 프론트엔드 기본 기술 > 3.3 실패를 다루는 화면 (상)
<!--meta: sec=s7; dept=FE|BE; level=주니어|시니어; ct_band=상-->
예매가 몰리는 시간에는 일부 요청이 실패하는 것이 정상입니다. 화면은 실패를 세 가지로 나누어 다룹니다. 다시 시도하면 되는 실패(일시적 과부하)는 자동으로 잠시 기다린 뒤 한 번 더 보내고, 사용자가 바꿔야 하는 실패(좌석이 이미 팔림)는 다른 좌석을 고르도록 안내하며, 결과를 알 수 없는 실패(결제 응답 없음)는 "결제 확인 중"을 띄우고 같은 요청을 다시 보내지 않습니다. 결과를 모르는 상태에서 다시 보내면 중복 결제의 원인이 되기 때문입니다.

## 줄서기 2. 백엔드 기본 기술 > 2.4 공연 정보 조회 API와 캐시 (하)
<!--meta: sec=s8; dept=BE|FE; level=신입; ct_band=하-->
공연 이름, 일정, 가격 같은 정보는 자주 바뀌지 않지만 예매 오픈 직전에 조회가 몰립니다. 서버 앞에 캐시를 두고 일정 시간마다 새로 받으며, 담당자가 정보를 고치면 그 공연의 캐시만 지웁니다. 화면은 캐시된 정보와 실시간 좌석 정보를 따로 받습니다.

## 줄서기 2. 백엔드 기본 기술 > 2.5 예매 내역 조회와 취소 API (하)
<!--meta: sec=s9; dept=BE; level=신입; ct_band=하-->
사용자는 예매 내역을 보고 공연 전날까지 취소할 수 있습니다. 취소는 결제 취소, 좌석 반환, 내역 상태 변경이 함께 일어나야 하므로, 결제 취소가 실패하면 나머지도 바꾸지 않고 다시 시도할 수 있게 상태를 남깁니다. 취소 버튼을 여러 번 눌러도 한 번만 처리됩니다.

## 줄서기 2. 백엔드 기본 기술 > 2.6 대기 순번과 예상 시간 계산 (중)
<!--meta: sec=s10; dept=BE|FE|DATA; level=주니어; ct_band=중-->
대기 순번은 사용자 앞에 남은 사람 수이고, 예상 시간은 순번을 최근 입장 속도로 나눈 값입니다. 입장 속도는 자동 조절로 계속 바뀌므로 최근 몇십 초의 평균을 쓰고, 값이 크게 흔들리면 범위로 보여 줍니다. 순번 조회가 몰려도 대기열 저장소를 직접 두드리지 않도록 몇 초 단위로 계산해 둔 값을 줍니다.

## 줄서기 2. 백엔드 기본 기술 > 2.7 결제 결과 웹훅 처리 (중)
<!--meta: sec=s11; dept=BE; level=주니어; ct_band=중-->
결제사는 결제 결과를 웹훅으로 알려 줍니다. 같은 알림이 여러 번 오거나 순서가 바뀌어 올 수 있어, 결제 번호와 상태 변경 순서를 기준으로 이미 처리한 알림은 무시합니다. 웹훅을 받지 못한 결제는 일정 시간 뒤 결제사에 직접 조회해 상태를 맞춥니다.

## 줄서기 2. 백엔드 기본 기술 > 2.8 좌석 상태 이벤트 스트림 (상)
<!--meta: sec=s12; dept=BE; level=주니어|시니어; ct_band=상-->
좌석 선점, 반환, 판매가 일어날 때마다 이벤트를 메시지 브로커에 남깁니다. 화면 갱신, 매출 집계, 이상 탐지가 같은 이벤트를 각자 읽습니다. 이벤트는 좌석 구역 단위로 순서를 보장하고, 읽는 쪽이 같은 이벤트를 두 번 받아도 결과가 같게 만듭니다. 시니어는 순서 보장 범위를 넓힐 때의 처리량 손실을 설명할 수 있어야 합니다.

## 줄서기 3. 프론트엔드 기본 기술 > 3.4 모바일 예매 화면 (하)

## 줄서기 3. 프론트엔드 기본 기술 > 3.5 좌석 지도 확대와 이동 (중)
<!--meta: sec=s14; dept=FE; level=주니어; ct_band=중-->

## 줄서기 3. 프론트엔드 기본 기술 > 3.6 오픈 순간 정적 자원 배포 (상)
<!--meta: sec=s15; dept=FE|BE; level=주니어|시니어; ct_band=상-->

## 줄서기 3. 프론트엔드 기본 기술 > 3.7 화면 성능 측정과 회귀 방지 (상)

## 줄서기 4. 데이터·AI 기본 기술 > 4.6 탐지 지표와 오탐 비용 (중)

이상 거래 탐지는 놓친 매크로와 잘못 막은 정상 사용자 모두 비용이 있습니다. 정상 사용자 차단은 고객 불만과 환불로 이어지므로, 재현율만 높이지 않고 정상 사용자 오탐률 상한을 먼저 정한 뒤 그 안에서 재현율을 높입니다. 기준값을 정할 때 두 비용을 함께 적습니다.

## 줄서기 4. 데이터·AI 기본 기술 > 4.7 실시간 탐지 모델 서빙 (상)
<!--meta: sec=s23; dept=AI|BE; level=주니어|시니어; ct_band=상-->
예매 도중에 탐지하려면 결제 요청마다 수십 밀리초 안에 점수를 내야 합니다. 무거운 특징은 미리 계산해 저장소에 두고, 요청 때는 가벼운 특징만 계산합니다. 탐지 서버가 느려지거나 멈추면 결제를 막지 않고 점수 없이 통과시키고 나중에 다시 검사합니다.

## 줄서기 4. 데이터·AI 기본 기술 > 4.8 탐지 결과 설명과 이의 신청 (상)
<!--meta: sec=s24; dept=AI|FE; level=주니어|시니어; ct_band=상-->
차단된 사용자에게 이유를 너무 자세히 알려 주면 우회 방법이 됩니다. 화면에는 일반적인 안내와 이의 신청 경로만 보여 주고, 내부에는 어떤 특징이 점수를 높였는지 기록합니다. 이의 신청으로 풀린 사례는 다음 학습에서 정상 사례로 씁니다.

## 줄서기 4. 데이터·AI 기본 기술 > 4.9 데이터 분포 변화 감시 (상)
<!--meta: sec=s25; dept=AI|DATA; level=주니어|시니어; ct_band=상-->
공연 장르, 예매 시각, 매크로 수법이 바뀌면 모델 성능이 떨어집니다. 주요 특징의 분포와 점수 분포를 예매마다 기록해 지난 기간과 비교하고, 차이가 크면 다시 학습할지 검토합니다. 시니어는 다시 학습하는 주기와 검증 방법을 정할 수 있어야 합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.1 단말 구성 (하)
<!--meta: sec=s26; dept=EMB; level=신입; ct_band=하-->
공연장 입구의 게이트 단말은 QR 스캐너, 작은 화면, 문 열림 장치, 통신 모듈로 이루어집니다. 단말은 전원이 들어오면 스캐너와 문 장치를 점검하고, 서버에서 그날 공연 정보를 받은 뒤 입장을 받기 시작합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.2 QR 스캐너 입력 처리 (하)
<!--meta: sec=s27; dept=EMB; level=신입; ct_band=하-->
스캐너는 읽은 값을 문자열로 보내지만, 화면 밝기나 휴대폰 보호 필름 때문에 같은 코드를 여러 번 읽거나 일부만 읽기도 합니다. 단말은 짧은 시간 안에 같은 값이 다시 들어오면 한 번으로 처리하고, 형식이 맞지 않는 값은 버리고 다시 대 달라고 안내합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.3 단말 상태 보고 (하)
<!--meta: sec=s28; dept=EMB|BE; level=신입; ct_band=하-->
단말은 1분마다 입장 처리 수, 오류 수, 통신 상태, 배터리 상태를 서버로 보냅니다. 서버는 보고가 끊긴 단말을 현장 관리자 화면에 표시해, 관리자가 그 게이트로 사람을 보내게 합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.4 오프라인 입장권 검증 (중)
<!--meta: sec=s29; dept=EMB|BE; level=주니어; ct_band=중-->
공연장 통신이 끊겨도 입장은 계속되어야 합니다. 입장권 QR에 서명을 넣어 단말이 서버 없이도 위조 여부를 확인하고, 이미 들어간 입장권 목록은 단말끼리 근거리 통신으로 나눕니다. 통신이 돌아오면 단말에 쌓인 입장 기록을 서버로 보내 맞춥니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.5 단말 시계와 입장권 유효 시간 (중)
<!--meta: sec=s30; dept=EMB; level=주니어; ct_band=중-->
입장권에는 유효 시간이 있어 단말 시계가 틀리면 정상 입장권을 거절할 수 있습니다. 단말은 켜질 때 시간을 맞추고, 맞추지 못하면 유효 시간 판단에 여유를 두고 그 사실을 기록합니다. 시계가 크게 틀린 단말은 관리자 화면에 경고로 표시합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.6 단말 펌웨어 배포 (중)
<!--meta: sec=s31; dept=EMB; level=주니어; ct_band=중-->
단말 펌웨어는 공연이 없는 날에만 배포합니다. 공연장 단말 일부에 먼저 설치하고 시험 입장을 해 본 뒤 나머지에 설치합니다. 설치 중 전원이 꺼져도 단말이 켜지지 않는 일이 없도록 이전 버전을 남겨 둡니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.7 중복 입장 방지와 단말 간 동기화 (상)
<!--meta: sec=s32; dept=EMB|BE; level=주니어|시니어; ct_band=상-->
같은 입장권을 캡처해 두 게이트에서 동시에 쓰는 경우를 막아야 합니다. 단말끼리 입장 기록을 빠르게 나누지만 통신이 늦으면 거의 동시에 두 번 통과할 수 있습니다. 이 짧은 틈을 줄이는 방법과, 남는 위험을 현장 확인으로 처리하는 규칙을 함께 정합니다. 시니어는 오프라인 동작과 중복 방지 사이의 균형을 설명할 수 있어야 합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.8 보안 부팅과 키 보관 (상)
<!--meta: sec=s33; dept=EMB; level=주니어|시니어; ct_band=상-->
단말이 입장권 서명을 확인하려면 공개 키가 필요하고, 단말 자신의 인증에는 비밀 키가 필요합니다. 비밀 키는 단말의 보안 저장 영역에 두어 꺼낼 수 없게 하고, 서명된 펌웨어만 부팅되게 합니다. 단말을 잃어버리면 서버에서 그 단말의 인증을 바로 끊을 수 있어야 합니다.

## 줄서기 5. 공연장 입장 게이트 단말 > 5.9 게이트 처리 속도 측정 (상)
<!--meta: sec=s34; dept=EMB; level=주니어|시니어; ct_band=상-->
공연 시작 직전에는 게이트당 1분에 수십 명이 지나갑니다. 스캔, 검증, 문 열림까지 걸린 시간을 단계별로 기록하고, 가장 느린 단계를 찾아 고칩니다. 측정은 실험실이 아니라 실제 공연장의 조명과 통신 환경에서 다시 확인합니다.
